## 0. 结论先行

**当前助手处在「档 1：只有本次会话」**，与 DeepSeek 网页版同一档位——服务端存着每一轮对话，但**模型读不到**。建议分两步走到「档 2」：

| 步 | 内容 | 新增表 | 收益 |
|---|---|---|---|
| **第一步**（强烈建议） | 历史装配从**客户端**移到**服务端** | **零**（基础设施已存在） | 修掉「刷新后助手失忆、换设备接不上」；同时让历史长度由服务端控制 |
| **第二步**（建议） | **用户级轻记忆**（≤20 条、用户可见可删、写入走既有确认卡片） | 1 张小表 | 助手不用每次重新问「你是不是负责东南亚线」 |

**明确不做**：自动抽取、证据链、置信度、向量检索（§8 说明理由）。

**一条贯穿全文的判据（§3）**：记忆里只放「**不能从库里推导出来的东西**」。

## 1. 现状：四段存储各管一段，「关于用户自己」是空白

| 存储 | 写入方 | 服务于 | **是否进模型** |
|---|---|---|---|
| `assistant_conversation_messages` (V85) | `AssistantConversationService.finish()` | 面板跨刷新接上 | **否** |
| `assistant_action_audit` (V83/V86/V90) | 每轮各写一行，带 `turn_index` | 排障、追责 | 否 |
| `assistant_pending_actions` (V82) | 写动作前 | 确认卡片 | 否 |
| `contact_profile_versions` / `contact_memory_facts` / `contact_memory_observations` / `contact_ai_labels` (V70–V76) | `ContactMemoryWorker` 等 | 客户画像 | 是（经 `contact.brief`） |
| **用户级记忆** | — | — | **不存在** |

**三个缺口**

- **缺口 A：服务端存了历史却不用。** `AssistantConversationLogService.replay(userId, conversationId, limit)` **已经存在**，读取形状正确（`(user_id, conversation_id, created_at, id)` 索引、时间正序、归属条件在 SQL 里）。但它只被 `GET /api/assistant/conversations/{id}/messages` 用来回放，**没有接进 `respond()`**——`respond(userId, conversationId, history, text)` 的 `history` 仍然完全来自请求体。
- **缺口 B：没有任何「关于当前用户」的记忆。** 现有记忆全是**关于客户的**（业务数据），没有一条是「这个用户是谁、他怎么说话、他反复澄清过什么口径」。
- **缺口 C：会话不是一等实体。** `conversationId` 由前端 `crypto.randomUUID()` 生成、存在 `localStorage['assistant.conversationId']`（`useAssistant.ts`）。服务端**没有会话元数据表**，因此无法列出「我的会话」；换浏览器即换会话号，即使库里那些行还在。

## 2. 三个正交决策

这三个问题决定了任何记忆方案的成本与风险，其余都是它们的推论。

### 2.1 谁装配上下文（对应缺口 A）

- **现在**：`useAssistant.ts` 取 `items.slice(-8)` → 请求体 → `AssistantRequestGuard.trimHistory` 再裁一次 → `AssistantPromptBuilder.buildMessages`。前端是先裁一遍、服务端再裁一遍的**双重裁剪**。
- **建议**：**以服务端为唯一真相。**

```
conversationId 存在 → 服务端按 (userId, conversationId) 查库装配；请求体的 history 被忽略
conversationId 缺失 → 退回请求体 history（保持现有行为，兼容老前端与单轮提问）
```

- **为什么第二条规则不能删**：`history` 可空是**合法用法**（单轮提问），且老版本前端仍会传它。直接删参数会让老前端 400。所以是「以服务端为准」而不是「取消参数」。
- **代价**：多一次 DB 查询（有索引，可忽略）；前端的 `items.slice(-8)` 变成**乐观 UI 的预览**，不再决定模型看到什么——**这一点必须写进前端注释**，否则下一个人会以为改前端能改上下文。

### 2.2 什么活过请求边界（对应缺口 B、C）

现有四条边界都是「不活」：工具结果明细不跨请求（`appendAssistant` 只存一句话）、确认卡片状态不进历史、候选集每次重建。

建议新增**一条**且只有一条边界：**用户级记忆**。它的内容由 §3 的判据约束。

会话升为一等实体（缺口 C）**本次不做**——见 §9 未决问题 3。

### 2.3 超限怎么办

- **现在**：`trimHistory` 静默从新往旧保留，更早的轮次**无声消失**。模型拿着残缺上下文照样自信作答，用户不知道。
- **建议两件事，方向相反但互不冲突**：

| 场景 | 正确做法 | 理由 |
|---|---|---|
| **历史**（会自然变长，无法避免） | **让裁剪可见**：响应里带一个标记，前端提示「较早的对话已不在本次上下文中」 | 读取侧只能在「丢」和「报错」之间选，报错不可接受，那就必须让「丢」被看见 |
| **记忆**（长不长由我们决定） | **在写入侧设限**：满 20 条时拒绝新增并提示先删 | 写入侧**可以报错**，读取侧不能 |

**这条是本方案最重要的一条工程原则**：静态记忆的成败不在「记多少」，而在「**超限时是否有人知道**」。在写入侧设限，是唯一能让超限产生**可行动错误**的位置；放到读取侧就只剩静默截断一条路。

## 3. 核心判据：只放「不能从库里推导出来的东西」

记忆同时是资产和负债：它替模型省下检索步骤，但也可能变成**第二份真相**——过期、与库不一致，而模型更信它（它看起来像"用户亲口说的"）。

因此判定一条内容能不能进记忆，只用一个问题：

> **这件事能不能从库里查到？**
> 能 → **不许存**（存了就是缓存，会过期，且与库冲突时无法裁决）
> 不能 → 可以存

按这个判据筛一遍：

| 想记的内容 | 能查到吗 | 结论 |
|---|---|---|
| 「张总是谁、什么偏好」 | 能，`contact.brief` | **不存** |
| 「我有哪些待办」 | 能，候选集自带 | **不存** |
| 「上次聊了东南亚线」 | 能，`replay()`（第一步之后就能） | **不存** |
| 「我负责东南亚线，不是欧美线」 | **不能**（`users` 表没有这个字段） | 存 |
| 「我们说的『客户』默认指货代，不是外贸公司」 | **不能** | 存 |
| 「回复给我用表格，别写长段落」 | **不能** | 存 |

⇒ 合法内容只剩三类，可枚举：

- `IDENTITY` — 我是谁、负责什么范围
- `GLOSSARY` — 我们内部的行话/口径（这个项目术语歧义真实存在：国内/海外联系人、4 类渠道）
- `PREFERENCE` — 输出偏好

**反过来也成立**：这三类都**不该**放进 `users` 表做正式字段。因为它们是**给模型看的语境**，不是系统行为的配置项——写进 `users` 会让人以为改了它系统行为会变。

## 4. 划界：为什么不复用 `contactmemory` 的表

`contact_*_memory` 系（V70–V76）是一套很重的机器：证据链表、置信度、观测→事实的提升、lease/fencing、Worker + Scheduler。**不要把它扩成通用的**，三条理由：

1. **归属人语义相反**。`contact_memory_facts` 的 `owner_user_id` 是**录入人**（记忆归属人）——所以 `ContactBriefProvider` 才必须判 `userId.equals(contact.getCreatedBy())` 来决定记忆可见性，也才有 doc §7.5 那条「记忆可见性 ≠ 联系人可见性」。用户记忆的 `owner` 就是**本人**，`where user_id = ?` 天然隔离，没有这层。
2. **输入可信度相反**。客户记忆的输入是**机器从聊天里猜的**，所以需要证据链与置信度来兜住误判。用户记忆的输入是**用户自己明说的**（§6 的写入路径保证了这点），不需要证据链。
3. **生命周期相反**。客户记忆会 stale（客户需求会变），要靠 `stale_at` / `last_confirmed_at` 管理。用户的一条偏好只有「对/不对」两种状态，错了就删。

**结论**：新建独立小表，不复用、不抽象成通用层。抽一个「通用记忆框架」会把两套相反语义压成一套，那正是下一堆 bug 的来源。

## 5. 数据模型

```sql
CREATE TABLE assistant_user_memory (
    id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id      uuid NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    kind         varchar(24) NOT NULL,
    content      varchar(200) NOT NULL,
    -- 来自哪次对话（可空：也允许将来从设置页手写）
    conversation_id uuid,
    created_at   timestamptz NOT NULL DEFAULT now(),
    updated_at   timestamptz NOT NULL DEFAULT now(),
    CONSTRAINT ck_assistant_user_memory_kind
        CHECK (kind IN ('IDENTITY', 'GLOSSARY', 'PREFERENCE')),
    CONSTRAINT ck_assistant_user_memory_content
        CHECK (length(btrim(content)) > 0)
);

-- 唯一的读取形状：某用户的全部记忆。注入时永远全量读（记忆体量小），所以不建 kind 上的索引。
CREATE INDEX ix_assistant_user_memory_user
    ON assistant_user_memory (user_id, created_at, id);

COMMENT ON TABLE assistant_user_memory IS
    'User-authored context for the assistant (who they are, house jargon, output preferences); never business data, which must be queried instead';
```

**为什么只有 3 列有意义、且刻意不设唯一约束**

- `content` 是自由文本，做语义去重需要规范化，而规范化会开始吞掉细微差别（「用表格」vs「尽量用表格」）。**去重交给用户**：超过 20 条时写入被拒并提示先删（§2.3）。
- **不存 `normalized_*`**：那是 `contact_memory_facts` 为了跨批次合并同类事实才需要的，这里没有那个需求。

**上限（全部是 `public static final` 常量，不是配置项）**

| 常量 | 值 | 理由 |
|---|---|---|
| `MAX_PER_USER` | 20 | 写入侧拒绝点。注入是**每次请求**都发生，无上限等于成本无上限 |
| `CONTENT_MAX` | 200 | 一条记忆是一句话，不是一段文档 |
| 最坏注入体积 | 20 × 200 = **4000 字符** | 与 `assistant.maxHistoryChars=8000` 同量级，占前缀预算的一半，可接受 |

**为什么是常量而不是 `assistant.*` 配置**：与 doc §7.5 的限额同理——这些值直接决定提示词体积。做成配置项，调大一个量级不会报错，只会让每次调用悄悄变贵；而做成常量，想改就得改代码，改的时候会被 code review 看见。

## 6. 写入路径：复用既有确认卡片，不新增安全面

**只有一条写入路径**：用户在对话里说「记住…」→ 模型调 `memory.remember`（**写动作**）→ `AssistantActionPolicy` 判为 `CONFIRM` → 落 `assistant_pending_actions` → 用户点确认 → 落库。

选这条路径的理由是它**零新增机制**：

- 写动作 → 确认卡片：既有（`AssistantPendingActionService.create`）
- 「改成了什么」的可视化：既有（V90 的 `changes` 列，`[{"field","label","before","after"}]`）
- 审计：既有（`AssistantActionAudit`，`decision=CONFIRM` / `result=PENDING`）
- 删除同理：`memory.forget` 走 CONFIRM，卡片上显示「将要删除：<该条内容>」

**为什么不做自动抽取**（即「模型观察到用户反复要求表格，就自己记一条」）：

- 它需要重造 `contactmemory` 那套重机器（§4），而信号强度远低于客户对话——用户很少说「我偏好 X」，更多是行为暗示；
- 更关键：**记错一条偏好会污染之后所有回答**，而用户不知道它从哪来。明说 + 确认把这条风险压到零。

**注入方式**

- 位置：`AssistantPromptBuilder.buildMessages` 的 **system 块内新增一个小节**（不新增一条 message，避免与「历史」混淆）。
- 必须带一句限权语：**「这些是用户先前告诉你的语境，可能已过时；与库中事实冲突时以库中查询为准。」** —— 记忆不能凌驾于工具结果之上，否则 §3 的「第二份真相」风险就回来了。
- 可见性：`GET /api/assistant/memory` 返回全部记忆，前端「助手记得我什么」入口可逐条删。**记忆必须可被用户检查**——这是它能被信任的前提。

## 7. 实施路径

每一步都可独立上线、独立回滚。

### 第一步 · 服务端装配历史（零新表）

1. `AssistantConversationService.respond` 增加分支：`conversationId != null` 时用 `conversationLog.replay(...)` 取历史，忽略请求体 `history`；否则维持现状。
2. `replay` 的 `limit` 与 `trimHistory` 对齐（同为 `maxHistoryTurns` 口径）——**注意命名陷阱**：`maxHistoryTurns` 量的是**消息条数**，8 条 ≈ 4 个来回。
3. 前端 `items.slice(-8)` 保留（乐观 UI），加注释说明它不决定模型看到什么。
4. 新增测试：同一 conversationId 二次请求，第二次的历史来自库而非请求体（带一个**故意伪造的** `history`，断言它没被采用）。这条测试是这一步的验收点。

**回滚**：单一分支，配置项可选（`assistant.server-side-history=true/false`）。

### 第二步 · 用户级轻记忆

1. 迁移 `V91__assistant_user_memory.sql`（§5）
2. `AssistantUserMemoryService`：`list(userId)` / `remember` / `forget`，全部带 `where user_id`
3. 工具 `memory.remember` / `memory.forget`（写）——注册进 `ToolRegistry`，`AssistantActionPolicy` 判 `CONFIRM`；**不需改只读白名单**
4. 注入：`AssistantPromptBuilder` 的 system 块新增一节 + 限权语
5. `GET /api/assistant/memory` + 前端查看/删除入口
6. 测试：越权（A 读不到 B 的记忆）、上限拒绝（第 21 条）、注入最坏体积（20×200 仍在上限内）、写入必须经 CONFIRM

### 第三步 · 让裁剪可见（§2.3）

响应体加一个字段标记「历史被裁剪过」，前端在气泡上方显示一行提示。**与第一、二步解耦，可随时插入。**

## 8. 非目标（明确不做）

| 不做 | 理由 |
|---|---|
| 自动抽取用户记忆 | §6；记错偏好的污染面大于收益 |
| 证据链 / 置信度 / 观测提升 | §4；用户明说的内容不需要机器推断的那套防护 |
| 向量检索 / embedding 记忆 | 20 条记忆全量注入即可，加检索层是为不存在的问题建基础设施 |
| 跨用户共享记忆（团队级） | 权限模型要重做（参考 §4 的归属人问题），当前无需求 |
| 会话升为一等实体 | §9 未决 3 |
| 记忆里存业务数据 | §3 判据直接禁止 |

## 9. 未决问题

1. **提示词预算未实测**。§5 的最坏注入体积是算出来的（4000 字符），没有实测它对总提示词与延迟的影响。第二步实施前应像 §7.5 那样构造最坏情况跑一次真实链路。
2. **`maxHistoryTurns=8` 是否偏保守**。若模型切到 128K 以上窗口，这个值明显偏低；若维持现状，8 条 ≈ 4 个来回对「会前准备」这类多轮场景偏紧。取决于运维侧给助手配什么模型——**这是产品决策，不是代码决策**。
3. **会话要不要升为一等实体**。缺了它，服务端无法列出「我有哪些会话」，换设备接不上。但要新增会话表 + 迁移前端 `localStorage` 逻辑，成本远大于前两步。**建议等「跨设备」成为真实诉求再做**——目前没有证据表明它是。
4. **注入位置的一个细节**：system 块内新增小节 vs 独立 system message。选了前者（避免与历史混淆），但没有实测模型对两者的遵从度差异。

## 附：外部参考（本文方案的取舍依据）

四个系统的对照，用于说明「为什么选这一档」：

| | 历史进请求 | 超限处理 | 常驻记忆 |
|---|---|---|---|
| **DeepSeek 网页版** | 重发全量（API 无状态） | **弹「长度上限」拒绝续聊** | **无**（侧边栏是档案，模型不读） |
| **本项目助手（现状）** | 客户端带 8 条 | 静默裁剪 | 无 |
| **WorkBuddy** | 服务端装配 | 滚动摘要 | 三层 |
| **Claude Code** | 重发全量 + prompt caching | ~95% 自动 compact，`/compact` 手动 | CLAUDE.md + 索引式 memdir |

两条被本方案采纳的经验：

1. **DeepSeek 的教训**——「保存 ≠ 记住」。它侧边栏存着全部历史却从不读，用户以为它记得。本项目有同样的隐患：`assistant_conversation_messages` 存着每一轮，但模型读不到。**这正是缺口 A 的由来**，也是第一步优先做的原因。
2. **Claude Code 的教训**——它把「静态文件记忆超限」做成**显式报错并要求重写索引**，而本项目的工作记忆是**静默截断**。→ 推论出 §2.3 那条「在写入侧设限」。

一条**未采纳**的：Claude Code 的「索引 + 主题文件」多文件结构。理由是它的成立依赖提示词明确告诉模型「去读 topic file」；本项目的注入只读固定位置，拆出去就是静默降级。**要用先确认注入行为。**

## 10. 实施记录

> 本文原定两步（§7），实际走了五条：① 服务端装配历史 → ② 让裁剪可见 → ③ 只读工具明细跨轮复用
> → ④ 用户级轻记忆 → ⑤ 会话号的兜底与回放失败的可见性。
> ③ 已在动工前被评审**否决**（2026-09-22 拍板）；④ 仍待口径确认；①②⑤ 已完成。
> 因此本文的落地清单是「§7 的两步 + ⑤」——**③ 与 ④ 没有代码**。
> ⑤ 严格说不属于记忆架构，它来自另一条追问：「每次打开都是新的聊天框吗，之前的记录呢？」

### ① 服务端装配历史 —— 已完成（2026-09-22）

**落点与草案不同，且实施时发现一个必须先修的问题。**

**1. `replay()` 不能直接用 —— 草案 §0 说「基础设施已现成」，这个说法不准确。**

它的 SQL 是 `order by created_at asc, id asc limit n`，取的是**最旧**的 N 条。短会话里看不出差别，
长会话里它会把「刚说过的话」全部丢掉、留下对话开头 —— 而指代（「那条」「改成后天」）恰恰指向
刚说过的话。这正好是 §2.1 要解决的问题本身。

⇒ 新增 `listRecentByConversation`（`desc` + Java 侧反转），并把归属谓词抽成
`WHERE_OWNED_BY_USER` 常量供两个读方法共用 —— 让「写第三个读方法时漏掉 `user_id`」
在结构上不可能发生。`replay()` 的 `asc` 保持不动：面板回放要的就是从开头读。

**2. 落点在 `AssistantController`，不在 `respond()`。** 草案 §2.1 没定死这一点。
选 Controller 的理由：`AssistantRequestGuard` 的职责本就是「给编排层一份已经合规的输入」，
而「历史从哪来」与「裁剪」属于同一件事；放进 `respond()` 就得给它注入 guard，
等于让编排层开始关心 HTTP 入参的形状。结果是 **`AssistantConversationService` 一行未改**。

**3. 回退规则**：`conversationId != null` 且库中有记录 → 以库为准；否则用请求体
（第一轮、无会话号的单轮提问、`@WebMvcTest` 这类未装配日志服务的环境）。
`limit` 取 `max-history-turns` —— 读多了是白读，读少了让「条数上限」这个配置失去意义。

**验收**：`theServerSideHistoryWinsOverTheRequestBody` —— 请求体塞 3 条**伪造**的历史，
断言 `respond` 收到的是库里那 2 条。其余用例在两条路径下结果相同，**只有这条能钉住顺序**。

### ② 让裁剪可见 —— 已完成（2026-09-22）

- `AssistantRequestGuard.trimHistory` 现在同时数出「丢了多少条」。分母是**有效历史**
  （空消息不计入）—— 否则「丢了 3 条」里会混进本来就没有内容的行，那个数字会变得不可信。
- 两个 `break` 分支（条数触顶 / 单条超预算）都会计数，各有测试：只改一处是这里最容易犯的错。
- 载体是 `AssistantTurnResult.HistoryTrim(droppedMessages)`，**`null` 表示一条没丢**（字段整体缺席），
  刻意不用 `0`：前端不该分两次判「是 0 还是不存在」。
- 传递用 `withTrimmedHistory(int)` 实例方法而非加构造参数 —— 裁剪是 HTTP 边界的事，编排层不该知道。
  所以 ② 同样**没有碰 `AssistantConversationService`**。
- 前端做成**会话级状态**（`useAssistant.trimmedHistory`）而不是每条消息上的字段：
  一旦开始丢，后面每轮都会丢，逐条显示只是一片重复噪音。渲染在输入框上方，
  措辞用「记不住」而不是「不在上下文里」—— 用户要判断的是「我需不需要重说一遍」。

**一条刻意的不对称**：`applyResult` 只在 `historyTrim` **出现**时更新状态，
绝不因为「没看到」而清空 —— 确认 / 取消的响应本来就不带这个字段，
按「没看到 = 没裁剪」处理会把提示误清掉。前后端各有一条测试钉住这件事。

**已知局限（明确记录）**：`trimmedHistory` 只活在内存里。刷新后回放接口不返回该信息，提示会消失。
要持久就得把裁剪规模落到消息行上（一次迁移）。**目前不做** —— 提示的主要价值在「当场」，
而刷新是一次自然的重新开始。

**验证**：ControllerTest 11→16 例、GuardTest 7→11 例（+9 例全绿）；
前端 3 个新用例覆盖「显示提示 / 不因缺席而清空 / 新会话清掉」。

### ③ 只读工具明细的会话内复用 —— **已否决**（2026-09-22 拍板不做）

**原案**：把只读工具的白名单投影（如 `ContactBrief.toData()`）随会话存下来，下一轮直接回放，
省掉「再问一句『他呢』就要重新检索」的那次往返。合规红线当时写得很清楚（只存投影、原文与转写不进）。

**把这条链路读完之后，原案站不住，三个理由按重要性排序：**

1. **它与本文 §2.2 自相矛盾，也就是与 §3 的判据冲突。** §2.2 的结论是「现有四条边界都不活，
   只新增**一条**且只有一条：用户级记忆」，而它列的第四条边界正是「工具结果明细不跨请求」。
   把明细变活等于新增第二条边界 —— 可 §2.2 判定它不该活，理由只有一条：那些内容**都能从库里重查到**。
   工具明细是「能查到」的典型，**存它就是缓存**（§3 明确禁止）。
2. **它会挤掉真正的对话。** 历史窗口 `max-history-turns=8` 量的是**条数**（8 条 ≈ 4 个来回），
   而单条 observation 上限 `OBSERVATION_MAX_CHARS=4000`。一条回放的明细就能顶掉好几轮真实对话，
   还会**更频繁地触发 ② 刚做的「裁剪提醒」** —— 用「提醒用户它记不住了」换「少一次检索」，方向反了。
3. **收益比看上去小，且方向是往「过期」走。** `contact.brief` 落进历史的那句话
   （`ContactAssistantTools.describe`）本就做了「点名 + 说有哪些节」，而模型的**原始回复**
   （`AssistantTurnResult.answer(reply)`）也是整段落进历史的。所以上一轮看过的内容里，
   **凡是被说出口的，历史里已经有了**；③ 真正补的只是「模型看到但没说出口」的那部分明细 ——
   而重查那部分明细是**新鲜的**（画像/事实/标签由 `ContactMemoryWorker` 按日更新），回放反而是过期源。

**结论**：③ 是用「永久上下文膨胀 + 过期风险」去换「一次只读往返」，而那次往返在 `max-read-turns=3`
的预算内、且返回的是新鲜数据。**建议不做**。若确实要压掉这次往返，更合适的落点是
「跨轮保留已检索到的**引用**（contactRef）而不保留明细」—— 但那等于把「候选集」这条边界也变活，
与 §2.2 冲突，要改就得先改那份判断，而不是**偷偷加一条通道**。

### ④ 用户级轻记忆 —— 待确认口径

§7 的信号清单（同一条背景解释 3 次以上 / 用户自发的「记住…」/ 出现第二个用户）尚未满足，
且这一步引入第一张「关于用户自己」的表，动工前与用户确认一次口径。

### ⑤ 会话号的兜底与回放失败的可见性 —— 已完成（2026-09-22）

它严格来说不属于记忆架构（不含任何存储），但它决定了**这套记忆「看起来」是不是残缺的**。
两条都来自同一个追问：「每次打开聊天框都是新的吗，之前的记录呢？」

**1. 打开面板时的回放失败被静默了 —— 而它的长相正是「记录没了」。**

`useAssistant.loadHistory` 的 catch 只打一句 `console.warn`。于是「助手没开启」（503）与
「刚开了一段新会话」在屏幕上**完全一样**：都是一片空白。而这两件事下一步动作正相反 ——
一个什么都不用做，一个得去查开关。现在分两路说出来：

- 503（`ASSISTANT_DISABLED` / `ASSISTANT_UNAVAILABLE`）→ 复用既有的 `unavailable`：顶部显示
  与发送失败**同一句**「AI 助手未开启」，并禁用输入框；
- 其余失败（断网、5xx）→ 新的 `historyError`，一条独立提示「上面这段对话没能读回来」。
  **不写进对话**：那会让人以为「我刚才那句话失败了」，可他还什么都没说。

`historyError` 不会因为后面某一轮成功就清掉 —— 它说的是「屏幕上缺了一段」，一次成功的新请求
补不回缺掉的那段（与 ② 里 `trimmedHistory` 同一条道理）。只有「新会话」清它。

**2. 会话号只活在浏览器里 —— 清缓存/换设备就等于失忆。**

会话号是前端生成、存 `localStorage` 的（它只是分组标签，不是凭证）。记录一直在
`assistant_conversation_messages` 里，丢的只是那个号。故新增
`GET /api/assistant/conversations/latest`，**零迁移**：`where user_id = ? order by created_at desc,
id desc limit 1`。端点没有路径参数、没有请求参数 —— 谁在问由认证上下文决定；
**一旦允许传号进来，它就从「查询」变成了「用别人的号探路」的入口**。返回体用
`{"conversationId": null}` 表达「服务端明确说没有」，而不是 204 / 404：后者会让前端把
「没有」与「这次出错了」归成一类，而两者的处置相反。

**3. 兜底必须让位于「用户主动开的新会话」—— 这是本步最容易做错的地方。**

服务端的答案是从**消息表**推的，所以它看不见一段「刚开、还没说话」的新会话，问它只会拿回
上一段对话。若让服务端说了算，用户点过「新会话」之后只要重开面板，他刚丢掉的那段就会自己回来 ——
**恰好否定了「新会话」这个唯一能清空上下文的入口**。所以：

- 本地号**优先**，服务端只在它读空时介入（常态路径不多发一次请求）；
- 两道闸：内存里的 `localActivityRef`（用户已经在这段里说过话）与持久化的
  `assistant.conversationStarted`（用户主动开的新会话还没被服务端收到）。后者在
  **服务端确认收到第一轮**时清除 —— 依据是「服务端确认」而不是「用户按下发送」，
  因为失败的发送不会在库里留下任何东西，那时撤掉标记会让用户刚丢掉的那段又回来。

**已知局限**：另一台设备上仍会拿回上一个会话 —— 服务端手里没有能区分「用户主动开了新会话」
与「这是台新设备」的信息，那个区别只存在于用户点那一下的意图里。要修得把「当前会话」写到
服务端，那是另一次迁移，**目前不做**。

**验收**：后端 `AssistantControllerTest` 16→19、`AssistantConversationLogServiceTest` 11→14、
`AssistantDisabledControllerTest` 3→4（两个「读会话」的端点也落在开关之下，否则关掉助手时
前端会把 404 当成「接口写错了」）；前端 21→25，其中
`never overwrites a conversation the user started on purpose` 是这一步的**回归防线**：
它模拟「点新会话 → 关面板 → 再打开」，断言不仅看不到旧对话，而且**根本没有问服务端**。
