# 企业微信连续消息段渲染设计

**日期：** 2026-08-10
**状态：** 已确认，等待实施
**替代：** 本文废止同文件早期版本中的“每条消息一个 OpenDataFrame”和“每个联系人一个 OpenDataFrame”路线。

## 1. 问题与目标

当前时间线为每条企业微信消息创建一个 OpenDataFrame，并使用企业微信官方文档未声明支持的 `display-type="text"`。真实授权环境表明外层 Frame 可以完成挂载，但内部 `ww-open-message` 仍为空白；点击后只是展开同一个空白组件，没有重新加载正文。

本轮目标是按统一时间线把相邻企业微信消息聚合为连续段，每段由一个官方 OpenDataFrame 自动加载，并让点击只承担官方详情预览。页面不得再显示空白消息框或由 `.msg.active` 产生的大面积蓝色轮廓。

本轮不改变会话同步、消息方向、时间线排序、viewer session、密钥来源、专区程序协议、Email、ChatApp、电话记录或 Spring 版前端。

## 2. 平台约束

- `ww-open-message` 正文由企业微信 OpenDataFrame 渲染，父页面不能读取、截断或重新排版正文。
- 使用企业微信官方示例声明的 `message-id`、`secret-key` 和 `open-type="viewMessage"`，不再使用未证实的 `display-type`。
- OpenDataFrame 模板样式只使用官方允许的 class selector，不直接通过 `ww-open-message { ... }` 控制组件内部样式。
- `handleModal` 只处理需要预览的图片、视频、聊天记录等详情；它不是消息正文重新加载事件。
- `modalUrl` 只能存在于当前页面内存和详情 iframe 的 `src`，不得写入日志、审计、后端请求、DOM data 属性或持久化缓存。

## 3. 唯一 Owner 与分段结构

企业微信时间线渲染 owner 保持在 `demo/message-center-demo/src/main/java/com/crmforlogistics/messagecenter/App.java` 的前端模块中。

父页面先按统一时间线顺序划分最大连续企业微信消息段：两个企业微信消息之间只要出现 Email、ChatApp、电话记录或其他条目，就必须结束前一段。单段超过 15 条时再按 15 条切块。每个段块拥有一个 OpenDataFrame，模板使用官方示例的 `wx:for` 一次接收该段最多 15 条 `{ msgid, secretKey }`。

分段和段 ID 是父页面的唯一真源。段 ID 由联系人 ID 与按顺序排列的消息 ID 生成稳定签名；OpenDataFrame 只负责段内官方消息内容，不拥有跨渠道排序。这样企业微信段仍处在原时间位置，Email、ChatApp 和电话记录不会被移入 iframe，也不会被集中到企业微信列表之外。

禁止恢复以下并行路线：

- 每条消息独立创建 OpenDataFrame；
- 把一个联系人的全部企业微信消息集中到单一 OpenDataFrame；
- 使用 `display-type="text"` 伪造单行文本；
- 通过裁剪跨域 iframe 假装获得自适应气泡；
- 点击空白宿主时仅切换 CSS 展开状态。

## 4. 加载流程

1. 用户打开联系人后，父页面按完整统一时间线生成普通条目和稳定企业微信段宿主。
2. 每个企业微信段收集对应的消息引用；单段最多 15 条，超出部分成为紧邻的下一段。
3. 每个段在不可见的准备容器中创建一个 OpenDataFrame，并使用官方 `wx:for` 模板渲染该段消息。
4. 一个段的 `handleMounted` 成功后才显示该段；挂载前不显示空白边框、空 iframe 或占位大框。其他已就绪渠道和企业微信段不等待该段。
5. 后台刷新先重新计算段签名。签名未变化的段复用现有 Frame；新增或变化的段独立准备并在成功后原子替换。
6. 段级重试、登录恢复或组件失效时，只重建受影响段，不重建整个联系人。
7. 联系人切换沿用联系人窗口缓存；段从窗口移除、缓存淘汰、登录失效或页面真正卸载时销毁对应 Frame。

`handleMounted` 只证明段 Frame 已挂载，不能证明每条内部组件都成功。官方文档仅保证 `binderror` 返回未知结构，因此不得假设错误事件一定包含 `msgid`。能够从真实事件稳定解析消息 ID 时记录单条失败；否则退化为段级失败状态和段级重试。

## 5. 展示与交互

- 企业微信段外层不使用 `.msg.active` 的统一蓝色 outline。
- 段宿主位于第一条企业微信消息原位置，后续同段的旧父页面空宿主不再生成；段前后的其他渠道条目保持原顺序。
- 段内布局、消息方向和正文由官方组件负责；父页面不强制官方正文高度、字号或字符截断。
- 官方组件未完成挂载前该段保持隐藏，不留下空框；相邻已就绪内容照常展示。
- 点击已加载的 `ww-open-message` 时，由官方组件触发 `handleModal`。
- 合法 HTTPS `modalUrl` 在当前消息附近原位展开；iframe 完成 load 前保持隐藏，成功后再显示。
- 详情创建或加载失败时删除 iframe，恢复已加载的官方消息条目，不留下大框。
- 同一联系人最多同时保留 15 个详情 iframe；淘汰规则沿用“优先最早且离开视口，否则最早”的确定性策略。

## 6. 错误与重试

- OpenDataFrame 创建或超时：该段显示一个紧凑失败标识，不为段内每条消息创建错误框。
- 单条 `ww-open-message` 报错且事件可稳定关联消息 ID：段首显示失败计数和消息标识，段内其他成功条目保持可用。无法稳定关联时只记录段级失败。
- 重试：销毁并重建受影响段；已有成功 Frame 在替代 Frame 成功挂载前保持可见，首次加载失败才显示紧凑段级状态。
- 登录失效：销毁所有联系人 Frame 和详情 iframe，进入现有重新登录流程。
- 错误日志只记录稳定错误类型、联系人 ID 和消息 ID，不记录 `secretKey` 或 `modalUrl`。

## 7. 资源边界

- 每个连续企业微信段块一个 OpenDataFrame，每个 Frame 最多 15 条消息。
- 当前联系人活动段 Frame 上限为 15；超过上限时只保留最近和视口邻近段，离开活动范围的段销毁实例并保留紧凑的可重载标识。
- 联系人窗口缓存继续限制为 3 个联系人；非当前联系人只保留最近使用的已就绪段，三个联系人合计最多 30 个段 Frame。
- 同一联系人最多 15 个展开详情 iframe。
- 创建队列、超时、取消、缓存淘汰和页面卸载必须有确定性清理。
- 后台自动刷新不得在引用集合未变化时重复创建 Frame。

## 8. 测试与验收

自动化测试必须先失败再实现，并覆盖：

- HTML 不包含 `display-type="text"`；
- 模板不包含裸 `ww-open-message { ... }` 样式选择器；
- 分段算法在任意非企业微信条目处断段，并把超过 15 条的连续段切块；
- 每个段块只创建一个 OpenDataFrame，同一个 Frame 接收最多 15 条按时间排序的消息引用；
- 跨渠道时间顺序保持不变，Email、ChatApp 和电话记录不进入企业微信 Frame；
- 未 `handleMounted` 时不显示空白企业微信段；
- 段签名未变化时刷新复用现有实例；
- 段变化或重试时先创建新实例，成功后再替换旧实例；
- 错误事件不能关联消息 ID 时正确退化为段级失败，不伪造单条错误；
- 企业微信消息不应用 `.msg.active` 大轮廓；
- 详情 iframe 加载成功前隐藏，失败后删除；
- 联系人缓存淘汰、登录失效和页面卸载会销毁 Frame 与详情 iframe。

针对性验收至少运行：

```bash
cd demo/message-center-demo
mvn -q -Dtest=UnifiedMessageStoreTest test
mvn -q test
node contracts/openapi/message-center-v1.test.mjs
mvn -q -DskipTests package
```

真实企业微信授权环境必须补充用户侧证据：打开含企业微信消息的联系人后，无需点击即可看到最近消息；点击消息能打开详情；刷新、切换联系人和自动轮询不会产生空白框、大蓝框或重复白屏。

## 9. 停止条件

若使用官方示例结构的段 Frame 仍为空白，应停止继续调整 CSS，只收集真实 SDK 错误、模板入参和官方最小示例对照证据。`binderror` 无法关联具体消息 ID 时允许按本设计退化为段级失败，但不得伪造关联，也不得通过未文档化属性、自动模拟点击或跨域读取绕过平台限制。
