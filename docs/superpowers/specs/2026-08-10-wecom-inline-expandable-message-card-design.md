# 企业微信连续消息段渲染设计

**日期：** 2026-08-10
**状态：** 自动化验收通过，真实企业微信授权浏览器待验收
**替代：** 本文废止同文件早期版本中的“每条消息一个 OpenDataFrame”和“每个联系人一个 OpenDataFrame”路线。

## 1. 问题与目标

当前时间线为每条企业微信消息创建一个 OpenDataFrame，并使用企业微信官方文档未声明支持的 `display-type="text"`。真实授权环境表明外层 Frame 可以完成挂载，但内部 `ww-open-message` 仍为空白；点击后只是展开同一个空白组件，没有重新加载正文。

本轮目标是按统一时间线把相邻企业微信消息聚合为连续段，每段由一个官方 OpenDataFrame 自动加载，并让点击只承担官方详情预览。页面不得再显示空白消息框或由 `.msg.active` 产生的大面积蓝色轮廓。

本轮不改变会话同步、消息方向、时间线排序、viewer session、密钥来源、专区程序协议、Email、ChatApp、电话记录或 Spring 版前端。

## 2. 平台约束

- `ww-open-message` 正文由企业微信 OpenDataFrame 渲染，父页面不能读取、截断或重新排版正文。
- 使用企业微信官方示例声明的 `message-id`、`secret-key` 和 `open-type="viewMessage"`，不再使用未证实的 `display-type`。
- OpenDataFrame 模板样式只使用官方允许的 class selector，不直接通过 `ww-open-message { ... }` 控制组件内部样式。
- `handleModal` 只处理需要预览的图片、视频、聊天记录等详情；它不是消息正文重新加载事件。
- `modalUrl` 只能存在于当前页面内存和详情 iframe 的 `src`，不得写入日志、审计、后端请求、DOM data 属性或持久化缓存。

## 3. 唯一 Owner 与分段结构

企业微信时间线渲染 owner 保持在 `demo/message-center-demo/src/main/java/com/crmforlogistics/messagecenter/App.java` 的前端模块中。

父页面先根据联系人渠道集合确定布局模式，再按统一时间线顺序划分最大连续企业微信消息段：

- `standalone`：联系人只有企业微信渠道。聊天区域只拥有一个全宽 OpenDataFrame，接收当前最近 15 条消息，并使用整个聊天区域的当前可视高度。父页面即使已经加载更多历史记录，也只把当前 15 条窗口投影到这个 Frame，不再追加第二个整屏 Frame。
- `mixed`：联系人还包含 Email、ChatApp、电话或其他渠道。任意非企业微信条目都会立即结束当前企业微信连续段；段内消息以 6 条为上限均衡切分，使每个 Frame 保持约 4～6 条的紧凑高度。例如 15 条切为 `5/5/5`，16 条切为 `5/5/6`，17 条切为 `5/6/6`，18 条切为 `6/6/6`。

每个段块拥有一个 OpenDataFrame，模板使用官方示例的 `wx:for` 接收该段 `{ msgid, secretKey }`。分组算法只决定 Frame 边界，不改变消息本身的时间顺序。

分段和段 ID 是父页面的唯一真源。段 ID 由联系人 ID 与按顺序排列的消息 ID 生成稳定签名；OpenDataFrame 只负责段内官方消息内容，不拥有跨渠道排序。这样企业微信段仍处在原时间位置，Email、ChatApp 和电话记录不会被移入 iframe，也不会被集中到企业微信列表之外。

禁止恢复以下并行路线：

- 每条消息独立创建 OpenDataFrame；
- 把一个联系人的全部企业微信消息集中到单一 OpenDataFrame；
- 使用 `display-type="text"` 伪造单行文本；
- 通过裁剪跨域 iframe 假装获得自适应气泡；
- 点击空白宿主时仅切换 CSS 展开状态。

## 4. 加载流程

1. 用户打开联系人后，父页面按完整统一时间线生成普通条目和稳定企业微信段宿主。
2. 每个企业微信段收集对应的消息引用；单段最多 15 条，超出部分成为紧邻的下一段。
3. 每个段在视口外、透明但保持真实宽高和布局的准备容器中创建一个 OpenDataFrame，并使用官方 `wx:for` 模板渲染该段消息。准备容器及其祖先不得使用 `display:none` 或 `visibility:hidden`，否则企业微信组件会在零布局宿主上初始化。
4. 一个段的 `handleMounted` 成功后才显示该段；挂载前不显示空白边框、空 iframe 或占位大框。其他已就绪渠道和企业微信段不等待该段。
5. 后台刷新先重新计算段签名。签名未变化的段复用现有 Frame；新增或变化的段独立准备并在成功后原子替换。
6. 段级重试、登录恢复或组件失效时，只重建受影响段，不重建整个联系人。
7. 联系人切换沿用联系人窗口缓存；段从窗口移除、缓存淘汰、登录失效或页面真正卸载时销毁对应 Frame。
8. 后台自动刷新在 60 秒 viewer 缓存窗口内比较当前时间线消息 ID 与 viewer 已加载消息 ID；发现新消息 ID 时立即请求最新 viewer 批次，不等待缓存窗口结束。
9. 历史页批次按布局模式选择：纯企业微信联系人从准备容器的实际渲染投影收集唯一 Frame 的最近 15 条；合并联系人请求本次新增旧页中的企业微信 ID，并与当前有效 viewer 合并，使旧段进入展示窗口而不丢失已有新段。
10. viewer 仍有效但目标 Frame 未挂载时，优先复用现有 `viewer.detail` 重挂载，不得重新创建 viewer session 或重复获取 JS-SDK 配置。mounted 判定只检查当前 viewer 引用能够覆盖的宿主，历史窗口外的 pending 宿主不参与判定。
11. 合并联系人的当前 viewer 批次必须按完整段从后向前装入 15 条预算；预算不足容纳下一个完整段时停止。例如 `5/5/6` 选择最近的 `5+6=11` 条，不得机械截成 `4/5/6`。只有段内全部消息引用齐全时，该段才可创建 Frame 或计为 mounted。

`handleMounted` 只证明段 Frame 已挂载，不能证明每条内部组件都成功。官方文档仅保证 `binderror` 返回未知结构，因此不得假设错误事件一定包含 `msgid`。能够从真实事件稳定解析消息 ID 时记录单条失败；否则退化为段级失败状态和段级重试。浏览器诊断必须分别标记 `create_start`、`mounted`、`message_binderror`、`frame_error`、`frame_create_error` 和 `frame_timeout`，且只输出有长度上限的白名单错误字段。

## 5. 展示与交互

- 企业微信段外层不使用 `.msg.active` 的统一蓝色 outline。
- 段宿主位于第一条企业微信消息原位置，后续同段的旧父页面空宿主不再生成；段前后的其他渠道条目保持原顺序。
- 纯企业微信联系人移除聊天区内边距，段宿主、外层消息和 Frame 使用聊天区域全宽；Frame 高度取聊天区域当前可视高度，由官方容器展示并滚动最近 15 条。窗口尺寸变化时只更新 Frame 外层高度，不销毁或重建 OpenDataFrame。
- 合并联系人中的企业微信段使用按消息数估算的紧凑高度；企业微信行移除父页面头像占位，使入站消息从聊天内容区左侧起始，出站消息仍靠右。
- 段内每条消息由 OpenDataFrame 模板生成“方向行 + 气泡”两层包装；父页面把统一时间线已有的 `inbound/outbound` 方向合并到对应 `{ msgid, secretKey }` 展示引用中，但不把正文传入 Frame。
- 入站方向行左对齐，使用白色、细边框气泡；出站方向行右对齐，使用与现有消息中心一致的浅绿色气泡。气泡最大宽度为 Frame 的 78%，最小高度与现有单行 36px 节奏一致，正文较长时由官方组件决定换行和实际高度。
- 气泡样式只作用于 OpenDataFrame 模板自有 class；不得使用 `ww-open-message { ... }` 选择器修改官方组件内部字号、行高或正文，也不得恢复 `display-type`、字符截断或伪造正文。
- 官方组件未完成挂载前该段保持隐藏，不留下空框；相邻已就绪内容照常展示。
- 点击已加载的 `ww-open-message` 时，由官方组件触发 `handleModal`。
- 合法 HTTPS `modalUrl` 在当前消息附近原位展开；iframe 完成 load 前保持隐藏，成功后再显示。
- 详情创建或加载失败时删除 iframe，恢复已加载的官方消息条目，不留下大框。
- 同一联系人最多同时保留 15 个详情 iframe；淘汰规则沿用“优先最早且离开视口，否则最早”的确定性策略。

## 6. 错误与重试

- OpenDataFrame 创建或超时：该段显示一个紧凑失败标识，不为段内每条消息创建错误框。
- 单条 `ww-open-message` 报错且事件可稳定关联消息 ID：段首显示失败计数和消息标识，段内其他成功条目保持可用。无法稳定关联时只记录段级失败。
- 重试：销毁并重建受影响段；已有成功 Frame 在替代 Frame 成功挂载前保持可见，首次加载失败才显示紧凑段级状态。
- 自动重挂载：首次可立即尝试；失败后按 5、10、20、40、60 秒退避，后续保持 60 秒上限。联系人缓存淘汰、登录失效、页面卸载或成功挂载时清理对应退避状态。
- registry 复用必须同时验证宿主中仍存在 `.wecom-segment-frame`；若 registry 标记 mounted 但 Frame DOM 已丢失，必须销毁失效实例并重新创建，不能返回伪复用成功。
- 登录失效：销毁所有联系人 Frame 和详情 iframe，进入现有重新登录流程。
- 错误日志只记录稳定阶段、段签名、段内消息数量以及 `name`、`message`、`errCode`、`errMsg`、`code`、`type`、`stage`、`status` 白名单字段，不记录 `secretKey`、访问令牌、`modalUrl` 或原始错误对象。

## 7. 资源边界

- 纯企业微信联系人只保留一个 OpenDataFrame，最多展示当前最近 15 条消息并占用一屏聊天区高度；合并联系人每个 OpenDataFrame 最多 6 条企业微信消息。
- 合并联系人采用均衡分组，避免同一连续段出现 `6/6/3` 这类末尾过短 Frame；非企业微信条目仍具有最高断段优先级。
- 当前联系人活动段 Frame 上限为 15；超过上限时只保留最近和视口邻近段，离开活动范围的段销毁实例并保留紧凑的可重载标识。
- 联系人窗口缓存继续限制为 3 个联系人；非当前联系人只保留最近使用的已就绪段，三个联系人合计最多 30 个段 Frame。
- 同一联系人最多 15 个展开详情 iframe。
- 创建队列、超时、取消、缓存淘汰和页面卸载必须有确定性清理。
- 后台自动刷新不得在引用集合未变化时重复创建 Frame。
- 后台自动刷新发现时间线出现 viewer 尚未加载的新消息 ID 时，必须立即请求包含最新 ID 的 viewer 批次；消息 ID 未变化时继续遵守 60 秒刷新间隔。
- viewer 引用集合未变化但 Frame 丢失时，只允许从有效 viewer 重挂载，并遵守有上限的退避；不得由 5 秒时间线轮询反复创建 session。
- mixed viewer 的 15 条上限按完整段计数，禁止切开 4～6 条均衡段；历史页新增旧段通过旧页批次补入现有 viewer。

## 8. 测试与验收

自动化测试必须先失败再实现，并覆盖：

- HTML 不包含 `display-type="text"`；
- 模板不包含裸 `ww-open-message { ... }` 样式选择器；
- 分段算法在任意非企业微信条目处断段，并把超过 15 条的连续段切块；
- 渠道唯一为企业微信时选择 `standalone`，多渠道联系人选择 `mixed`；
- 纯企业微信历史页从 10 条当前消息合并 10 条旧消息后，仍只生成一个宿主，并把实际渲染的最近 15 条完整绑定到该宿主；
- 合并联系人连续 15～18 条企业微信消息分别切为 `5/5/5`、`5/5/6`、`5/6/6`、`6/6/6`；
- 纯企业微信 Frame 使用聊天区可视高度，resize 只调整宿主高度而不重建 Frame；
- 合并联系人移除企业微信行头像占位，且穿插其他渠道时保持原时间线位置；
- 每个段块只创建一个 OpenDataFrame，同一个 Frame 接收最多 15 条按时间排序的消息引用；
- 跨渠道时间顺序保持不变，Email、ChatApp 和电话记录不进入企业微信 Frame；
- 未 `handleMounted` 时不显示空白企业微信段；
- 段签名未变化时刷新复用现有实例；
- 段变化或重试时先创建新实例，成功后再替换旧实例；
- 错误事件不能关联消息 ID 时正确退化为段级失败，不伪造单条错误；
- 企业微信消息不应用 `.msg.active` 大轮廓；
- 详情 iframe 加载成功前隐藏，失败后删除；
- 联系人缓存淘汰、登录失效和页面卸载会销毁 Frame 与详情 iframe。
- 有效 viewer 缺少 mounted Frame 时复用现有 detail；连续后台 tick 遵守重挂载退避；混合联系人窗口外的旧 pending 宿主不触发 session 重建。
- mixed `5/5/6` 在 15 条 viewer 上限下选择完整 `5+6` 段，不渲染部分段；registry 仍 mounted 但 Frame DOM 丢失时会销毁并重建实例。

针对性验收至少运行：

```bash
cd demo/message-center-demo
mvn -q -Dtest=UnifiedMessageStoreTest test
mvn -q test
node contracts/openapi/message-center-v1.test.mjs
mvn -q -DskipTests package
```

真实企业微信授权环境必须补充用户侧证据：打开含企业微信消息的联系人后，无需点击即可看到最近消息；点击消息能打开详情；刷新、切换联系人和自动轮询不会产生空白框、大蓝框或重复白屏。

截至 2026-08-10，分段、段级 Frame、稳定宿主复用、原子重试、详情 iframe 生命周期、BFCache 清理、资源上限、完整 Maven 测试、OpenAPI 合同和打包门禁均已完成自动化验收。本地 fixture 不能渲染企业微信授权组件正文，且当前自动化环境没有可用浏览器，因此真实正文、官方详情和桌面/移动视觉仍必须在服务器授权环境验收；在取得该证据前不得把本文状态改为“完成”。

## 9. 停止条件

若使用官方示例结构的段 Frame 仍为空白，应停止继续调整 CSS，只收集真实 SDK 错误、模板入参和官方最小示例对照证据。`binderror` 无法关联具体消息 ID 时允许按本设计退化为段级失败，但不得伪造关联，也不得通过未文档化属性、自动模拟点击或跨域读取绕过平台限制。
