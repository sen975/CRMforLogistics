# AI Topic 手动整理与联系人合并拆分设计

## 1. 目标

在保留日常自动 Topic 更新的前提下，增加人工可控的历史整理流程，并修正联系人合并、拆分时 Topic 归属不清和历史 Topic 消失的问题。

本设计覆盖四条链路：

1. 按联系方式和时间范围选择消息，人工确认 AI 匹配结果；
2. 普通 Topic 接收新消息后重新生成概要，而不是永久保留旧概要；
3. 联系人合并后，来源 Topic 进入独立待确定区，由用户决定合并、保留或入库；
4. 联系人拆分后，属于被拆联系方式的仓库 Topic 恢复到新联系人的待确定区，但不自动生成正式 Topic。

## 2. 产品边界

- 日常消息仍按现有 6 分钟静默窗口自动触发 Topic 生成或增量更新。
- 普通 Topic 不增加额外的人工确认状态；AI 匹配到已有 Topic 后直接更新该 Topic 的当前标题/概要。
- `REVIEW_PENDING` 只用于联系人合并、联系人拆分和人工历史整理产生的候选 Topic。
- 待确定 Topic 不进入普通时间轴、不进入 Topic 仓库、不参与自动 Topic 匹配。
- 企业微信只使用状态为 `COMPLETED` 且摘要非空的官方单条摘要；未完成、失败、媒体不支持或摘要为空的记录不能进入 AI 输入。
- 消息来源只能归属一个 Topic；移动来源时原位迁移，不复制消息或摘要。
- 群 Topic 始终以 `WECOM_GROUP` owner 独立存在，不迁移到个人联系人 Topic。

## 3. Topic 状态

| 状态 | 普通时间轴 | 自动匹配候选 | 待确定区 | Topic 仓库 | 语义 |
| --- | --- | --- | --- | --- | --- |
| `READY` | 是 | 是 | 否 | 否 | 正常活跃 Topic |
| `REVIEW_PENDING` | 否 | 否 | 是 | 否 | 联系人结构变化或人工整理产生、等待用户决定的候选 |
| `STORED` | 否 | 否 | 否 | 是 | 用户明确入库的 Topic |
| `ARCHIVED` | 否 | 否 | 否 | 否 | 被新 Topic 融合吸收或无来源的历史记录 |

`ARCHIVED` 不再表示等待重算或等待人工确认。普通 Topic 的概要更新不改变其 `READY` 状态。

## 4. 普通 Topic 的自动更新

自动 worker 继续使用现有 owner 和 6 分钟静默窗口：

1. 收集同一 owner 下尚未归类的消息、电话、邮件和已完成企业微信摘要；
2. 将新增来源与同 owner 的 `READY` Topic 做关联；
3. 匹配到已有 Topic 时，使用该 Topic 的完整历史来源、当前概要和新增来源重新生成标题/概要；
4. 低关联来源创建新的 `READY` Topic；
5. 新 Topic 或更新结果通过现有异步任务提交，最终快照事件后前端刷新。

人工编辑过的概要保留在版本历史中，但不锁定后续 AI 更新；当前概要以最近一次成功提交的结果为准。

`REVIEW_PENDING`、`STORED`、`ARCHIVED` 和其他 owner 的 Topic 不参与自动匹配。

## 5. 手动整理流程

联系人时间轴增加“手动整理 Topic”入口，流程为：

1. 选择一个联系方式和起止时间；
2. 服务端按联系人权限、联系方式和时间范围返回候选记录；
3. 用户可以逐条勾选，也可以全选当前结果；单批最多 200 条；
4. 企业微信无有效官方摘要的记录显示为不可选，并显示原因；
5. 用户提交选择后，服务端创建一次有界的 AI 预览任务；
6. AI 将所选记录分别匹配到多个已有 `READY` Topic，或生成一个/多个新 Topic；
7. 预览逐项显示：来源记录、目标 Topic、关联度、预计标题和预计概要；
8. 用户可以调整目标 Topic 或改为新 Topic，然后确认整批应用；
9. 应用时校验来源仍未被其他任务归类、目标 Topic 版本未变化、来源仍属于所选联系方式；校验失败则拒绝过期预览并要求重新生成。

匹配到已有 Topic 时，应用事务使用该 Topic 的全部已有来源加本次选中来源重新生成并保存概要，Topic ID 保持不变。生成新 Topic 时分配新 ID。预览失败或应用失败不改变已有 Topic 快照。

## 6. Topic 融合

Topic 的“合并”统一采用融合生成新 Topic 的语义，包括普通 Topic 与待确定 Topic 的合并：

1. 用户选择至少两个同一 owner 的 Topic；
2. AI 使用所有被选 Topic 的完整来源、标题、概要和时间范围生成融合预览；
3. 用户确认后，在一个事务中创建全新的 Topic 和新 ID；
4. 所有来源原位移动到新 Topic，不复制来源；
5. 所有旧 Topic 改为 `ARCHIVED`；
6. 新 Topic 继承正确 owner、来源范围和最新事件时间；
7. 保存旧 Topic ID 到新 Topic 的融合血缘，并保存新 Topic ID 到旧 Topic 的归档血缘；
8. 任一校验、AI 生成或来源唯一性检查失败时整体回滚，旧 Topic 保持原状态。

不同 owner 的 Topic、个人 Topic 与群 Topic 不允许融合。

## 7. 联系人合并

联系人合并将来源联系人合并到目标联系人，但不把来源 Topic 直接混入目标联系人普通时间轴：

1. 来源联系人的身份转移到目标联系人；
2. 来源联系人标记为 `merged` 并记录 `merged_to_id`；
3. 来源联系人下的 `READY` Topic 转移 owner 到目标联系人，并改为 `REVIEW_PENDING`；
4. 这些候选只出现在目标联系人的待确定区，与目标联系人原有 `READY` Topic 分开显示；
5. 来源联系人下的 `STORED` Topic 保持入库语义并保留审计归属，不自动混入普通时间轴；
6. 待确定 Topic 在人工处理完成前冻结，新到消息仍按目标联系人普通自动流程处理；
7. 待确定 Topic 支持三种处理：
   - 保留：改为目标联系人下的 `READY` 独立 Topic；
   - 入库：改为 `STORED`；
   - 合并：与选定 Topic 融合生成全新 Topic，参与融合的旧 Topic 全部变为 `ARCHIVED`。

合并操作只迁移联系人归属，不迁移群 Topic，不把来源 Topic 与目标普通 Topic 自动拼接。

## 8. 联系人拆分

拆分一个联系方式到新联系人时：

1. 创建新联系人并移动选定联系方式；
2. 按来源联系方式定位消息、邮件、电话记录和可用企业微信摘要；
3. 对 `READY` Topic：
   - 若 Topic 全部来源属于被拆联系方式，则移动到新联系人并改为 `REVIEW_PENDING`；
   - 若 Topic 混合多个联系方式，则从原 Topic 移出被拆来源，形成新联系人的 `REVIEW_PENDING` 候选；原 Topic 保留其他来源并重新生成概要；
   - 若原 Topic 移出来源后为空，则原 Topic 改为 `ARCHIVED`；
4. 对 `STORED` Topic：
   - 属于被拆联系方式的来源恢复到新联系人的 `REVIEW_PENDING` 候选；
   - 混合来源时只拆出对应来源，剩余来源继续留在仓库；
5. 新联系人不会因拆分自动生成 `READY` Topic；用户必须在待确定区手动选择保留、入库或融合；
6. 拆分候选保留原 Topic 标题和拆分前概要作为参考字段，但这些字段不冒充新 Topic 的当前 AI 概要。

拆分不恢复 `ARCHIVED` Topic。已被其他 Topic 融合吸收的来源必须通过融合血缘审计，不重复恢复。

## 9. 数据与并发合同

- `ai_topics.status` 增加 `REVIEW_PENDING`，并为待确定区建立 owner、状态和更新时间索引。
- 待确定候选需要记录来源操作（`MERGE_SOURCE`、`SPLIT_SOURCE`、`MANUAL_SELECTION`）、原联系人/原 Topic 和创建操作 ID。
- `ai_topic_items` 的来源唯一约束继续保证一条消息、电话记录或企业微信摘要最多属于一个 Topic。
- 手动预览提交携带 Topic 版本和来源快照指纹；应用时使用乐观锁，过期预览不得覆盖新结果。
- Topic 融合使用新 Topic ID和事务内来源迁移，保留操作版本与双向血缘。
- `ai_topic_versions.change_type` 必须同时允许新 Topic 的 `MERGED` 和旧 Topic 的 `MERGED_INTO`，否则融合确认事务会因版本血缘写入违反数据库约束而整体回滚。
- 自动 worker 不读取或修改 `REVIEW_PENDING`。
- 所有选择数量、AI 输入、输出、请求响应审计、租约和重试次数均有上界；不保存企业微信正文、凭据或 API 密钥。

## 10. API 与前端

后端提供以下能力，均使用当前登录用户权限和异步任务合同：

- 查询联系人待确定 Topic；
- 按联系方式和时间范围查询可选来源；
- 创建手动整理预览；
- 调整并确认预览分配；
- 将待确定 Topic 保留或入库；
- 创建 Topic 融合预览并确认生成新 Topic；
- 联系人合并/拆分后返回待确定区刷新事件。

前端要求：

- 普通 Topic、待确定 Topic、仓库 Topic 使用三个独立区域或标签，不混排；
- 待确定项显示来源操作类型、原 Topic、来源数量、时间范围和处理状态；
- 手动整理支持逐条勾选与全选，支持预览、修改目标和整批确认；
- 普通 Topic 继续展示最新概要，收到最终快照事件后刷新；
- 不通过轮询或乐观删除伪造最终状态。

## 11. 验收

### 后端

- 普通新消息经过静默窗口后更新已有 Topic 概要，且不进入人工确认状态；
- 手动选择可按联系方式和时间范围筛选，逐条勾选/全选，预览可匹配多个 Topic；
- 过期版本或已被其他任务归类的来源不能应用；
- Topic 融合创建新 ID，旧 Topic 全部 `ARCHIVED`，来源不重复；
- 联系人合并后来源 `READY` Topic 只出现在 `REVIEW_PENDING`，目标原有 Topic 不被隐藏；
- 联系人拆分后相关 `STORED`/`READY` 来源进入新联系人的待确定区，不自动生成 `READY` Topic；
- 群 Topic 不参与个人 Topic 合并或拆分；
- 自动 worker 永不消费 `REVIEW_PENDING`。

### 前端

- 普通、待确定、仓库三类 Topic 清晰分区；
- 手动整理支持联系方式、时间范围、逐条勾选、全选和 AI 预览；
- 待确定项支持保留、入库、融合；融合确认后显示新 Topic；
- 已被 Topic 占用的来源记录显示所属 Topic 标题；点击标题在当前来源记录下方内联展开 Topic 概要、时间范围和来源数，不跳转联系人页面或仅展示 `STORED` 的 Topic 仓库。
- 联系人合并和拆分后页面只在最终快照事件后刷新，不出现旧 Topic 瞬间消失或重复显示。
