# 邮件发送先持久化设计（待评审）

## 问题与边界

当前 `EmailSendService.sendInternal` 在 SMTP 成功后才写入 `messages` 和附件。
2026-09-28 的真实错误显示 `MessageMapper.insertWithSequence` 显式写入
`counts_as_unread=NULL`，触发 `NOT NULL` 约束；邮件实际已发送，但人工和 AI
入口均报告失败。既有 `email_submissions(PENDING)` 仅记录收件人和主题，不能
代替完整消息持久化。

目标是：提交记录、出站消息正文以及请求中的全部附件均持久化成功，且数据库
事务已提交后，才调用 SMTP。任一预发送步骤失败均不得调用 SMTP。沿用现有
邮件账号归属、附件数量/总大小限制和人工、AI 共用的发送服务；不做自动重发，
不把历史已发但落库失败的邮件重新发送。此次不更改公开 API 或表结构。

## 唯一 Owner 与状态

`EmailSendService` 负责出站顺序和外部 SMTP 边界；数据库预处理由同渠道的
事务服务负责，`EmailSubmissionMapper`、`MessageMapper` 和附件存储分别负责
既有数据合同。Controller、AI 工具和前端只消费发送结果，不另行判断发送状态。

1. 验证账号、地址、SMTP 设置和附件输入；无用户上下文的现存入口也须
   在持久化前确定唯一邮件账号，找不到账号则直接失败。生成并固定 MIME
   `Message-ID`。
2. 在明确的事务边界内创建 `email_submissions(PENDING)`、联系人身份/会话、
   `messages(pending)`。消息应携带相同 provider message ID，设置
   `counts_as_unread=false`、`current_status_at` 和现有出站消息必要字段；
   必须检查每项插入实际影响一行。事务提交失败则抛出结构化持久化错误，
   不启动 SMTP。
3. 若有附件，先将全部附件对象与元数据存为 ready；存储操作完整返回且其
   数据库事务提交后才允许发送。附件预处理失败时，尽力把尚未发送的消息与
   提交记录标记为 `failed` / `FAILED`，清理本次已写入的附件对象；即使
   标记失败也失败，仍禁止发送并记录可核查的消息/提交标识（不记录附件
   内容或带文件名的对象键）。不能通过放弃附件继续发送。
4. 预处理全部成功后才注册提交租约并调用 SMTP。SMTP 抛异常时保持保守的
   `UNKNOWN` / `submission_unknown`，因为无法仅凭异常证明服务器未接收；
   不自动重试。
5. SMTP 明确成功后，将提交记录从 `PENDING` 改为 `SMTP_SENT`，再将消息
   改为 `sent`，最后将提交记录改为 `SENT`。发送后的任一更新失败都返回
   `EMAIL_SEND_OUTCOME_UNKNOWN`，尽力将尚未定稿的状态标为待核查，不得
   再次发送；后台过期租约仍由现有 UNKNOWN 机制兜底。消息已记为 `sent`
   但提交记录收口失败时保留消息事实，不反向标为未发送。

附件存储涉及 MinIO 和数据库，无法通过一个数据库事务保证两者原子提交；
预处理失败的补偿只清理本次上传对象，清理失败需记录对象键供人工核对。
不能因清理成功的假设而放行 SMTP。SMTP 与数据库也不能组成原子事务，
所以保留发送结果不明及人工核查边界。

## 不采用的简化方案

只补 `countsAsUnread=false` 虽能修复本次约束异常，仍会在其他落库失败时
造成“已发出但消息缺失”。只在 SMTP 前写入提交记录也仍缺正文和附件。
改成后台自动重试会在 SMTP 结果未知时造成重复邮件，超出本轮边界。

## 验收

- 测试先证明消息插入失败、提交记录失败、附件对象/元数据失败时 SMTP 零调用；
  成功路径验证完整预处理在 SMTP 前完成且 `pending`、未读标记和 Message-ID
  正确；SMTP 异常和发送后状态更新异常均不触发二次发送。
- 使用真实 PostgreSQL 校验插入约束、事务提交和 `PENDING -> FAILED` 等
  状态迁移；专项测试覆盖人工入口与 AI 共用服务，运行后端编译。
- 不重发既有失败记录；部署后通过一次可控人工邮件与一封带附件邮件核对
  DB、MinIO、SMTP 和界面显示，未经实机验证不得声称提供商侧已通过。
