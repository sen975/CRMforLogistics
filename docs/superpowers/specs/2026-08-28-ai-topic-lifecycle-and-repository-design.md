# AI Topic 生命周期、异步任务与弃用仓库设计

## 1. 目标与边界

本设计替代 2026-08-27 的 AI Topic 时间轴设计。系统为联系人已有和后续的 ChatApp、邮件、电话沟通生成并保存 Topic；Topic 在联系人右侧按时间线展示，并提供折叠、编辑、合并和弃用。员工可在独立的 Topic 仓库跨联系人检索被弃用的 Topic，并恢复它们。

AI 输入渠道严格限于：

- `chatapp`
- `email`
- `phone`（转录文本和人工备注）

`wecom` 不进入输入、指纹、模型 payload、Topic 来源、摘要、匹配或 Topic 仓库。本轮不实现 Topic 拆分、跨联系人合并、向量检索、自动回复或企业微信 AI。

Topic 领域的唯一 owner 是 Spring 后端。前端仅展示后端已提交的投影和提交异步命令，不能计算关联度、推测任务完成结果，或用本地状态伪造最终 Topic。

## 2. 已确认的现状和缺口

当前实现由模型返回 `relevance`，后端仅将其与 `AI_TOPIC_MATCH_THRESHOLD`（默认 `0.65`）比较；没有后端标题相似度、关键词相似度或向量相似度计算。

当前输入服务会将已关联的历史来源再次送入模型，且新建 Topic 可以先入库、后因来源唯一约束冲突而无来源。这会导致重复归类、空 Topic 和重复生成风险。本设计要求从输入、校验和事务提交三层解决，而不依赖 prompt 约束。

当前前端在任务为 `GENERATING` 时每三秒轮询。该行为不符合“异步完成后才更新展示页”的要求，必须删除。

## 3. 领域状态与数据不变量

### 3.1 Topic 状态

`ai_topics.status` 仅有以下含义：

| 状态 | 含义 | 右侧时间轴 | 模型候选 | Topic 仓库 |
| --- | --- | --- | --- | --- |
| `READY` | 正常可用 Topic | 展示 | 可关联后续未归类消息 | 不展示 |
| `ARCHIVED` | 被合并到其他 Topic 的历史 Topic | 不展示 | 不参与 | 不展示 |
| `DISCARDED` | 员工明确弃用但保留的 Topic | 不展示 | 不参与 | 展示，可恢复 |

`ARCHIVED` 只表示合并历史，不能作为弃用的别名。新增 Flyway 迁移扩展已部署迁移中的 CHECK 约束，并在 `ai_topic_versions.change_type` 中增加 `DISCARDED` 和 `RESTORED`；不得修改已经部署的 `V26`。

弃用和归档都不删除 `ai_topics`、`ai_topic_items` 或 `ai_topic_versions`。因此，一个已经进入任意状态 Topic 的来源仍被视为“已归类”。

### 3.2 来源不变量

1. 一个消息或电话记录最多有一个 `ai_topic_items` 关联，数据库部分唯一索引是最终裁决。
2. AI 输入只包含该联系人可访问的、支持渠道的、未出现在任何 `ai_topic_items` 中的来源。
3. 已被 `DISCARDED` Topic 占用的历史来源永久不再进入输入，即使该 Topic 随后恢复也不重新发送。
4. 仅 `READY` Topic 的标题、员工确认摘要或 AI 摘要、时间范围和来源 ID 可作为增量候选上下文；`ARCHIVED`、`DISCARDED` 永不发送给模型。
5. 一个新 Topic 必须在同一事务内至少成功写入一个来源关联后才可持久化。来源冲突时不创建空 Topic；已存在 Topic 只更新实际成功关联的来源对应的时间范围和版本。

这些不变量确保弃用 Topic 内的历史消息不会回流，且新消息不会关联到已弃用 Topic。

## 4. 增量归类与关联度

首次生成时，AI 只接收当时全部未归类的支持渠道来源；后续生成时，只接收自上次成功归类后新出现且尚未归类的来源。输入按 `occurred_at, id` 正序，受记录数和字节数上限约束。

对每一批输入，模型必须将每个来源恰好分配一次：

- 归入一个现有 `READY` Topic：`topicKey` 必须是候选 Topic 的 UUID，并返回 `relevance`。
- 创建一个新 Topic：`topicKey` 必须是非 UUID 的本批临时键，并返回标题、概要和来源集合。

当前版本的关联度计算方式是模型语义判断，而不是后端相似度算法：模型阅读新消息的正文、主题、渠道、时间和候选 Topic 的标题、概要、时间范围后返回 `0..1` 的 `relevance`。后端只接受有效候选 UUID 且 `relevance >= AI_TOPIC_MATCH_THRESHOLD` 的复用结果；低于阈值、无效 UUID 或不属于当前联系人的 UUID 都按新 Topic 处理。

后端在解析和提交前强制检查：来源 ID 必须来自本批、不能重复、不得遗漏；每个来源只能出现一次。任何重复、遗漏、未知来源、非法渠道、无效 JSON 或空标题均拒绝整批输出，不写入 Topic。数据库唯一约束在并发下再次阻断重复来源写入。这样即使模型误判，也不会产生冗余关联或空 Topic；未处理来源会保留，供明确重试后的新任务处理。

本版本不引入 embedding 或向量数据库。若后续模型关联质量不足，再以可观测的误关联率为依据设计向量候选检索，而不是与当前模型分数并行维护两个真相来源。

## 5. 全异步命令与最终快照刷新

### 5.1 任务模型

AI 初始/增量生成继续使用生成任务。员工编辑、合并、弃用和恢复新增统一的 Topic 操作任务，最少包含：任务 ID、操作类型、目标 Topic/联系人、请求 JSON、发起人、状态、乐观锁版本、错误码、创建/完成时间和幂等键。

所有变更端点只校验调用者身份、联系人访问权、请求边界和幂等性，然后创建任务并返回 `202 Accepted` 与任务投影；它们不直接变更 Topic，也不返回推测后的 Topic 内容。worker 在事务中重做权限、状态与版本校验，提交最终数据和审计版本后才标记任务完成。

操作任务类型：

- `EDIT`
- `MERGE`
- `DISCARD`
- `RESTORE`

合并后的概要重整可以作为独立 AI 生成任务，但不阻塞合并任务。重整失败时保留已提交的合并摘要和来源。

### 5.2 完成通知与前端规则

初始/增量生成任务，以及编辑、合并、弃用、恢复操作任务，在完成或最终失败后各发送一次不含联系人 ID、消息内容、Topic 标题或任何敏感数据的 `topic-snapshot-completed` SSE 事件。事件只表示“某个 Topic 快照可能已变化”。

前端规则：

1. 不使用 `refetchInterval`，不轮询 Topic。
2. 不使用 optimistic update，不在提交命令后直接删除、恢复、修改或合并页面中的 Topic。
3. 仅在当前页面收到 `topic-snapshot-completed` 事件时，失效其已挂载的 Topic 时间轴或仓库查询，并从 API 读取已提交的最终快照。
4. 事件断连或页面离开时不猜测任务结果；用户下次进入、手动刷新或重新连接后读取数据库快照。
5. 提交后可显示本地“任务已提交”提示，但不把它作为 Topic 状态，也不改变列表内容。

`topic-snapshot-completed` 使用全局无内容事件，避免现有全局 SSE hub 向无权用户泄露联系人或 Topic 标识。API 查询本身仍执行用户访问校验。

## 6. HTTP API

### 6.1 联系人时间轴

`GET /api/v1/contacts/{contactId}/topics` 返回仅 `READY` Topic 与最后生成任务投影。它可以幂等提交首次或增量生成任务，但返回的是当前已提交快照，不等待模型，也不要求前端轮询。

### 6.2 异步命令

- `POST /api/v1/topics/{topicId}/edit`
- `POST /api/v1/topics/merge`
- `POST /api/v1/topics/{topicId}/discard`
- `POST /api/v1/topics/{topicId}/restore`

每个端点返回统一的 `TopicOperationProjection`：`id`、`kind`、`status`、`errorCode`、`createdAt`、`completedAt`。请求携带 `expectedVersion`；合并携带每个 Topic 的版本。重复提交使用客户端产生的幂等键返回同一未完成或已完成操作，避免双击创建重复任务。

### 6.3 Topic 仓库

`GET /api/v1/topic-repository?search=&page=&size=` 仅分页返回当前员工可访问联系人下的 `DISCARDED` Topic。检索范围为联系人显示名/备注、Topic 标题和当前摘要；按弃用时间倒序。服务端在查询层复用联系人可访问条件，前端筛选不构成权限边界。

仓库投影包含联系人名称、Topic 标题、概要、弃用时间、来源数量、来源条目和版本。来源正文仍通过原有消息/电话详情授权链读取，仓库不额外复制正文。

## 7. 界面

### 7.1 联系人右侧时间轴

右侧时间轴作为联系人详情顶部区域：

- 整个 `Topic 时间轴` 可折叠；折叠时只显示标题、`READY` 数量和展开控件。
- 时间轴展开时，每个 Topic 默认折叠，仅显示标题与单行概要。
- 单 Topic 展开时才显示完整概要、时间范围、来源数量、来源消息列表和点击定位按钮，以及编辑、合并、弃用操作。
- 弃用需二次确认；提交后保持当前已提交列表，直到后台完成事件触发一次最终快照刷新。
- 失败只提示任务失败和可重试原因，保留上一次已提交内容。

### 7.2 跨联系人 Topic 仓库

新增 `/topic-repository` 路由和导航入口。页面提供搜索、分页、弃用时间、联系人名称、标题、概要和来源数量；单项可折叠查看来源，并提供恢复操作。恢复需二次确认，提交后不乐观移除卡片；收到完成事件并取得最终列表后才消失。恢复后的 Topic 回到 `READY`，未来未归类的新消息可再次关联它。

## 8. 并发、失败与审计

- 生成和操作 worker 均有租约、最大尝试次数、退避和恢复机制；禁止无限重试和无限线程。
- 同一联系人/输入指纹最多一个未完成生成任务；同一对象和幂等键最多一个等价操作任务。
- 任务实际执行时才以乐观锁验证版本。过期命令失败为结构化冲突，不覆盖较新的员工操作。
- `DISCARDED`/`RESTORED`、编辑和合并都写入 `ai_topic_versions`，保留操作者、版本和必要状态变更审计。
- AI/provider 错误不影响收发消息、联系人信息或已保存的 Topic 快照。
- 不在日志、SSE、API 错误或前端 bundle 输出 API key、来源正文或模型完整响应。

## 9. 验收

后端：

- 输入查询只返回未归类 ChatApp、邮件和电话；WeCom、任何状态 Topic 的已关联来源均被排除。
- 仅 `READY` Topic 进入模型候选；`DISCARDED` 永不进入候选或右侧查询。
- 模型重复、遗漏、未知来源或低关联度输出分别被正确拒绝或创建新 Topic；不会产生空 Topic。
- 弃用保留 Topic、版本和来源；恢复后可作为候选，但历史来源不回流。
- 仓库跨联系人搜索和分页严格受当前用户联系人权限过滤。
- 所有命令返回 `202`，worker 完成前查询保持旧快照；每个终态生成或操作任务只发布一次无敏感字段 SSE 事件。

前端：

- 右侧整体折叠、单 Topic 折叠和来源展开/定位均可用；来源不会因折叠功能被删除。
- 时间轴只展示 `READY`；弃用后仅在收到完成事件且重新查询后消失。
- 仓库支持跨联系人检索、展开来源、恢复；恢复完成后才从仓库列表消失。
- 不存在 Topic 查询轮询或乐观列表变更；SSE 只触发一次失效查询。
- 桌面右侧 Sider 与移动 Drawer 均不溢出、遮挡或打断消息时间线。
