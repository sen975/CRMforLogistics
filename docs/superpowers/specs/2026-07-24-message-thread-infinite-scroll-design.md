# 消息线程向上滚动分页加载设计

**日期：** 2026-07-24  
**状态：** 用户已确认设计，待实现计划  
**适用范围：** `demo/message-center-demo` 当前旧内嵌消息中心页面，以及后续 React/TanStack Query 前端迁移时的同一消息分页语义。

## 1. 背景与问题

当前运行面仍是 `App.java` 内嵌 HTML/CSS/JavaScript 和旧 `/api/*` 路由。消息线程通过 `GET /api/threads?contactPointId=...` 一次性返回某个联系人/账号下的完整消息列表，前端 `loadThread` 会完整渲染整条时间线。

当单个联系人或账号的消息很多时，这会导致：

- 初次打开联系人时请求体和 DOM 节点过大。
- 一个窗口只能展示有限消息，但页面仍加载了不可见的历史消息。
- 静默刷新或同步后容易重复重绘完整线程。
- 后续 React 迁移时如果不先定义分页语义，会把同一问题带入新前端。

## 2. 目标

- 默认每个联系人/账号只加载最近 10 条消息。
- 用户在消息窗口向上滚到顶部时，再加载更早的 10 条消息。
- 新加载的历史消息插入当前列表顶部，并保持用户当前看到的位置不跳动。
- 后端仍是消息真相；前端只持有当前联系人已加载页，不伪造消息总量或历史完整性。
- 旧 `/api/threads` 的分页语义应贴近 OpenAPI v1 已定义的 `cursor + limit + MessagePage`，为后续 `/api/v1/conversations/{conversationId}/messages` 和 React/TanStack Query 迁移铺平道路。

## 3. 非目标

- 不在本轮重写成 React。
- 不引入虚拟列表库；当前页面先用有界分页减少 DOM 规模。
- 不改变联系人合并、拆分、未读、发送、附件预览和媒体代理语义。
- 不把旧 JSONL 文件路径恢复成新真源；旧运行面只作为当前 demo 的过渡实现。
- 不使用深层 `offset` 分页。

## 4. 推荐方案

采用后端 cursor 分页 + 前端向上滚动触发加载。

### 4.1 接口语义

旧接口扩展为：

```text
GET /api/threads?contactPointId=<id>&limit=10&cursor=<cursor>
```

返回页对象：

```json
{
  "items": [],
  "nextCursor": null
}
```

- `items` 按时间正序返回，便于前端直接渲染聊天时间线。
- 首次无 `cursor` 时返回最近 `limit` 条消息。
- `nextCursor` 指向本页最早消息之前的历史位置；为 `null` 表示没有更早消息。
- `limit` 默认 10，服务端设置上限，避免异常请求一次拉大量消息。

### 4.2 Cursor 规则

cursor 应由消息排序键构成，优先使用：

```text
timestamp + messageId
```

排序规则保持当前消息线程语义：

```text
timestamp ASC, stable id ASC
```

查询更早消息时使用相反方向查出比 cursor 更早的消息，再反转为正序返回。这样可以稳定处理同一时间戳下多条消息。

### 4.3 前端状态

前端为每个 `contactPointId` 保存一个线程页状态：

- `items`：已加载消息列表。
- `nextCursor`：下一次向上加载的 cursor。
- `isLoadingOlder`：防止连续滚动重复请求。
- `hasLoadedInitial`：避免重复初始化。
- `renderKey`：用于判断静默刷新是否需要更新。

切换联系人时只初始化该联系人最近 10 条。用户返回同一联系人时，可以复用已加载页；如果联系人 `lastTime` 或 `messageCount` 变化，再按当前选中联系人做轻量刷新。

### 4.4 交互

- 打开联系人后，消息区滚动到底部，展示最近消息。
- 用户滚动到顶部附近，例如 `scrollTop <= 24px`，如果 `nextCursor` 不为空且没有正在加载，则请求更早一页。
- 历史页返回后插入列表顶部。
- 插入前记录 `oldScrollHeight`，插入后设置：

```text
scrollTop = newScrollHeight - oldScrollHeight + oldScrollTop
```

这样用户视线停留在原来的消息附近，不会突然跳到顶部或底部。

### 4.5 新消息与静默刷新

静默刷新或同步收到新消息时：

- 当前选中联系人只请求最新页或比较联系人摘要。
- 如果用户正在底部附近，则合并新增消息并滚到底部。
- 如果用户正在上翻历史，则不强制滚动，保留当前位置，并沿用现有“有新消息”提示。
- 不因为新消息到达清空已加载的历史页。

## 5. 备选方案与取舍

### 方案 A：只在前端截取最近 10 条

优点是改动最少。缺点是后端仍一次性返回所有消息，无法解决请求体过大和静默刷新重绘问题，也会污染后续 React 迁移。放弃。

### 方案 B：后端 cursor 分页，前端向上滚动加载

这是推荐方案。它同时解决请求体、DOM 数量、滚动体验和未来接口合同一致性，改动范围仍控制在消息查询 facade、旧 HTTP 路由和当前线程渲染逻辑内。

### 方案 C：直接上虚拟列表

虚拟列表适合单线程上万条消息的成熟产品形态，但当前 demo 仍在旧内嵌前端阶段。它会引入更多滚动测量和边界复杂度，不适合作为当前最小闭环。暂不采用。

## 6. Owner 与边界

- 消息排序、cursor、limit、是否还有历史消息由 `UnifiedMessageStore` / 后续 `messaging` 模块负责。
- HTTP 路由只做参数解析和页对象返回，不拥有消息分页真相。
- 前端只负责触发分页、合并页数据和保持滚动位置。
- OpenAPI v1 的 `MessagePage` 是后续前后端分离后的合同参照。

## 7. 验收标准

- 打开一个消息数超过 10 的联系人时，首屏只请求并渲染最近 10 条。
- 向上滚到消息区顶部后，自动加载更早 10 条。
- 多次向上滚动可以继续加载，直到 `nextCursor` 为 `null`。
- 历史消息插入顶部后，当前阅读位置不跳动。
- 切换联系人后，新联系人仍只加载最近 10 条。
- 静默刷新或新消息到达时，不清空当前已加载历史页；用户在底部附近时新消息可自动滚到底部。
- 附件预览、点击消息详情、发送消息、联系人合并/拆分仍按现有行为工作。

## 8. 测试计划

- 后端单元测试：构造同一联系人 25 条消息，验证无 cursor 返回最近 10 条且 `nextCursor` 存在；使用 cursor 再取 10 条更早消息；最后一页返回 `nextCursor = null`。
- 后端排序测试：同一时间戳多条消息按稳定 id 排序，cursor 不重复、不漏消息。
- 前端交互测试或手工浏览器验收：打开联系人、顶部滚动加载、加载后保持滚动位置、切换联系人后仍默认 10 条。
- 回归命令：`cd demo/message-center-demo && mvn -q -Dtest=UnifiedMessageStoreTest test`。
- 若启动页面验收：使用非用户端口，例如 `WEB_PORT=8100`，验收结束后关闭服务并确认端口无监听。

## 9. 风险与停止条件

- 如果当前未提交改动已经改变 `UnifiedMessageStore.thread` 或 `App.java` 线程渲染语义，实现前必须先复核 diff，不能覆盖用户改动。
- 如果分页设计需要删除旧接口、改公开 API 或改变联系人合并合同，必须先暂停并确认。
- 如果发现旧文件模式无法可靠生成稳定 cursor，应先收敛为后端明确的页模型，不允许用前端数组下标假装全局分页真相。
