# 用户私有渠道通讯录设计

## 目标

为 WhatsApp、邮件和电话建立按登录用户严格隔离的渠道通讯录，并让联系人从首次收信、首次发信或人工录入开始形成完整的消息时间轴。

本设计支持：

- 用户只看到自己 WhatsApp 账号、邮件账号、电话记录和人工录入产生的联系人。
- 同一个客户分别联系两个系统用户时，在两个用户名下形成相互独立的联系人、备注、标签、消息、附件和 Topic。
- WhatsApp、邮件和电话拥有独立通讯录入口，并能从通讯录准确进入对应渠道时间轴。
- 用户可以人工添加尚无消息的邮箱或号码，并从空时间轴发起第一条 WhatsApp 或邮件消息。
- 用户自行配置自己的唯一 WhatsApp 账号和唯一邮件账号。

## 产品边界

- 不引入联系人、会话或消息分配功能。渠道账号的 owner 或电话记录的创建用户就是业务数据归属依据。
- 不自动判断不同邮箱、电话号码或渠道身份是否属于同一个自然人。跨渠道关联继续使用现有联系人手动合并能力。
- 不允许管理员借角色读取其他用户的联系人、消息、附件、Topic 或渠道密钥。管理员只负责用户和角色管理。
- 每个用户最多拥有一个有效 WhatsApp 账号和一个有效邮件账号，业务页面不提供账号选择器。
- 电话不配置渠道账号，系统不提供拨号能力；电话通讯录只用于查找联系人和查看电话时间轴。
- 企业微信继续使用现有通讯录、授权、解绑、会话和数据模型。本设计不新增或迁移企业微信能力，也不得破坏现有入口。
- 已产生业务记录的联系人不提供删除或隐藏能力。只有人工添加且从未产生任何业务记录的联系人可以删除。

## 术语与规范值

产品界面统一显示“WhatsApp”。现有后端、数据库和 API 中代表 WhatsApp 的规范渠道值为 `chatapp`；本设计沿用该持久层值，不新增并行的 `whatsapp` 业务路径。邮件和电话的规范值分别为 `email`、`phone`。

`owner` 表示一条业务数据所属的系统用户。`created_by` 只表示创建行为的操作者，不能继续承担权限真相。`MANUAL` 表示用户人工添加的联系人来源；数据库落值应遵循当前 schema 已有的小写枚举规则 `manual`，API 投影可使用大写展示枚举。

## 架构与唯一所有者

采用显式 owner 模型。联系人应用服务是联系人归属、身份建档、备注、标签、合并、拆分和删除条件的唯一业务 owner；渠道接入服务只负责把标准化后的渠道事件交给该服务。Controller、同步 worker 和前端不得各自推断联系人归属。

服务端认证上下文是用户身份的唯一来源。所有面向用户的写接口忽略并拒绝请求体中的 owner 字段；所有查询、搜索、详情、合并、拆分、标签、消息、附件、Topic 和发送操作必须在服务端执行 owner 校验。越权读取统一表现为资源不存在，避免泄露资源是否存在。

## 数据模型

### 渠道账号

为 `channel_accounts` 增加可空外键 `owner_user_id`。可空仅用于承载无法可靠归属的历史数据；上线后的 WhatsApp 和邮件账号必须写入当前登录用户。

数据库增加部分唯一索引，保证每个用户最多一个处于有效、过期或失败待修复状态的 `chatapp` 账号，以及一个同类状态的 `email` 账号。已明确解绑或停用的历史账号不占用唯一名额。新建、重新授权、停用和解绑均由服务层再次校验该约束，并处理并发冲突。

渠道凭证继续保存于加密配置。读取接口只返回账号标识、授权状态、同步状态、最近同步时间和脱敏配置，不返回可恢复的密钥。密钥只能替换，不能回显。

企业微信现有绑定表和授权合同不迁入 `channel_accounts`，不因本设计建立第二套绑定真相。

### 联系人与渠道身份

为 `contacts` 增加可空外键 `owner_user_id`，并把它作为联系人访问权真相。新联系人同时写入 `owner_user_id` 和 `created_by`；前者表示归属，后者保留审计含义。

`contact_identities` 通过所属联系人继承 owner，不复制第二个 owner 字段。身份作用域规则为：

- WhatsApp：`identity_scope = channel_account_id`。
- 邮件：`identity_scope = channel_account_id`，替换当前固定的全局 `email` scope。
- 电话：`identity_scope = owner_user_id`，因为电话没有渠道账号。
- 企业微信：保持现有规则，不在本设计中迁移。

身份唯一性继续由“渠道类型 + 身份作用域 + 标准化值”定义。因此相同邮箱或号码可以在不同用户下独立存在，同一用户的同一渠道内则复用一条身份。

联系人保存用户自己的备注；渠道昵称、邮件显示名和真实地址保存在渠道身份或对应的结构化渠道资料中。更新备注不得覆盖上游渠道昵称或真实邮箱、号码。

### 标签

为 `contact_tags` 增加 `owner_user_id`，标签名称只要求在同一 owner 内不区分大小写唯一。服务端只允许标签绑定同 owner 的联系人，并在标签列表、创建、修改、停用和绑定接口中执行 owner 过滤。

### 电话记录

为 `call_records` 增加可空的 `owner_user_id` 和 `contact_id`。新记录必须写入两者；现有字符串 `created_by` 只保留为历史审计字段，不再作为查询权限依据。

电话身份按当前用户和标准化号码查找。没有对应联系人时创建用户私有联系人，再写入通话记录。电话附件、录音、转写、修订和 Topic 均从通话记录与联系人派生访问权。

### 会话、消息和 Topic

会话与消息继续通过 `channel_account_id` 和 `contact_identity_id` 关联归属，Topic 继续通过联系人或现有 owner 合同归属，不新增容易冲突的重复 owner 字段。所有 repository 查询必须从当前用户 owner 约束出发，不能先查全库再在 Java 或前端过滤。

## 渠道账号自助管理

“个人设置 → 渠道配置”新增 WhatsApp 和邮件两个分栏。企业微信授权与解绑保持当前已完成的实现和位置，电话不出现渠道配置。

普通用户可以创建、查看、修改、重新授权、停用或解绑自己的 WhatsApp 和邮件账号。账号 owner 始终由后端取当前认证用户。管理员没有查看或修改其他用户渠道账号的旁路。

已产生消息的渠道账号只能解绑或停用，不能物理删除。解绑停止后续同步和发送，但保留历史联系人、会话、消息、附件、Topic 和审计记录。重新绑定相同上游账号标识时恢复原账号；改绑另一个 WhatsApp 号码或邮箱账号时创建新账号和新身份作用域，旧账号只保留历史数据。不得仅凭显示名称复用账号，也不得把旧账号的联系人或消息改挂到新账号。

当前邮件收发读取全局配置并取第一条邮件账号的实现必须退出业务主线。邮件同步改为按每个有效邮件账号独立连接和拉取；邮件发送始终使用当前登录用户唯一的有效邮件账号。WhatsApp 同样只使用当前用户唯一的有效账号。

## 通讯录 API 合同

### 列表与搜索

提供 WhatsApp、邮件、电话三个用户私有通讯录查询。接口必须分页，并接受有上界的搜索词和页大小。默认排序为：

1. 有消息或通话的条目按最近联系时间倒序。
2. 从未产生业务记录的人工条目按创建时间倒序参与排序。
3. 时间相同时使用稳定 ID 排序，避免翻页重复或遗漏。

搜索范围为当前用户条目中的备注、渠道昵称、邮件显示名、真实邮箱或号码。查询不得返回其他用户或 `owner_user_id IS NULL` 的数据。

通讯录按渠道身份投影，一条邮箱或一个号码对应一行。投影至少包含联系人 ID、身份 ID、渠道类型、显示名称、真实地址、来源、最近联系时间、是否存在业务记录、可删除状态、标签和同一联系人拥有的其他渠道类型。

### 人工新增

- WhatsApp：提交号码，服务端自动使用当前用户唯一 WhatsApp 账号。
- 邮件：提交邮箱，服务端自动使用当前用户唯一邮件账号。
- 电话：提交电话号码，不使用渠道账号。

号码和邮箱只做格式、长度和标准化校验，不验证真实可达性。新增操作只创建联系人及渠道身份，来源记为 `manual`；不伪造会话、消息、通话或最近联系时间。

同一作用域内重复添加相同标准化地址时返回结构化冲突，并返回或标识现有条目，不静默创建重复联系人。当前用户尚未配置相应 WhatsApp 或邮件账号时可以先保存人工联系人；此时身份使用当前用户的待配置私有作用域，账号成功配置后必须在事务中迁移到账号作用域并解决冲突。发送仍被阻止，直到账号有效。

### 自动建档

入站 WhatsApp 根据接收渠道账号确定 owner；入站邮件根据正在同步的邮件账号确定 owner。渠道接入服务以“owner + 渠道账号 + 标准化地址”调用联系人应用服务：身份不存在时创建私有联系人和身份，存在时更新渠道昵称和最近联系投影，但不覆盖用户备注。

出站发送执行相同的查找或建档流程。首次发送成功后才创建真实会话和消息；发送失败不得留下伪造的成功消息。若发送请求需要预留幂等记录，应使用明确的发送状态并允许重试，不能把它计为已联系成功。

电话记录创建或导入时，根据当前用户与标准化号码查找或创建电话联系人，并直接绑定 `owner_user_id/contact_id`。

### 修改、合并、拆分与删除

备注和标签操作只作用于当前用户的联系人。联系人合并只允许同一 owner 内执行，保留所有渠道身份，并触发现有 Topic 联系人合并协调流程；跨 owner 合并按资源不存在处理。

拆分产生的联系人仍归当前用户，并触发现有 Topic 拆分恢复流程。不同渠道身份不会自动合并，也不会根据相同昵称推断关系。

仅当联系人来源为人工添加，且不存在消息、会话业务内容、通话、附件、Topic 或其他领域引用时允许物理删除。存在任何业务记录时，前端不显示删除操作，后端即使被直接调用也返回 `CONTACT_HAS_ACTIVITY`。本设计不增加隐藏或恢复状态。

## 页面与导航

顶部导航调整为：

- `WhatsApp` 下拉：通讯录、模板、群发。
- `邮件` 下拉：通讯录。
- `电话` 下拉：通讯录、电话仓库。
- 企业微信导航保持现状。

三个通讯录为独立页面，复用现有设计 token、分页、搜索、加载态和错误反馈。页面首屏提供搜索与新增命令，不制作营销式介绍区域。

通讯录 API 使用同一服务端 owner 合同：

- `GET /api/channel-address-books/{channelType}`：按当前登录用户、渠道、搜索词和有界分页返回通讯录。
- `POST /api/channel-address-books/{channelType}`：为当前登录用户创建人工联系人，请求体不能指定 owner。
- `DELETE /api/channel-address-books/{channelType}/{contactId}`：仅删除当前用户无业务记录的人工联系人。

`channelType` 只接受 `chatapp`、`email`、`phone`，并兼容输入 `whatsapp` 后立即规范为 `chatapp`。WhatsApp 和邮件身份作用域使用当前用户有效渠道账号 ID；尚未配置账号时使用当前用户 UUID 作为待绑定作用域。电话身份始终使用当前用户 UUID 作为作用域。入站同步必须调用共享的 `resolveOrCreateInbound(ownerId, channelType, accountId, address, displayName)`，并通过数据库唯一约束的 `ON CONFLICT DO NOTHING` 收敛并发建档。

显示名称遵循以下优先级：

1. 有用户备注时显示 `备注（渠道昵称、邮件显示名或真实地址）`。
2. 无备注时显示渠道昵称或邮件显示名。
3. 均缺失时显示真实邮箱或号码。

当前列表渠道不重复显示为徽标，只显示该联系人经人工合并后存在的其他渠道。例如邮件通讯录可显示 `张经理（Pazuma） 【WhatsApp】 【电话】`。人工添加且尚无业务记录的条目显示简洁的“手动添加”标识。

点击 WhatsApp 或邮件条目进入对应渠道时间轴。已有消息时展示该渠道现有会话；没有消息时展示空时间轴并打开已预填号码或邮箱的发送区。路由必须携带明确的渠道和身份 ID，不能仅靠联系人 ID 猜测用户点击的是哪个地址。

点击电话条目进入该身份对应的电话时间轴，只展示已有通话、录音、转写和 Topic，不显示拨号或发送控件。

## 隔离与安全

所有业务数据隔离都在服务端 repository/service 边界执行，前端隐藏菜单、路由守卫和客户端过滤不构成授权。需要审计的入口至少包括：

- 联系人列表、搜索、详情、备注、标签、合并、拆分和删除。
- 会话列表、时间轴、消息详情、附件下载和已读状态。
- WhatsApp 模板、发送、同步、群发和 webhook 投影。
- 邮件发送、同步和附件。
- 电话仓库、详情、录音、转写、修订和 Topic。
- Topic 查询、生成、预览、应用、仓库和来源记录。
- 渠道账号读取、更新、授权、解绑和同步状态。

管理员角色不得作为以上查询的 `OR admin` 条件。后台同步没有终端用户会话时，必须从被处理的渠道账号读取 owner 并显式下传；无法取得 owner 的账号不启动同步。

## 历史迁移

迁移采用一次性正式 schema 和数据迁移，不长期保留新旧权限双路径。

1. 新增可空 owner 字段、索引和外键，部署代码前执行。
2. 根据渠道账号、会话、消息发送者和有效 `created_by` 建立可审计的 owner 候选。
3. 唯一确定 owner 的 WhatsApp 数据按渠道账号回填；被多个 owner 共用的旧联系人按 owner 复制联系人、备注和身份，并重连各自会话与消息。
4. 旧邮件全局 `identity_scope='email'` 按实际 `channel_account_id` 和账号 owner 拆分。若同一 identity 被多个邮件账号使用，为每个 owner 创建独立联系人与 identity，并重新关联对应会话。不得根据联系人名称猜 owner。
5. 电话记录仅在 `created_by` 可解析为有效用户且归属唯一时回填；再在该 owner 内按标准化号码关联或创建联系人。
6. 全局标签按实际联系人 owner 复制为用户私有标签，并重建同 owner 的绑定。
7. 无法可靠归属的账号、联系人、身份、消息和电话记录保留空 owner，不进入普通用户或管理员业务接口，也不允许后续同步。
8. 完成数据检查后启用新数据非空写入规则和每用户唯一账号索引；历史空 owner 通过约束豁免保留，不能被新请求制造。

迁移必须输出每类记录的总数、成功归属数、拆分数、冲突数和未归属数，并提供部署前后对账 SQL。不得提供普通用户或管理员前端“认领历史数据”功能；后续若需处理未归属数据，只能通过单独审核的一次性运维映射完成。

## 异常与并发

- 当前用户未配置或已解绑对应账号时，历史通讯录和消息仍可读，发送和同步返回明确的 `CHANNEL_ACCOUNT_REQUIRED` 或 `CHANNEL_ACCOUNT_INACTIVE`。
- 单个渠道账号认证或同步失败只更新该账号状态，不阻塞其他账号、用户或渠道。
- 单条消息解析失败写入结构化失败记录并继续处理后续消息；重试有次数、退避和终态上限，不允许永久占据队列头部。
- 同一地址的并发自动建档依赖数据库唯一约束收敛，服务端捕获冲突后读取已创建身份，不能生成两个联系人。
- 账号唯一约束冲突返回 `CHANNEL_ACCOUNT_ALREADY_EXISTS`。
- 跨 owner 或未归属资源统一返回 `RESOURCE_NOT_FOUND`。
- 删除存在业务记录的联系人返回 `CONTACT_HAS_ACTIVITY`。
- 同步、发送、分页、搜索词、附件、重试和批处理均沿用或补齐明确上界与超时。

## 验收标准

1. 用户 A、B 分别通过各自账号联系同一邮箱或号码时，两人只能看到自己的联系人、消息、附件、备注、标签和 Topic；管理员也不能通过业务 API 读取任一用户数据。
2. 每个用户只能建立一个有效 WhatsApp 账号和一个有效邮件账号；业务发送和通讯录不显示账号选择器。
3. WhatsApp 与邮件入站按实际接收账号自动建档，出站按当前用户账号自动建档；邮件同步不再取全库第一条账号。
4. 三个通讯录支持有界分页、搜索和稳定的最近联系排序；无消息人工联系人按创建时间排序。
5. 展示名称、跨渠道徽标和“手动添加”状态符合合同，不暴露内部 ID 或其他用户资料。
6. WhatsApp、邮件空时间轴可预填并发起首次发送，首次成功后生成真实会话；失败不会伪造成功消息。电话时间轴不出现拨号或发送控件。
7. 备注、标签、合并和拆分只能在同一 owner 内操作，并与现有 Topic 协调流程保持一致。
8. 仅人工添加且无任何业务记录的联系人可删除；有记录时前后端均阻止删除，不产生隐藏状态。
9. 历史迁移能对账账号、联系人、身份、会话、消息、电话和标签；无法归属的数据在所有业务 API 中不可见。
10. 一个账号或一条消息失败不会阻塞其他同步任务，终态失败可诊断且不会无限重试。
11. 后端需要覆盖 schema、owner 查询、并发建档、同步隔离、发送、合并拆分、删除和越权集成测试；前端需要覆盖导航、搜索、排序、展示、空时间轴、预填发送区和电话只读状态。
12. 发布前通过后端全量测试、前端全量测试、前端生产构建和后端 Jar 打包，并在桌面与移动视口实测三个通讯录的加载态、空态、错误态和核心交互。

## 实施顺序

1. 增加 schema、owner 索引与迁移对账测试。
2. 建立服务端 owner 上下文和联系人应用服务合同。
3. 改造渠道账号自助管理、WhatsApp 投影、邮件逐账号同步与发送、电话记录归属。
4. 收紧联系人、消息、附件、Topic 和电话仓库的全部查询边界。
5. 增加通讯录 API、人工建档和删除门禁。
6. 接入顶部导航、三个通讯录页面、空时间轴与发送预填。
7. 执行历史迁移演练、权限回归、前端实测和制品构建。

每一步必须先通过所属层的专项测试。历史迁移对账或跨用户隔离测试失败时停止上线，不允许以前端过滤作为临时替代。
