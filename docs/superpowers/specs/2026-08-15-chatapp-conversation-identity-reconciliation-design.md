# ChatApp 会话身份对账修复设计

**状态：** 已确认，待实施

**日期：** 2026-08-15

## 1. 问题与证据

ChatApp 账号 `8613266259485` 下存在两个本地联系人：

- 正常联系人身份是 `8613428277520`，对应会话包含正常入站和外发消息。
- 另一个联系人名称是 `8613428277520`，但其 ChatApp 身份值错误地保存为
  `8613266259485`，对应会话混入了不同真实收件人的外发历史。

数据库与本地 CAMS 历史共同证明，错误会话不是单纯的页面标题问题：其中至少 26 条消息的
`UserNumber` 是 `8613428277520`，8 条消息的 `UserNumber` 是本方号码
`8613266259485`。其余旧消息必须继续使用 CAMS 的 provider 记录核对，禁止根据联系人名称、
消息正文或时间猜测收件人。

当前 `ThreadPage` 使用 `contacts.display_name` 作为标题，`ThreadService` 使用会话关联的
`contact_identities` 生成消息收发方。因此只改前端标题会继续展示错误收件人，也会让后续发送
选择错误身份。

## 2. 目标

1. 使用 CAMS `ListChatappMessage` 返回的 `UserNumber` 修复已有消息与联系人的归属。
2. 发给 `8613428277520` 的消息进入该号码现有会话。
3. 发给本方 `8613266259485` 的自测消息保留在独立的本方号码会话，并把联系人名称修正为
   `8613266259485`。
4. 当前和后续消息同步发现已有消息关联了错误身份时，可以事务性自愈。
5. 无法取得 provider 收件人证据的消息保持原状并进入结构化未决清单，不做推测性迁移。

## 3. 边界

- CAMS `UserNumber` 是 ChatApp 消息对端号码的唯一 provider 真源。
- `BusinessNumber` 是本方发送账号，不得作为普通对端联系人，除非 `UserNumber` 本身与其相同，
  即明确的自发自收消息。
- 本轮不删除消息、附件、状态事件或审计记录。
- 本轮不把旧 JSONL 文件引入 Spring 运行时，也不依赖已废弃 demo。
- 本轮不合并两个号码的联系人；本方号码和对端号码继续是两个独立身份。
- 历史修复只处理 CAMS 能以 provider message ID 明确确认的消息。

## 4. 唯一 owner

新增 `ChatAppMessagePeerReconciliationService` 作为 ChatApp 消息与会话身份对账的唯一 owner。
它接收结构化命令：账号 ID、provider message ID、CAMS `UserNumber`，负责验证、查找或创建目标
身份及会话，并在必要时移动消息。

`ChatAppPollingProjector` 只负责把 CAMS 行映射为该命令并调用 owner。Controller、scheduler、
前端和 Mapper 不得自行判断消息归属。

## 5. 在线自愈流程

每条 `ListChatappMessage` 记录按以下顺序处理：

1. 校验 `MessageId/UniqueMessageId` 和 `UserNumber`，并按当前 ChatApp 账号范围归一化号码。
2. 按 `channel_account_id + provider_message_id` 查找已有消息。
3. 如果消息不存在，沿用当前投影流程，使用 `UserNumber` 创建或复用目标身份与会话。
4. 如果消息已存在，读取其会话和身份；身份的账号范围与号码都一致时不写库。
5. 如果号码不一致，调用对账 owner 事务性移动消息。
6. 完成身份对账后再处理 provider 状态，确保状态更新不会继续固化错误会话。

同一账号中允许 `UserNumber == BusinessNumber`。这类记录必须进入本方号码身份，不得为了避免
“自己是联系人”而改写成其他号码。

## 6. 事务性移动

消息移动必须锁定源会话和目标会话，锁顺序固定按 UUID 排序，避免并发死锁。事务内执行：

1. 再次校验消息仍位于预期源会话，防止重复对账。
2. 为目标会话递增 `next_ingest_sequence`，将该序号赋给移动消息。
3. 更新消息的 `conversation_id` 和 `ingest_sequence`；消息 ID、provider ID、时间、正文、附件及
   状态事件不变。
4. 从源会话剩余消息中按 `occurred_at desc, id desc` 重算 `last_message_id/last_message_at`；为空时
   两者置空。
5. 从目标会话全部消息中按同一规则重算 `last_message_id/last_message_at`。
6. 两个会话更新 `updated_at/version`。源会话的 `next_ingest_sequence` 不回退，以保持序号单调。

页面分页以 `occurred_at + id` 为真源，因此移动消息追加新的 ingest sequence 不改变历史展示顺序。

## 7. 现有数据修复

提供受管理员控制、账号范围明确且日期范围有上界的一次性对账入口。入口调用现有 CAMS gateway
分页读取指定时间段，逐条向对账 owner 提交 `provider message ID + UserNumber`。默认不暴露给
普通用户，单次最多读取 50 页、每页 100 条。

执行前记录受影响联系人、会话和消息数量；执行后返回：扫描数、号码一致数、成功移动数、
创建身份数、无法确认数和失败明细。单条失败不回滚已完成的其他 provider 事实，但每条移动自身
必须原子完成。

针对当前数据，执行结果应满足：

- 确认发给 `8613428277520` 的消息全部归入其现有会话。
- 确认发给 `8613266259485` 的自测消息留在本方号码会话。
- 本方号码联系人名称修正为 `8613266259485`，对端联系人名称保持 `8613428277520`。
- 未被 CAMS 返回的 provider message ID 保持原归属并列入未决清单。

## 8. 错误与资源治理

- 非法号码返回 `CHATAPP_PEER_NUMBER_INVALID`，不创建事件或联系人。
- provider message ID 不存在返回未决结果，不创建替代消息。
- 跨账号身份或会话返回 `CHATAPP_PEER_SCOPE_MISMATCH`。
- 移动时发现消息已由其他任务修复，按幂等成功处理。
- CAMS 分页、时间范围和单次消息数必须有上界；一次账号对账同一时刻只允许一个执行实例。
- 日志只记录账号 ID、provider message ID、结构化错误码和计数，不输出凭据或完整消息正文。

## 9. 测试与验收

后端测试覆盖：

- 本方 `8613266259485` 向 `8613428277520` 外发时，目标身份必须是 `8613428277520`。
- 本方号码自发自收时，目标身份必须是 `8613266259485`。
- 已有消息身份错误时被移动到正确会话，附件和状态事件仍关联原消息。
- 源、目标会话摘要正确重算，源序号不回退。
- 重复处理同一 provider 行不重复移动、不重复创建联系人。
- 无 provider 证据的历史消息不移动，并出现在未决结果中。
- 不同 ChatApp 账号下相同号码仍保持独立身份。

数据库实测验收：修复前后分别查询两个身份、两个会话、消息数、消息方向、provider message ID、
最后消息和联系人名称；总消息数必须守恒，附件数和状态事件数不得减少。
