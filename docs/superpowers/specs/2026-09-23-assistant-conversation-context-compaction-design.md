# 助手对话上下文滚动摘要设计

> 日期：2026-09-23 ｜ 状态：用户已确认
> 范围：消息中心 AI 助手的多轮对话上下文；不涉及联系人记忆层或 Codex 自身上下文管理。

## 1. 目标

长对话继续保留完整原文，但模型不再因为只取最近几条消息而丢失较早的目标、约束和决定。每轮上下文由旧对话摘要、最近消息原文和当前请求组成，并受明确预算约束。

用户已确认接受：摘要可能无法逐字保留原对话细节，但完整原文仍可在聊天记录中查看。

## 2. 当前基线

- `assistant_conversation_messages` 是服务端追加写对话记录，面向完整回放。
- 助手上下文使用服务端保存的最近消息；默认 `max-history-turns=8`、`max-history-chars=8000`。
- `AssistantRequestGuard` 从较新消息向较旧消息保留，超出限制时裁掉更早记录；响应会带历史裁剪信息。
- 当前没有持久化旧对话摘要，模型看不到被裁掉的早期语境。
- `AssistantModelClient` 当前只读取模型文本、模型名和耗时，不暴露供应商 usage token 统计。

## 3. 方案选择

### 推荐：按会话持久化滚动摘要

在历史超过上下文窗口时，把已移出原文窗口的旧消息压成有界摘要并持久化；每轮复用已有摘要，只把尚未覆盖的旧消息追加到下一次摘要输入。保留最近消息原文，以维持“那条”“刚才说的”等短距离指代。

此方案会在触发压缩时增加一次模型调用，但后续请求复用摘要，不反复总结全部历史；原始消息不变，可用于完整回放和重新生成摘要。

### 未选方案

- 每轮临时总结全部旧消息：不增加持久化合同，但重复计费、延迟高，失败重试也可能重复压缩。
- 只保留最近窗口：成本最低，但这是现有策略，无法解决早期对话脉络丢失。
- 引入通用聊天记忆框架：当前系统已经有服务端日志、历史裁剪和提示构建边界；为单一摘要投影再引入另一套状态管理没有足够收益。

## 4. 架构与数据合同

### 唯一 owner

新增的助手对话上下文组装层负责决定摘要覆盖范围、压缩触发、摘要输入与最终模型窗口。`AssistantConversationService` 继续编排请求；`AssistantConversationLogService` 继续拥有原始对话的追加和回放；`AssistantPromptBuilder` 只消费组装好的摘要与近期历史，不自行裁剪或生成摘要。

### 摘要投影

新增独立 `assistant_conversation_summaries` 表，每个 `(user_id, conversation_id)` 最多一条当前摘要，至少包含：

- 摘要文本（有数据库长度约束）；
- `through_message_id`：摘要完整覆盖到的最后一条消息；
- `version`：用于并发更新 fencing；
- 创建和更新时间。

原文仍仅存于 `assistant_conversation_messages`。摘要是可丢弃、可重建的派生投影，不成为对话真相，也不承载工具权限、确认动作、当前候选集或工具结果的权威副本。

## 5. 上下文装配流程

1. 以服务端 `(user_id, conversation_id)` 对话记录为真源；无服务端记录时继续使用当前请求的 history 回退行为，不为仅存在于请求体的历史持久化摘要。
2. 计算近期原文窗口：沿用最近消息优先规则及条数、字符限制；当前消息不纳入旧摘要。
3. 若近期窗口之外存在未被摘要覆盖的完整历史消息，则按有界批次读取。摘要输入是上次摘要加上其覆盖游标之后的新旧消息，不重复读取完整历史。
4. 生成长度受限的更新摘要，并以摘要旧版本/旧游标作为并发条件写入；并发请求不得用较旧快照覆盖较新摘要。
5. 向主回答模型发送：系统提示词、标注为“历史参考且可能不完整”的摘要、近期原文、当前请求。摘要不得覆盖系统指令、当前数据库事实或工具实时结果。
6. 对话回放始终读取原始追加消息，不把摘要伪装成用户或助手曾说过的话。

当摘要实际进入本轮上下文时，响应必须带结构化 `historyCompaction` 元信息（至少包含被摘要覆盖的消息数），前端明确提示“较早对话已整理为摘要，细节可能不完整；完整原文仍可回看”。它与现有 `historyTrim` 分开：未被摘要覆盖且也未进入近期原文的消息仍按裁剪计数提示，不得把摘要说成原文完整保留。

摘要至少保留：当前目标、用户明确给出的约束、已确认决定、未解决事项和理解后续指代所需的必要名词。不得把模型猜测升级为用户已确认事实；对相互冲突的历史，应保留冲突或按时间标注，而不是擅自裁决。

## 6. 预算、成本与失败处理

- 为 system prompt、对话摘要、近期历史、当前请求及模型输出预留分别的预算；输入整体必须在主模型调用前完成预算检查。
- 以模型适配的 tokenizer 估算输入 Token，供应商返回的 usage 用于事后核对和校准；现有字符/消息限制和序列化字节限制保留为最后一道上限，不替代 Token 预算。
- 第一轮默认只注入日期/时区和工具合同，不预加载待办、会话或联系人候选；模型选择只读检索工具后，服务端才把该工具返回的有界候选替换进下一轮上下文。这样与本轮无关的候选不会消耗预算。
- 只有待压缩旧消息达到配置的最小 Token 量/预估节省门槛时才调用摘要模型；刚越过近期窗口但压缩收益不足时，沿用裁剪，不为极少量历史额外付一次模型调用。
- 摘要源消息批次、摘要输出、每轮摘要调用次数和主模型上下文均必须有硬上限，禁止一条长对话触发无界循环。
- 摘要生成失败或超时，不阻塞本轮回答：回退到现有近期历史裁剪路径，并保留现有裁剪提示；失败摘要不推进覆盖游标。每个请求最多尝试一次摘要生成，避免重试放大费用。
- 摘要生成调用的模型、输入/输出 Token（若供应商提供）、耗时和失败原因应可观测。Token 统计缺失时记录为不可用，不伪造估值为真实 usage。

## 7. 安全与隔离

- 查询和更新始终同时约束 `user_id` 与 `conversation_id`；不得仅依赖调用方做归属校验。
- 摘要及原对话均作为不可信历史文本处理；其中出现的指令不能授权工具调用、修改权限或覆盖当前系统规则。
- 摘要器只处理该会话已落库消息，不读取其他会话、联系人、渠道或工具状态。
- 摘要不得包含待确认动作可执行状态；待确认状态始终查询当前服务端状态。

## 8. 验收标准

- 短会话不额外调用摘要模型，现有近期历史行为保持不变。
- 长会话请求同时包含历史摘要与最近原文；摘要游标之前的消息不会被重复输入，游标之后且应纳入的消息不会静默遗漏。
- 完整回放仍返回原始对话，摘要内容不会作为聊天消息展示。
- 前端能区分“早期历史已摘要”和“早期历史仍有消息被裁掉”；开始新会话时清除这两类会话级提示。
- 同会话并发压缩不能覆盖较新版本；跨用户使用相同会话 UUID 不能读写对方摘要。
- 摘要模型超时、无效输出或超长输出均回退到现有裁剪行为，当前请求仍可继续处理。
- 长历史、长单条消息、供应商缺少 usage、摘要连续失败等测试证明所有循环、请求和输出都有界。
- 用代表性对话评估摘要后任务连续性、事实/约束保留率及 Token 成本；压缩不能使用户确认内容或执行边界消失。

## 9. 非目标与风险

- 不删除、改写或归档原始聊天记录；不改变完整回放功能。
- 不修改联系人 AI 记忆、客户画像、联系人事实或标签上下文。
- 不引入向量数据库或额外记忆框架；相关消息排序仍由对话上下文 owner 负责。
- 摘要会丢失部分措辞、弱信号和细节，可能影响远距离指代。通过保留最近原文、可见裁剪状态和完整原文回放降低风险，但不能保证摘要与原文等价。
- 摘要调用会产生额外 Token 与延迟；其成本应与节省的主模型输入 Token 对比后再调节触发频率和预算。

## 10. 实施边界

实施应先补摘要数据合同和并发更新测试，再实现有界摘要更新及上下文组装，最后接入 prompt 与可观测性。不要在本设计确认前改动现有 assistant WIP；实施时必须基于当时工作区重新审计调用链、测试和配置。

## 11. 已确认的实现决定

- Token 估算使用 jtokkit `o200k_base`，未知编码在启动时失败；供应商未返回 usage 时记录为不可用，不用字节数或字符数冒充真实 usage。
- `assistant_conversation_summaries` 是每个用户/会话一行的可重建投影，使用 `(created_at, id)` keyset 游标和版本 CAS；V100 已在 PostgreSQL 17.5 空库通过 Flyway 全量迁移。
- 摘要投影读取或写入发生数据库访问异常时，本轮保留近期原文并回退裁剪；客户端 fallback history 不进入摘要持久化。真实服务端原文读取仍由会话日志 owner 提供，不把数据库错误伪装成“无历史”。
- 上下文服务的生产构造器显式使用 Spring 注入；摘要调用没有工具注册表或写操作权限。摘要输出及主请求均执行完整 prompt token 预算检查。
- 前端 `historyCompaction` 与 `historyTrim` 分开显示，并在新会话时清除；完整回放只读取原始消息表。

## 12. 验收边界

截至 2026-09-24，摘要专项后端 73/73 通过、V100 Flyway/Testcontainers 1/1 通过、助手面板测试 26/26 通过、前端生产构建通过。后端全量回归为 2133 tests，其中摘要相关链路通过；全量仍有 2 个与本设计无关的既有失败（ChatApp 出站幂等、联系人记忆迟到消息），以及此前由构造器注入问题造成的连锁错误已修复并由 `AppIntegrationTest` 10/10 复验通过。
