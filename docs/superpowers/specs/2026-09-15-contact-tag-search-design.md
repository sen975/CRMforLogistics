# 联系人标签搜索设计

## 目标

让用户按标签模糊查找联系人。统一会话列表、渠道通讯录和发送页联系人选择器三个搜索入口都提供「联系人」和「标签」两种搜索模式，模式决定匹配范围，两者互不混搜。

## 边界

- 只做搜索。标签的创建、编辑、删除沿用现有的 `PUT /api/contacts/{id}/tags`，本轮不改。
- 标签归属恒为当前登录用户的 `contact_tags.owner_user_id`，与详情页 `findActiveByContactIdAndOwner` 一致。管理员看到的也是自己打的标签，不因管理员身份放开。
- 不做独立的标签筛选器，不做「标签:xxx」这类语法。
- 不改搜索结果的排序规则。
- 不改变联系人模式及无搜索时的任何现有行为。

## 交互合同

- 三个入口的搜索框各带一个模式选择控件，取值「联系人」/「标签」，默认「联系人」。
- 切换模式时清空当前关键词，并重置分页与游标。
- placeholder 随模式切换。联系人模式保持各页现有文案；标签模式显示「搜索标签名」。
- 标签模式无结果时，空状态文案区别于「暂无联系人」，明确说明没有联系人被打上含该关键词的标签。

## 接口合同

三个列表接口各新增一个可选参数 `searchMode`，取值 `contact` 或 `tag`：

| 接口 | 新增参数 |
| --- | --- |
| `GET /api/conversations` | `searchMode` |
| `GET /api/contacts` | `searchMode` |
| `GET /api/channel-address-books/{channelType}` | `searchMode` |

缺省或为 `contact` 时，行为与改动前完全一致。未知取值返回 HTTP 400 和错误码 `CONTACT_SEARCH_MODE_INVALID`，不静默降级为联系人模式——静默降级会让用户以为自己搜的是标签，拿到一份名字命中的结果。

## 匹配规则

- 联系人模式：完全沿用现有的名称、备注、号码、邮箱匹配，不匹配标签。
- 标签模式：只匹配标签名，子串模糊（大小写不敏感），不匹配姓名、备注、号码、邮箱。
- 只匹配 `status = 'active'` 的标签。
- 只匹配当前用户的标签。
- 标签模式下群聊不出现在结果中，因为群没有联系人标签。
- 关键词为空白时，两个模式都退回「无搜索」分支。

## 命中标签回填

- 标签模式下的结果行额外返回命中的标签名，只含与本轮关键词匹配的标签，不含该联系人的其他标签。
- 一次搜索里一个联系人可能命中多个标签，全部返回，按标签名小写排序，与详情页的标签排序一致。
- 联系人模式及无搜索时该字段为空。

## 展示

- 统一会话列表：命中标签 chip 显示在联系人行的名称区域。
- 渠道通讯录：chip 追加在「联系人」列名字之后，不新增表格列。
- 发送页选择器：chip 追加在下拉选项的名称之后。
- 三处都只在标签模式且确有命中标签时显示 chip。

## 错误与安全

- 标签搜索的作用域是当前用户，不能通过搜索探测其他用户的标签。
- 鉴权沿用三个接口的现有规则，不新增。
- 关键词里的 `%`、`_` 仍按通配符处理，这是三处搜索的既有行为，本轮不单独修改，以保持一致。

## 验收

- 标签模式输「客户」能搜到标签为「VIP客户」「老客户」的联系人。
- 昵称含「VIP」但没有 VIP 标签的联系人，标签模式下搜「VIP」不出现。
- 联系人模式下搜昵称，结果不因该联系人打了标签而改变。
- 用户 A 打的标签，用户 B 搜不到。
- 停用的标签搜不到。
- 结果行只显示命中的标签，不显示该联系人的其他标签。
- 标签模式下不出现群聊。
- 不传 `searchMode` 时，三个接口的响应与改动前一致。
- 三个入口都能切换模式，切换后关键词清空。
