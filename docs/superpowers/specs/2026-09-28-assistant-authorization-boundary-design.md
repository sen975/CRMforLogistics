# 助手授权读取边界设计

状态：已确认设计；助手渠道投影、审计脱敏、部分授权错误合同和 Mapper 门禁已实现；确认回执进入模型历史的泄露路径阻断最终验收
日期：2026-09-28

## 1. 背景与目标

助手需要能够长期读取用户有权限访问的数据，包括联系人、会话、消息、电话、记忆、待办和 AI Topic。当前系统已经把登录用户 ID 传入助手编排和工具调用，但不同领域的授权查询、敏感字段投影和候选引用规则分散在多个服务中。

本设计的目标是建立一个长期有效的授权边界：

- 助手严格继承当前用户在系统内已有的数据权限；
- 不因为加入助手白名单而新增任何业务权限；
- 读取授权和字段投影由领域 owner 负责，而不是由模型、控制器或候选集决定；
- 未来增加助手工具或字段时，能够通过架构测试和权限测试阻止越权回归；
- 在满足用户请求的前提下，尽量减少邮箱、手机号、渠道账号、消息正文和通话转写等敏感数据进入模型上下文。

## 2. 产品边界

### 2.1 本轮目标

1. 统一助手工具的身份来源、授权读取和最小投影原则。
2. 补齐助手候选与简报的授权渠道身份投影，让模型能够区分同名联系人和不同账号；不改变普通联系人 API 的现有身份可见语义。
3. 为联系人、会话、消息、通话、记忆、待办和 AI Topic 建立 owner service 边界。
4. 明确授权失败、敏感字段拒绝、伪造引用和内部异常的错误合同。
5. 增加跨用户、团队授权、过期授权、管理员、删除/合并和日志泄露测试。

### 2.2 非目标

- 不新增用户、团队或管理员权限。
- 不重定义现有业务权限模型、团队分配规则或会话授权规则。
- 不把所有非密码字段放入全局助手白名单。
- 不将账号密码、访问令牌、原始邮箱、手机号或第三方凭证交给模型。
- 不在本轮引入数据库 Row-Level Security；当前项目继续使用现有 service 和 SQL 授权边界。
- 不以候选集、历史对话、摘要或模型传入的 ID 作为授权凭证。

## 3. 当前证据与问题

### 3.1 已有安全基础

- `AssistantController` 从认证上下文取得 `SecurityUtil.currentUserId()`。
- `AssistantConversationService` 将该 ID 传入 `ToolRegistry.invoke`。
- 工具 schema 使用 `additionalProperties: false`，模型不能通过参数注入另一个 `userId`。
- 联系人候选使用 `ContactMapper.listForUser`，其 SQL 已包含本人、团队、会话授权、软删除和合并排除条件。
- 消息读取使用带 owner/会话授权的查询；企业微信旧消息另有授权校验。
- 待办、发送和记忆工具均将当前用户 ID 传入领域服务。

### 3.2 已发现的具体风险

`ContactService.getById` 先通过 `findAccessibleById` 验证联系人可见性，随后调用不带用户范围的 `ContactIdentityMapper.findByContactId` 读取联系人全部渠道身份。该响应也供普通联系人页面使用；直接改成 identity-scoped 查询会改变现有联系人 API 的行为。本轮不改这个共享响应，只确保助手不把它或身份原值送进模型；普通 API 的身份可见性另行审计。

助手侧的 `contact.search` 当前只投影姓名、备注和引用 ID，未暴露渠道值；`contact.brief` 只读取授权联系人及其 owner 记忆投影。该设计必须保持，并不能因为需要“看见渠道”而直接把所有身份值加入候选。

## 4. 核心原则

### 4.1 身份单一来源

用户身份只能来自认证上下文。请求体、工具参数、模型输出、会话历史和待确认动作都不能覆盖当前用户 ID。

### 4.2 授权由领域 owner 执行

每个数据域的 owner service 负责把当前用户 ID 传入既有授权查询，并在资源读取时重新验证。控制器、模型提示词、候选 provider 和 `ToolRegistry` 不拥有业务授权语义。

### 4.3 候选集不是权限

候选集用于消歧、限制模型编造引用和控制上下文大小，但只代表“当前已发现的引用窗口”。任何 `brief`、`read`、发送或写操作都必须重新走 owner service 授权查询。

### 4.4 授权后再投影

先取得授权资源，再转换成显式的助手 DTO/record。禁止把 Entity、Mapper 行或包含未审计字段的响应对象直接序列化给模型。

### 4.5 最小字段原则

只有当前任务必需的字段才能进入模型上下文：

- 联系人：姓名、备注、角色、当前用户可见的渠道类型，以及有界的渠道身份值、显示名和账号标签；
- 联系人身份：只有发送或明确查询身份时才读取，默认不回传原始地址；
- 会话：类型、名称、渠道类型、时间、未读数和置顶状态，不回传最后一条正文；
- 消息：仅用户明确引用的单条消息正文；
- 通话：授权范围内的摘要或明确请求的转写；
- 记忆：画像、结构化事实、AI/人工标签和话题；
- 待办：当前用户自己的待办字段；
- AI Topic：当前用户可见的 Topic 投影。

账号密码、访问令牌、邮箱/手机号原始值、渠道账号凭证和完整内部元数据永不进入通用助手上下文。

## 5. 模块边界与数据流

```text
认证上下文
  -> AssistantController
  -> AssistantConversationService
  -> ToolRegistry
  -> 领域 Owner Service
  -> 授权查询
  -> 最小字段 Projection
  -> ToolResult
  -> 模型
```

### 5.1 层职责

| 层 | 职责 | 禁止事项 |
|---|---|---|
| `AssistantController` | 读取认证用户、转换 HTTP 形状 | 解析请求体 userId、执行业务授权 |
| `AssistantConversationService` | 对话编排、上下文预算、工具循环 | 直接查业务表、重新实现领域权限 |
| `ToolRegistry` | 工具注册、schema 校验、统一调用 | 直接访问 Mapper、决定资源归属 |
| 领域 Owner Service | 授权、资源读取、领域错误转换 | 把未投影 Entity 交给模型 |
| Projection | 字段白名单、长度和数量上限 | 读取后再依赖调用方“记得过滤” |
| Mapper | 带授权条件的结构化查询 | 提供助手专用的无范围全字段查询 |

### 5.2 领域 owner

| 领域 | Owner | 授权依据 |
|---|---|---|
| 联系人 | `ContactService` / 联系人授权查询 | 本人、团队分配、有效会话授权、管理员 |
| 联系人身份 | owner-scoped `ContactIdentity` 查询 | 联系人可见性与具体身份范围 |
| 会话 | `ConversationAccessService` / `ConversationMapper` | 分配、团队、有效授权、管理员 |
| 消息 | `MessageQueryService` | 消息所属会话授权；旧企业微信记录额外校验 |
| 通话 | `ContactTimelineService` / `CallRecordService` | owner/contact 范围和既有电话权限 |
| 联系人记忆 | `ContactMemoryQueryService` | 联系人 `created_by` owner |
| 待办 | `TodoItemService` | `todo.user_id = current user` |
| AI Topic | `AiTopicService` | 既有用户/联系人 owner 规则 |
| 发信 | `OutboundMessageService` | 联系人授权、身份授权、渠道账号规则 |

## 6. 具体行为合同

### 6.1 助手候选与简报的授权渠道身份投影

`ContactService.getById` 及 `listForUser` 的既有返回行为保持不变。联系人 owner 提供仅供助手消费的 `listAuthorizedChannelProfiles(userId, contactId)`：查询 `findByContactIdAndOwner`，只投影有界的渠道类型、身份值、显示名和账号标签。`identityScope` 只用于 owner-scoped 的账号名称解析，不进入模型；无法按当前用户解析账号时 `accountLabel` 为 null。候选和简报都从该投影派生 `channelTypes` 与 `channels`，不返回 `ContactIdentityEntity`、数据库 ID、normalized value 或凭证。

联系人可见但身份不可见时：

- 联系人基本信息可以按既有规则返回；
- 不返回该身份的原始地址、规范化地址或第三方账号标识；
- 发送操作重新由 `OutboundMessageService` 按当前用户权限解析目标；
- 助手工具不把“联系人可见”推导为“所有身份可见”。

### 6.2 发送工具

`message.send_email` 和 ChatApp 发送工具只接收 `contactRef`、主题和正文等业务参数。收件地址或第三方目标由服务端通过当前用户授权解析，不接受模型传入的 `to`、邮箱、手机号或账号 ID。

### 6.3 引用与重新授权

历史候选、对话摘要、模型生成的引用和待确认动作中的资源 ID 都是不可信输入。每次调用 `contact.brief`、`message.read`、时间线读取、发送或写操作时，owner service 必须重新授权。授权失败不得因为该 ID 曾出现在候选集中而放行。

### 6.4 联系人候选的跨请求窗口

`contact.search` 的成功结果可在当前登录用户与当前助手会话的 `(user_id, conversation_id)` 下保留一个短期引用窗口。窗口只存最多 20 个 `CONTACT:<uuid>`，不存姓名、渠道身份、邮箱、号码、正文或凭证；每次非空检索替换该会话上一次的联系人窗口，空结果不清空。新会话、缺失会话号、过期或存储不可用时不恢复，模型必须重新调用 `contact.search`。窗口从检索完成起 30 分钟过期，后台定时删除过期行；数据库约束限制条数和 JSON 字节大小，进程内同样限制。并发较旧的结果不得覆盖较新结果。

恢复窗口时，`ContactCandidateProvider` 逐条按当前用户重新执行 `ContactMapper.findAccessibleById`，仅把依然可见的联系人重新投影为当前姓名和当前授权渠道；撤权或删除项静默排除。窗口是防止模型编造 `contactRef` 的有界上下文，不是业务授权凭证。解析器保持 `x-candidateSet` 命中校验；`contact.brief` 及其他实际工具继续由领域 owner 在每次调用时重新授权。窗口与对话摘要分离，摘要中的旧引用不能自行恢复为候选。

## 7. 错误、隐私与审计合同

### 7.1 错误码

- `UNAUTHENTICATED`：无认证身份，HTTP 层返回 401。
- `FORBIDDEN_OR_NOT_FOUND`：资源不存在或当前用户无权访问，统一对外措辞。
- `INVALID_ARGUMENT`：引用格式错误或不属于当前候选窗口，沿用现有助手工具/API 合同。
- `SENSITIVE_FIELD_DENIED`：请求的敏感字段不在当前操作授权范围内。
- `INTERNAL`：内部异常；不得将 SQL、路径或底层异常传给模型。

### 7.2 不得泄露的信息

授权失败不得说明资源是否真实存在、资源所属用户、其他用户的联系人或身份、数据库异常、邮箱、手机号、访问凭证或第三方账号标识。

### 7.3 审计字段

审计可记录当前用户 ID、工具名、资源类型、脱敏资源 ID、授权结果、投影字段集合、失败原因码、耗时和返回条数。不得记录完整消息正文、通话转写、完整 prompt、邮箱、手机号、密码或访问令牌。

## 8. 测试与门禁

### 8.1 必测矩阵

1. 本人资源可读。
2. 团队分配资源可读。
3. 有效共享授权资源可读。
4. 撤销或过期授权立即不可读。
5. 管理员行为与现有系统规则一致。
6. 其他用户私有联系人、消息、通话、记忆、待办和 Topic 不可读。
7. 伪造资源 ID、旧候选 ID和跨会话引用均被拒绝。
8. 软删除、合并联系人及其旧身份不可通过助手读取。
9. 不需要地址的场景不返回邮箱、手机号和原始身份值。
10. 错误响应和审计日志不包含正文、转写、凭证或原始地址。

### 8.2 架构门禁

- `service.assistant.mcp` 不得直接依赖 Mapper。
- 新工具必须声明引用参数的候选集绑定或明确豁免。
- 新的只读工具必须进入显式 read-only allowlist，并通过启动期注解一致性检查。
- Projection 必须是显式 DTO/record，不得直接序列化 Entity。
- 新增敏感字段必须同时提供 owner 查询、字段投影和权限测试，否则禁止合入。

### 8.3 完成标准

- 所有助手读取工具都经过领域 owner 授权；
- 助手候选和简报只通过联系人 owner 的授权查询读取渠道身份投影；普通 `ContactService.getById/listForUser` 行为不变；
- 既有助手对话、发送确认和上下文压缩行为保持通过；
- 权限专项测试、助手专项测试、架构测试和后端编译通过；
- 设计、实施计划和验收记录进入 `docs/superpowers/README.md` 索引；
- 无法在本地验证的真实外部权限场景被明确记录，不以模拟结果替代。

## 9. 风险与取舍

### 设计风险

- 普通联系人 API 仍有“先授权联系人、再用无范围关联查询”的历史路径；本轮不改变其返回语义，它的权限细化须独立产品决策和 UI 回归。
- 管理员权限可能比普通用户更宽，但仍必须经过字段投影；管理员不等于可以把全字段交给模型。
- 同一联系人可能有多个渠道身份，身份可见性和联系人可见性必须保持两个概念。

### 可记录债务

- 本轮不引入数据库 RLS。若未来出现非助手入口频繁绕过 owner service，再单独评估数据库级隔离。
- 本轮不改变现有数据保留策略；消息和通话转写的生命周期继续由各自领域合同负责。

## 10. 实施顺序

实施计划必须按以下顺序拆分：

1. 建立助手工具到 owner service 和投影的审计清单。
2. 给助手候选和简报增加 owner-scoped 渠道身份投影、账号标签解析和用户隔离测试，保持普通联系人 API 不变。
3. 逐个核对消息、会话、通话、记忆、待办和 Topic 工具的 owner 路径。
4. 补统一错误码、敏感字段投影和日志泄露测试。
5. 加架构门禁，阻止助手直接访问 Mapper 和未声明字段投影。
6. 运行专项测试、编译和权限回归，记录无法在本地完成的外部验收。

## 11. 2026-09-28 实施核对

- 联系人渠道身份由 `ContactService.listAuthorizedChannelProfiles` 按 owner-scoped 身份查询投影；候选和简报输出 `channels`，普通联系人 API 的身份返回语义未改变。
- `AssistantAuditService` 新增审计记录只保存原话字符数与 SHA-256 摘要、参数顶层键名与类型、规范化参数摘要；不再保存原话和参数值。现有表列宽兼容，无新迁移。已有历史行不会被这次写入逻辑回填或删除，仍需独立治理。
- 已检查的格式正确但资源不存在或无权访问路径返回 `FORBIDDEN_OR_NOT_FOUND` 和中性文案；格式错误保持 `INVALID_ARGUMENT`。`message.read` 保留用户明确引用的单条正文，不再附带 `from/to` 原始地址。`ContactGroupService` 的访问失败有独立异常类型，避免与字段校验混淆。
- `AssistantToolAuthorizationArchitectureTest` 约束助手 MCP 生产类不得直接依赖 Mapper。测试结果、跳过项和工作树提交边界见[授权边界验收记录](../reviews/2026-09-28-assistant-authorization-boundary-verification.md)。
- 尚未闭合：待确认卡片的 `summary` 同时承载可供人核对的地址/正文和会持久化进入下一轮模型的 `message`，发送成功回执也把原始收发地址写入结果。需要明确前端回执与模型历史的分离合同，再补跨两轮验收；当前不得声称“地址永不进入通用助手上下文”。
