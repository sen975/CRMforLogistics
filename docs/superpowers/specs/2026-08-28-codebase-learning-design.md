# 代码库学习计划设计（修订版：含可迁移沉淀）

> **日期**：2026-08-28（修订：加入「能力沉淀层」）
> **目的**：为「产品背景、技术栈不熟」的使用者建立对本项目（消息中心 CRM）的持久心智模型，对抗遗忘曲线，并随项目持续开发而保持更新；同时**沉淀可迁移的技术与开发经验，不随离开项目而作废**。
> **背景**：一次性读代码（311 个 Java 文件）对有限脑容量不友好；静态文档会随持续开发过期；且使用者不会一直做这个项目——项目是训练场，不是终点。

---

## 1. 目标

建立对项目架构与核心部分的**持久**心智模型，并**沉淀带得走的能力**。五个使用场景：

1. **上手开发 / 修 bug** —— 能快速定位到对应前后端类与方法
2. **对外讲解** —— 能给客户/团队讲清 9 大板块与整体架构
3. **建立认知** —— 理解最核心部分，不依赖读完全部代码
4. **评估架构** —— 能判断哪里设计好、哪里是技术债（如当前 presplit）
5. **沉淀能力** —— 积累可迁移到任何项目的技术模式、踩坑经验、工作方法，以及技术栈熟练度

## 2. 核心原则

| 原则 | 含义 |
|---|---|
| 先地图后细节 | 先有整体空间感，再逐板块深入；绝不一上来读代码 |
| 领域类比翻译 | 每个技术概念用使用者熟悉的 CRM/物流/日常语言讲，不做术语轰炸 |
| 主动回忆 | 回顾卡 + 定期测验，对抗遗忘曲线 |
| 轻量不仪式 | 每次会话可中断、可恢复、可跳过；不搞繁重流程 |
| 随开发走 | 学习跟着项目开发节奏持续刷新，不是一次性投入 |
| 分层沉淀 | 产物分两层：项目层（随项目过期）+ 能力层（带得走） |

## 3. 学习结构（三层）

### 第 0 层 · 逛地图（一次性，只建空间感，不读代码）

产出 1 页架构总图，标注**基准 commit**：

- 9 大板块的位置关系与依赖方向（业务 → 基础设施）
- 一条主数据流：一条消息从「发送 → 落库 → 被查到」
- 后台定时任务全景

架构总图是锚点，只有大改才更新。

### 第 1~9 层 · 板块循环（先学 3 个最稳定的核心板块）

**先学最稳定的业务地基**：消息核心、联系人、基础设施。变化慢，学完长期有效。

每个板块一个小循环（讲解 → 动手 → 回顾卡）：

1. **讲解（约 20 分钟）**：为什么有这个板块、解决什么问题、入口 API、关键链路，全程领域类比
2. **动手（1 个小任务，30 分钟内）**：改字段 / 顺着链路查一段 / 修个小 bug，逼使用者摸到真实代码
3. **回顾卡（1 张）**：职责 + 入口 + 关键链路 + 一句话锚点 + 类比，由使用者亲手写下

### 每周回顾（约 30 分钟，持续性）

1. **先 diff 再复习**：用 `git log` 看这两周改了哪些板块，只重看变动的板块，其余不碰
2. **测验**：用已攒的回顾卡出题（填空 / 复述 / 判断），使用者作答
3. **答错的进入下一周再考**

## 4. 持续维护机制（关键，随开发走）

1. **板块卡带「上次核对」日期**：`上次核对: YYYY-MM-DD`，一眼看出哪张可能过期
2. **每周回顾 = 先 diff 再复习**：对照 `git log` 检查板块变化，自动清理过期知识
3. **开发即学习**：做任何 feature / 修任何 bug，改完顺手更新对应板块卡
4. **新增板块 → 新开卡**：如最近的 AI topic 就是新板块，做的时候开一张卡
5. **维护成本必须低**：更新卡片发生在「本来就在改这段代码」时，不是额外写文档任务

## 5. 能力沉淀层（带走的资产，新增）

### 两层产物

- **A. 项目层**：地图 + 板块卡。负责「在这个项目里能干活」，离职后价值归零
- **B. 能力层**：每次学板块 / 修 bug / 做架构决策，抽一条**可迁移的收获**，沉淀进独立能力库。这层**属于使用者个人，不属于项目**——离开时拷贝带走，进下一个项目继续用同一套结构积累

### 能力库条目格式

```
【类别】技术模式 / 架构决策 / 踩坑经验 / 工作方法
【名称】可靠消息投递 · outbox 模式
【一句话】发消息不直接发，先写进待发箱表，后台 worker 轮询再发，防止发一半丢消息
【本项目实例】MessageSendApplicationService 写 outbox_jobs → MessageOutboxScheduler 每秒轮询
【能迁移到】任何「发送不可靠 / 需要重试」的系统：订单通知、消息推送、外部 API 调用
```

### 积累节奏（随开发走，不额外加负担）

- 每学一个板块 → 讲解时顺带提炼至少 1 条
- 每修一个 bug / 每做一次 review → 抽 1 条（**踩坑经验最值钱**）
- 每周回顾时顺带整理

### 技术栈熟练度清单

另存一份「我会了什么」自评，学之前 vs 学之后逐项打勾：Spring Boot / MyBatis-Plus / PostgreSQL / React / Docker。

## 6. 产物与存放（私有记忆库）

| 文件 | 内容 |
|---|---|
| `docs/learning/00-架构总图.md` | 一页图（从 `docs/代码板块地图.md` 浓缩），标注基准 commit |
| `docs/learning/板块N-<名称>.md` | 每板块 1 张回顾卡，含「上次核对」日期 |
| `docs/learning/README.md` | 学习进度跟踪：已学 / 待学 / 薄弱点 / 上次全量核对日期 |
| `docs/learning/transferable/00-模式库.md` | 技术模式 + 架构决策（随时间增长） |
| `docs/learning/transferable/01-踩坑与经验.md` | bug 教训、review 反馈、工作方法 |
| `docs/learning/transferable/02-技术栈熟练度.md` | 能力自评清单（学前 vs 学后） |

这些是「使用者的私有记忆库」，不是给别人的正式文档。

## 7. AI 的角色边界

AI 是**建议型教练**：负责讲解、出任务、出题、协助记录回顾卡与能力库条目。

- 学习节奏、深度、顺序由使用者定
- 使用者随时可打断、跳过、要求换类比
- AI 不自动改项目代码（涉及改动先确认）

## 8. 成功标准

- 面对真实 bug，使用者能独立说出「去哪找入口、走哪条链路、是哪个类」
- 不看文档能给客户讲清 9 大板块
- 对「哪里架构好、哪里是债」有自己的判断
- 持续开发几个月后，心智模型仍与代码现状一致（依赖「上次核对」机制）
- **离开项目时，带走一叠可复用的模式库 + 一套成熟的开发工作方法 + 一份技术栈熟练度清单**——这才是真正的「沉淀」

## 9. 与现有文档的关系

- 不替代 `docs/代码板块地图.md`（评审/压测视角）与 `docs/代码阅读顺序.md`（通读视角）
- 本计划是**使用者视角**的私有学习路径，从现有文档浓缩出「总图 + 回顾卡 + 能力库」这一轻量层

## 10. 首个实现步骤

1. 建 `docs/learning/` 骨架：`README.md`（进度跟踪）+ 回顾卡模板 + `transferable/` 三个能力库模板
2. 产出 `00-架构总图.md`：从代码板块地图浓缩的一页图，标注基准 commit
3. 之后按「先学 3 个核心板块」开始第 1 个板块循环
