# 企业微信只读消息采集 PoC 方案

## 1. 文档定位

本文用于描述企业微信一对一销售沟通场景下的“只读消息采集”技术探索方案。

本方案不是第一阶段 MVP 的正式交付主线，也不替代企业微信官方能力。当前产品正式主线仍为：

1. 企业微信客户联系 API：同步外部联系人、销售归属、标签、备注等客户资产数据。
2. 企业微信会话内容存档：在客户已开通且满足合规条件时，作为官方聊天记录来源。
3. AI 回复草稿：系统生成回复建议，销售复制或唤起企业微信客户端后由本人确认发送。
4. CRM 沟通时间线：沉淀 WhatsApp、邮件、电话纪要、企业微信资料和可合规获取的聊天记录。

本文方案仅作为增强实验线，用于验证在授权测试环境中是否可以把销售企业微信客户端中的聊天消息只读归档到 CRM。

## 2. 结论摘要

企业微信官方通常不允许第三方系统代替某个销售个人向个人微信客户发送一对一消息。若目标是获取销售与客户之间的聊天内容，官方路径主要是会话内容存档。

私有协议、iPad 协议、模拟客户端类方案可以作为技术 PoC 验证消息读取能力，但不应作为正式客户交付承诺。第一阶段最多验证“只读采集 + 联系人匹配 + CRM 时间线归档”，不做自动发送、群发、朋友圈发布和风控规避能力。

推荐边界：

```text
只读消息采集
  -> 消息标准化
  -> 联系人身份匹配
  -> CRM 沟通时间线
  -> AI 摘要 / 跟进提醒 / 回复草稿
```

禁止边界：

```text
模拟销售自动发送
  -> 群发
  -> 朋友圈发布
  -> 多账号规避风控
  -> 代理池 / 指纹绕过作为产品能力
```

## 3. 适用场景

本方案仅适用于以下场景：

1. 客户希望先验证企业微信销售私聊消息是否能进入 CRM 时间线。
2. 企业微信会话内容存档暂未开通、开通周期较长，或客户希望评估替代采集的技术可行性。
3. 使用测试企业、测试销售账号、测试客户号进行验证。
4. 企业内部已完成必要的授权、告知和合规确认。
5. 系统只读取和归档消息，不代替销售发送任何消息。

不适用于以下场景：

1. 对外承诺稳定替代企业微信官方 API。
2. 在客户正式销售账号上无授权运行。
3. 做企业微信自动群发、自动回复、朋友圈自动发布。
4. 规避企业微信风控、封禁、登录校验或访问控制。
5. 把私有协议采集作为 CRM 唯一消息来源。

## 4. 总体链路

```text
测试销售企业微信账号
        ↓
客户端实例层
创建实例、登录、保存会话、心跳保活、断线恢复
        ↓
长连接事件层
监听文本、图片、语音、文件、撤回、系统通知等事件
        ↓
协议适配层
解析私有协议事件，输出内部统一消息结构
        ↓
消息标准化层
统一方向、类型、发送人、接收人、时间、原始消息 ID、附件信息
        ↓
身份匹配层
根据销售账号、客户标识、昵称、备注、手机号、企业微信客户联系数据进行联系人匹配
        ↓
CRM 沟通时间线
写入联系人和企业可见的沟通记录，标记为实验性非官方来源
        ↓
AI 协作层
生成摘要、跟进提醒、风险提示、回复草稿
```

## 5. 模块设计

### 5.1 WeCom Client Capture Collector

职责：

1. 管理测试销售账号的客户端采集实例。
2. 维持登录态、心跳和断线恢复。
3. 从客户端事件流中读取消息事件。
4. 将原始事件投递到消息队列或内部接收接口。

边界：

1. 不直接写 CRM 业务表。
2. 不做联系人归属判断。
3. 不生成 AI 回复。
4. 不提供发送消息能力。
5. 不保存明文敏感密钥到普通日志。

建议输出：

```json
{
  "sourceType": "wecom_client_capture",
  "officialSource": false,
  "collectorInstanceId": "capture-instance-id",
  "salesUserKey": "sales-account-key",
  "rawConversationKey": "raw-conversation-key",
  "rawMessageId": "raw-message-id",
  "messageType": "text",
  "direction": "inbound",
  "senderHint": "sender-hint",
  "receiverHint": "receiver-hint",
  "content": "message content",
  "mediaRef": null,
  "sentAt": "2026-07-02T10:00:00+08:00",
  "capturedAt": "2026-07-02T10:00:03+08:00"
}
```

### 5.2 Message Normalize Service

职责：

1. 将采集层事件转换为 CRM 内部统一消息模型。
2. 处理文本、图片、语音、文件、链接、撤回、系统消息等类型。
3. 生成幂等键，防止重复写入。
4. 保留必要原始引用，便于排查。

建议幂等键：

```text
sourceType + salesUserKey + rawConversationKey + rawMessageId
```

如果原始消息 ID 不稳定，可增加时间窗口和内容摘要作为辅助去重依据，但数据库唯一约束必须优先于 Redis 去重。

### 5.3 Contact Identity Match Service

职责：

1. 把企业微信采集到的对话对象匹配到 CRM 联系人。
2. 支持人工确认和人工修正。
3. 保留匹配置信度和匹配依据。
4. 避免把同名客户错误合并。

匹配依据优先级建议：

1. 官方客户联系 API 同步到的 `externalUserId` 或可稳定关联标识。
2. 销售账号 + 外部联系人备注。
3. 手机号。
4. 邮箱。
5. WhatsApp 账号。
6. 昵称。
7. 群聊上下文。
8. 人工选择。

匹配状态：

```text
matched        已匹配
ambiguous      多个可能联系人，需要人工确认
unmatched      未匹配
manually_bound 人工绑定
ignored        忽略，不进入客户时间线
```

### 5.4 CRM Communication Timeline

职责：

1. 存储标准化后的沟通记录。
2. 根据联系人和企业关系控制可见范围。
3. 支持按联系人、企业、销售、渠道、时间筛选。
4. 明确展示来源是否官方。

企业维度可见规则：

1. 联系人必须被使用者设定到某个企业后，才在该企业详情中出现。
2. 消息必须先归属到联系人，再根据联系人企业关系进入对应企业时间线。
3. 未匹配联系人消息进入待归档池，不直接出现在企业详情。

### 5.5 AI Collaboration Service

职责：

1. 对沟通记录生成摘要。
2. 识别客户意图、询价、投诉、跟进节点。
3. 生成回复草稿。
4. 生成待办提醒。

边界：

1. AI 不直接发送企业微信消息。
2. AI 草稿需要销售确认。
3. 采集来源为实验性非官方数据时，页面需要保留来源提示。

## 7. 协议技术注意点

### 7.1 登录态与设备实例

私有协议方案通常不是普通 API token，而是模拟客户端设备登录。需要特别关注登录态保存、设备实例、验证码、ticket 失效、异地登录、账号安全提醒和设备数量限制。

PoC 必须使用测试账号，不使用正式销售主号。

### 7.2 长连接、心跳与断线恢复

消息事件来自客户端长连接，必须处理心跳、断线、重连、离线期间消息补偿、重复事件和乱序事件。

CRM 不应假设消息严格实时，也不应假设每条消息只到达一次。

### 7.3 二进制协议与解析隔离

私有协议字段可能随企业微信版本升级变化。采集层输出必须先转换为内部统一消息结构，CRM 核心模型不得直接依赖私有协议字段、私有指令号或客户端版本特性。

### 7.4 加密、序号和防重放

文章中涉及 RSA、ECDH、AES、ChaCha20、mmtls / TLS-like、序号 IV 等概念。此类内容属于协议适配层内部风险，不应扩散到业务层。

如果解密、序号、时间戳、会话密钥任何一项不稳定，采集链路都可能失效。

### 7.5 消息幂等

必须用数据库唯一约束保证最终幂等。Redis 或内存缓存只能作为性能优化，不能作为最终事实。

建议唯一键：

```text
tenantId + sourceType + salesUserId + rawConversationKey + rawMessageId
```

### 7.6 时间同步

部署机必须开启 NTP 校时。消息至少保留：

1. `sentAt`：消息原始发送时间。
2. `capturedAt`：采集器捕获时间。
3. `createdAt`：CRM 入库时间。

### 7.7 语音消息

企业微信移动端语音可能涉及 Silk 编码。第一阶段 PoC 建议只保存语音消息元数据和文件引用，语音转写放到第二阶段。

不要在 PoC 第一轮同时做实时语音转码、ASR、语义分析，否则复杂度会掩盖消息采集本身的验证结果。

### 7.8 网络、证书和客户端版本

证书链、客户端版本、系统时间、网络出口变化都可能影响链路稳定性。PoC 需要记录运行环境：

1. 操作系统。
2. 企业微信客户端版本。
3. 网络出口。
4. 证书配置。
5. 采集器版本。
6. 最近一次登录时间。

### 7.9 风控与合规

只读采集也可能触发企业微信风控。不得把代理池、指纹规避、多账号绕风控作为产品能力。

PoC 必须保留开关，出现异常登录、验证码、账号安全提醒、频繁掉线时立即停止。

## 8. PoC 验收目标

第一轮 PoC 只验证以下问题：

1. 是否可以稳定读取测试销售账号的文本消息。
2. 是否可以识别消息方向：客户发给销售、销售发给客户。
3. 是否可以拿到足够稳定的会话标识和消息标识。
4. 是否可以把消息匹配到 CRM 联系人。
5. 是否可以把未匹配消息进入待归档池。
6. 是否可以做到重复消息不重复入库。
7. 是否可以在断线重连后继续采集。
8. 是否可以在页面上明确展示“实验性非官方来源”。

第一轮 PoC 不验证：

1. 自动发送消息。
2. 群发。
3. 朋友圈发布。
4. 多账号批量登录。
5. 语音实时转写。
6. 文件长期归档。
7. 大规模并发。

## 9. PoC 实施阶段

### 9.1 第 0 阶段：合规与测试环境确认

交付物：

1. 测试企业微信企业。
2. 测试销售账号。
3. 测试客户账号。
4. 内部授权说明。
5. PoC 开关和停止条件。

停止条件：

1. 无法确认授权。
2. 必须使用正式销售主账号。
3. 客户要求自动发送或群发。

### 9.2 第 1 阶段：只读文本消息采集

目标：

1. 采集测试账号文本消息。
2. 标准化为内部消息结构。
3. 写入待归档池。
4. 完成幂等去重。

验收：

1. 连续运行 2 小时不崩溃。
2. 手动发送 30 条测试消息，CRM 不少于 29 条成功入库。
3. 重启采集器后不重复写入历史消息。

### 9.3 第 2 阶段：联系人匹配

目标：

1. 用官方客户联系数据辅助匹配。
2. 用备注、昵称、手机号等弱标识辅助匹配。
3. 支持人工确认。

验收：

1. 明确匹配、模糊匹配、未匹配三种状态。
2. 模糊匹配不自动写入企业详情。
3. 人工确认后后续同会话可自动归档。

### 9.4 第 3 阶段：时间线展示与 AI 草稿

目标：

1. 联系人详情展示企业微信采集消息。
2. 企业详情只展示已归属联系人的消息。
3. AI 可基于历史消息生成摘要和回复草稿。

验收：

1. 页面明确展示来源为 `wecom_client_capture`。
2. AI 草稿不触发自动发送。
3. 销售可复制草稿或跳转到企业微信客户端处理。

## 10. 风险分级

| 风险 | 等级 | 说明 | 处理方式 |
| --- | --- | --- | --- |
| 企业微信协议升级导致失效 | 高 | 私有协议字段、加密或登录流程变化 | 仅作为实验增强线，保留官方主线 |
| 账号触发安全校验 | 高 | 登录异常、验证码、设备限制 | 使用测试账号，异常立即停用 |
| 消息匹配错误 | 高 | 同名客户或弱标识导致归错联系人 | 默认进入待归档池，人工确认 |
| 重复消息 | 中 | 断线重连或重放导致重复事件 | DB 唯一键幂等 |
| 漏消息 | 中 | 离线、掉线、补偿失败 | 记录采集断点和健康状态 |
| 语音/附件处理复杂 | 中 | 编码、下载、转码、存储成本高 | 第一阶段只做元数据和引用 |
| 合规争议 | 高 | 员工/客户聊天数据采集敏感 | 明确授权、告知、审计和开关 |

## 11. 与正式 MVP 的关系

正式 MVP 不依赖本 PoC 成功。

如果 PoC 成功：

1. 可作为企业微信消息归档增强能力。
2. 可辅助客户在未开通会话内容存档前做内部试用。
3. 可为 AI 摘要、跟进提醒、回复草稿提供更多上下文。

如果 PoC 失败：

1. 不影响企业、联系人、标签、多渠道身份管理。
2. 不影响 WhatsApp、邮件、电话纪要能力。
3. 不影响企业微信客户联系 API 同步。
4. 不影响官方会话内容存档接入预留。

## 12. 产品口径

对内可以称为：

```text
企业微信客户端消息辅助归档实验模块
```

对客户不应称为：

```text
企业微信官方消息接口
企业微信官方聊天同步
企业微信自动收发系统
企业微信免存档聊天记录同步
```

推荐对外描述：

```text
系统支持企业微信客户联系资料同步，并预留企业微信会话内容存档接入能力。在授权测试环境中，可评估企业微信客户端消息辅助归档能力，用于内部沟通记录沉淀和 AI 辅助分析；最终发送仍由销售本人在企业微信客户端完成。
```

## 13. 推荐决策

建议保留两条线：

1. 正式产品线：客户联系 API + 会话内容存档 + AI 草稿 + 销售本人发送。
2. 技术探索线：只读客户端消息采集 PoC。

第一阶段开发时，CRM 核心模型必须保持渠道中立。无论消息来自 WhatsApp API、邮件、电话纪要、企业微信会话存档，还是企业微信客户端采集，最终都进入统一的 `Communication Message` 模型。

私有协议只能存在于适配层，不能成为 CRM 的业务真相源。
