# 把后台的企业微信拉到前台：可行性与方案

> 需求原话：**「单纯把后台的企业微信拉到前台就行，不需要定位到具体的聊天窗」**。两个平台（Windows / macOS）都要。
> 本文只出方案，不含代码改动。

---

## 1. 先说结论

**你现在的「唤起」其实是「启动」。**

页面上那个按钮发出的是**裸 `wxwork://`**（`WeComConversationPanel.tsx:36` 对非群聊写死），
它对企业微信的含义只有一句：「确保客户端在运行」。**没有任何「打开某个会话」的语义**。
于是：

| 企业微信当前状态 | 它的行为 | 你看到的现象 |
| --- | --- | --- |
| 未运行 | 启动进程 | 新窗口天然在前台 → **像是唤起了** |
| 已在后台 | 收到一个「无事可做」的请求 | **不动窗口** → 像是失败了 |

所以「只能唤起没启动的」不是随机现象，而是裸协议语义的必然结果。

**而「把已运行的应用窗口拉到前台」这件事，纯浏览器做不到** —— 浏览器沙箱不允许 JS 操作其它应用的窗口。
网页唯一能做的对外动作就是请求打开一个 URL scheme，而**要不要激活窗口，决定权在操作系统和客户端自己手里**，不在网页。

## 2. 两个平台的机制（这一节决定「有没有解」）

| | macOS | Windows |
| --- | --- | --- |
| 谁处理这个 scheme | LaunchServices | 注册表 `HKCU\Software\Classes\wxwork\shell\open\command` |
| 已运行的实例怎么收到 | 通过 Apple Event 投递 URL | **新进程**把参数经 IPC 转发给旧实例，然后自己退出 |
| 会不会激活窗口 | LaunchServices 打开 URL 时**默认会 activate** 目标应用 | 由**旧实例**调 `SetForegroundWindow` ⇒ 会被系统**前台锁定**拒绝 |
| 纯 Web 能否拉到前台 | **值得实测，可能本来就通** | **不可靠**，取决于企业微信自己怎么实现 |

微软官方对这个问题的定性（原文 *Foreground activation permission is like love: You can't steal it, it has to be given to you*）：

> 单实例程序里，第二个实例把命令行转发给第一个实例后，第一个实例调 `SetForegroundWindow` **会失败** ——
> 因为窗口管理器看到的是「它只是收到了一条消息，就决定抢前台」，而那条消息不是输入消息，
> 所以它没有任何资格拿前台。

⚠️ 注意：**第二个实例是有前台权限的**（它是被用户点击启动的），**第一个实例没有**。
这就是为什么「未启动时能唤起」——那时窗口是**第二个实例自己的**。

**一个容易被忽略的线索**：Windows 在拒绝置前时，默认行为是**让任务栏图标闪烁**。
也就是说企业微信其实已经在任务栏提醒你了，只是没人告诉你去看。

## 3. 三条路线（按成本从低到高）

### 路线 1：体验兜底（零成本，但仍要配合下面的路线）

不再指望可靠置前，而是**把「没反应」变成「一句话」**：唤起后探测网页是否真的失焦，没失焦就明确提示用户。

```js
// 示意，非最终代码
location.href = 'wxwork://';
setTimeout(() => {
  // hasFocus() 比 document.hidden 准：同窗口内切标签也算失焦
  if (document.hasFocus()) {
    message.info('企业微信已在后台运行，请点任务栏（Windows）/ Dock（macOS）上的图标切换过去');
  }
}, 1200);
```

- 优点：零依赖、零部署，立刻能让用户知道该干什么。
- 局限：**不解决问题**，只是把沉默变成提示。

### 路线 2：macOS 先实测（零成本，可能白捡）

macOS 的 LaunchServices 在打开 URL scheme 时**默认会 activate 目标应用** —— 那么 macOS 上
**现在这版裸 `wxwork://` 理论上就应该能把后台的企业微信切到前面**。如果你实测确实不行，
那说明还有别的原因（最常见的是**企业微信被最小化**或**在另一个桌面 Space**，而不是「在后台」）。

**一个 30 秒的自测方法**（浏览器里点一次按钮，然后立刻看）：

```bash
# 唤起动作发生后，看前台应用到底是谁（macOS 自带，不需要任何权限）
lsappinfo info -only name "$(lsappinfo front)"
```

如果输出是企业微信 ⇒ macOS 侧本来就是通的，问题只在 Windows。
如果仍然是浏览器 ⇒ 再往下查它是最小化了还是在别的 Space（`Mission Control` 里看一眼）。

### 路线 3：本地协议处理器（**唯一能「确定有效」的方案**）

思路：**不再让浏览器直接唤起企业微信**，而是唤起一个**我们自己的、由用户点击启动的本地小程序**，
由它去激活企业微信窗口 —— 因为它有前台权限，`SetForegroundWindow` 不会被拒。

网页侧只需要换一个 `href`：

```html
<a href="focus-wecom://">在企业微信中打开</a>
```

**macOS 实现**（一个最小 `.app`，约 5 行脚本）：

```bash
APP=~/Applications/FocusWeCom.app
osacompile -o "$APP" -e 'on open location theURL
    tell application "企业微信" to activate
end open location'
# 注册 focus-wecom:// 协议
P="$APP/Contents/Info.plist"
/usr/libexec/PlistBuddy -c "Add :CFBundleURLTypes array" "$P"
/usr/libexec/PlistBuddy -c "Add :CFBundleURLTypes:0 dict" "$P"
/usr/libexec/PlistBuddy -c "Add :CFBundleURLTypes:0:CFBundleURLName string com.crmforlogistics.focuswecom" "$P"
/usr/libexec/PlistBuddy -c "Add :CFBundleURLTypes:0:CFBundleURLSchemes array" "$P"
/usr/libexec/PlistBuddy -c "Add :CFBundleURLTypes:0:CFBundleURLSchemes:0 string focus-wecom" "$P"
```

- 首次使用 macOS 会弹一次「允许控制企业微信」的自动化授权，之后静默。
- 也可反过来再支持 `wxwork://` 作为回退（没装 helper 的机器不至于完全没反应）。

**Windows 实现**（同样的原理，换成一个极小 exe 或现成小工具）：

1. 注册协议 `focus-wecom` 指向一个 exe；
2. exe 里做：`FindWindow` 找到企业微信主窗口 → `ShowWindow(SW_RESTORE)`（应对最小化）
   → `SetForegroundWindow`；若仍失败，用 `AttachThreadInput` 把当前线程与目标窗口线程关联后再置前
   （这是社区里公认能绕过前台锁定的做法）。

```bat
:: 注册（HKCU 即可，不需要管理员）
reg add "HKCU\Software\Classes\focus-wecom" /ve /d "URL:Focus WeCom" /f
reg add "HKCU\Software\Classes\focus-wecom" /v "URL Protocol" /d "" /f
reg add "HKCU\Software\Classes\focus-wecom\shell\open\command" /ve /d "\"%LOCALAPPDATA%\CRM\focus-wecom.exe\" \"%%1\"" /f
```

- 优点：**确定有效**，Windows/macOS 都能解决；网页侧改动极小（换一个 href）。
- 成本：需要在每台销售电脑上装一次（可用组策略 / MDM 批量推，也可让首次登录时自动下载安装）。

## 4. 顺带发现（与本问题无关，但是个确实的漏实现）

后端 `ThreadService.java:150` 构造 `WeComGroupThreadResponse` 时，第 5 个实参写死 `null` ——
而那个位置正是 `openClientUrl`。所以**群聊的「在企业微信中打开」按钮根本不渲染**
（前端 `WeComGroupHeader.tsx:33` 是 `openClientUrl ? <Button/> : null`）。

有意思的是**同一个方法上一行已经算出了 `chatId`**（`groupChatId(source.providerConversationKey())`），
只是没拿去拼 URL。前端测试里期待的格式是 `wxwork://message?chatid=<chatId>`。

> 但这**不影响**「拉不到前台」这个问题 —— 群聊按钮现在是压根不显示，不是显示了没用。
> 如果之后要让群聊也能跳，那是另一件事，且它同样受本文第 2 节的平台限制。

## 5. 建议的推进顺序

1. **先按路线 2 自测一次 macOS**（30 秒，零成本）——很可能 macOS 侧本来就是好的。
2. 给所有唤起按钮**加路线 1 的兜底提示**（零成本，立刻改善体验，且不依赖任何部署）。
3. 如果 Windows 侧必须可靠置前，再评估**路线 3**：先在一台机器上做 helper 验证可行性，
   再决定是否批量部署（这一步涉及分发，属于产品决策，不只是技术问题）。
