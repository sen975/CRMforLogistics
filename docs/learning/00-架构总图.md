## 一句话定位

「多渠道消息中心」——不管消息从哪来（企业微信 / 邮件 / 短信模板 / WhatsApp / 电话录音），都**归一化**成同一种「消息」，统一落库、统一展示在会话里、统一发送。

## 技术栈

Spring Boot 3.4.5 + MyBatis-Plus + PostgreSQL + MinIO（对象存储）+ React 前端；**无 Redis**。
外部依赖：企业微信（代开发应用）、阿里云 ChatApp + OSS、Meta WhatsApp、SMTP/IMAP 邮件、FunASR 语音转写。

## 一条主数据流（消息从发到收）

```
【发】前端点发送 → MessageSendApplicationService → 写 outbox_jobs（待发箱）
     → 事务提交 → 事件通知 → MessageOutboxScheduler 每秒轮询 → 实际发出
【收】渠道 webhook/轮询 收到 → 归一化成标准 message → 落库 → 投影到会话
【查】前端打开会话 → GET /api/threads → 多表联查 + 游标分页
```

类比：发消息像邮局——先写进邮筒（outbox），邮递员（scheduler）定时来取件投递，防止信弄丢。

## 后台定时任务全景（稳定性重点）

| 任务 | 频率 | 板块 |
|---|---|---|
| MessageOutboxScheduler | **1s** | 消息核心（发送） |
| ChatAppSyncScheduler | 5s + 5min | chatapp |
| EmailSyncScheduler | 5min | 邮件 |
| WeComChatDataSyncRuntime | **60s** | 企微（最重：拉取+解密+入库） |
| WeComDailySummaryScheduler | 60s | 企微 |
| WhatsAppTemplateReconciliationScheduler | 300s | WhatsApp |

## 越界依赖（架构债，改这些要小心）

- `MessageOutboxWorker` 直接依赖 chatapp 网关（核心 → 渠道，反向）
- `ChannelAccountService` 跨渠道编排
- `service/whatsapp` 复用 chatapp 网关
