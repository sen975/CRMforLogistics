## 一句话定位

「多渠道消息中心」——不管消息从哪来（企业微信 / 邮件 / 短信模板 / WhatsApp / 电话录音），都**归一化**成同一种「消息」，统一落库、统一展示在会话里。

> **出站不是统一的（2026-09-20 更正）**：入站确实全渠道归一；但出站只有 chatapp 走 outbox（`service/chatapp/outbox/`，
> `jobType` 全库唯一取值 `chatapp_send`），email 走 `channel/email/EmailSendService`、wecom 走
> `channel/wecom/WeComSendService`，两者都是**同步直发**。原表述「统一发送」在出站链路上与代码不符。

## 技术栈

Spring Boot 3.4.5 + MyBatis-Plus + PostgreSQL + MinIO（对象存储）+ React 前端；**无 Redis**。
外部依赖：企业微信（代开发应用）、阿里云 ChatApp + OSS、Meta WhatsApp、SMTP/IMAP 邮件、FunASR 语音转写。

## 一条主数据流（消息从发到收）

```
【发】前端点发送 → service/chatapp/outbox/MessageSendApplicationService → 写 outbox_jobs（待发箱）
     → 事务提交 → 事件通知 → service/chatapp/outbox/MessageOutboxScheduler 每秒轮询 → 实际发出
     （仅 chatapp 走这条异步链路；email / wecom 为同步直发）
【收】渠道 webhook/轮询 收到 → 归一化成标准 message → 落库 → 投影到会话
【查】前端打开会话 → GET /api/threads → 多表联查 + 游标分页
```

类比：发消息像邮局——先写进邮筒（outbox），邮递员（scheduler）定时来取件投递，防止信弄丢。

## 越界依赖（已清零；门禁是硬规则，不是基线）

门禁 `ArchitectureBoundaryTest` 曾把 51 条历史越界冻结成基线、**只对新增越界失败** —— 那是为了「能立即合入而不把构建当场打红」搭的过渡脚手架。
2026-09-20 四步清理把基线推到 **0**，脚手架已一并拆除（`FreezingArchRule` → 普通规则，删掉 `archunit_store/` 与 `archunit.properties`）：
**现在任何一条新越界都会让构建当场变红。** 完整清单与处理方式见 [docs/代码板块地图.md](../../代码板块地图.md) 第四节。

**归零过程 51 → 40 → 32 → 0**，四步全部「只删不加」：

- ~~`MessageOutboxWorker` 直接依赖 chatapp 网关（11 条）~~ —— **已修复**：归类错误（chatapp 专属 outbox 被放进消息核心），出站三件套搬到 `service/chatapp/outbox/`
- ~~`service/whatsapp` 复用 chatapp 网关（3 个文件 / 8 条）~~ —— **已修复**：命名拆分的后果（whatsapp 与 chatapp 底层同为阿里云 CAMS）。CAMS 供应商原语（凭证三件套）搬到 `infrastructure/cams/`，`ChatAppPublicTemplateGateway` 接口随消费方搬到 `service.whatsapp.template/`
- ~~`service/account`、`service/aitopic` 依赖 wecom 渠道实体（2 个文件 / 28 条）~~ —— **已修复**：实体归属漂移。`WeComUserBindingEntity` / `WeComMessageSummaryJobEntity` 从 `channel/wecom/` 归位到 `entity/`（`entity/` 里早已有 7 个 WeCom 实体，`type-aliases-package` 也只声明了 `…entity`）
- ~~`WhatsAppHistorySyncWorker` 依赖 `channel/chatapp/ChatAppMessageSyncService`（4 条）~~ —— **已修复**：归类错误（消费 `whatsapp_history_sync_jobs` 表、驱动 CAMS 同步适配器，与 `service/chatapp` 下 3 个同型 job worker 同类），worker 归位到 `service/chatapp/`
- ~~`ChannelAccountService` 跨渠道编排（债在 `switch(channelType)` + 硬编码凭证表，不在依赖方向，故从来不在基线内）~~ —— **已修复**：抽出渠道注册表（`ChannelType` + `ChannelTypeRegistry`），`switch` 与凭证表已删除，新增渠道只需加一个实现类

**写代码时的约束**（门禁会强制）：业务域访问渠道必须经由 `service.channel` 编排层，或走对应板块的内部结构，
不得直接 import `channel` 包下的网关 / 凭证解析器 / 实体。白名单只有三个包
（`service.channel` / `service.wecom` / `service.chatapp`），**加白名单要写明理由，它不是过测试的开关**。

另有一处**不属于门禁范围、但已记录**的残留：`service/channel/ChatAppCapabilityService` 在判断账号是否为
WhatsApp 账号时写死了 `"chatapp"/"whatsapp"`。它是 CAMS 能力探测服务、本身就是 WhatsApp 专属代码，
不是核心对渠道的感知，故未纳入注册表。
