# 踩坑与经验（bug 教训、review 反馈、工作方法）

> **踩坑经验最值钱。** 每修一个 bug / 每次 review，抽 1 条。
> 条目格式同模式库。

---

## 1. 异步任务的日志/追踪不贯穿

【类别】踩坑经验
【名称】traceId/MDC 不自动传到异步线程
【一句话】后台 scheduler/worker 的日志不会带请求的 traceId，排查异步任务只能靠日志密度 + 时间戳，加全局 traceId 过滤器对它们无效
【本项目实例】`MessageOutboxScheduler`、`WeComChatDataSyncRuntime` 等异步链路
【能迁移到】任何用异步/多线程 + 日志排查的系统

## 2. 核心域直接依赖渠道网关 = 越界

【类别】踩坑经验
【名称】核心模块不该 import 具体渠道实现；但先分清是「依赖写错」还是「**归类错误**」
【一句话】依赖方向应该是「业务 → 基础设施、业务 → 渠道」，反向 import 一经发现要先判病根：**多数情况是这个类放错了包，而不是依赖方向写反了**。直接抽接口做抽象，往往只是把归类问题包装成了架构复杂度
【本项目实例】`service/message/MessageOutboxWorker` → `channel/chatapp/ChatAppOutboundGateway`（原架构债 #1）。判为**归类错误**的证据很硬：这套 outbox 的 `jobType` 全代码库唯一取值 `chatapp_send`、租约前缀写死 `chatapp-outbox-`、错误码全 `CHATAPP_*`、装配开关名自带渠道 —— 它就是 chatapp 专属出站队列。2026-09-20 处置：出站三件套整体搬到 `service/chatapp/outbox/`，**零抽象**，越界随之消失
【能迁移到】设计分层时先定好依赖方向；review 时盯反向 import，但动手前先问「这个概念的 owner 到底是谁」，而不是条件反射地抽端口
