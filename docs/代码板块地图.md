## 二、板块详情

### 板块 1 · 消息核心

- **职责**：消息的收发、会话（conversation）、线程（thread/分页时间线）。
- **文件范围**：`service/message/`、`service/conversation/`。
  > chatapp 的出站链路（outbox）已于 2026-09-20 归位到 `service/chatapp/outbox/`，不再是本板块文件。

**入口 API**

| Method | Path | Service |
|---|---|---|
| GET | `/api/messages/{id}` | MessageQueryService |
| GET | `/api/threads` | ThreadService.threadPage |
| GET | `/api/threads/wecom/contact/{contactId}` | ThreadService |
| GET | `/api/threads/wecom/group/{sourceConversationId}` | ThreadService |
| GET | `/api/conversations` | UnifiedConversationService |
| POST | `/api/send/email`、`/api/send/chatapp`、`/api/send/chatapp-media` | 见各渠道板块（发送走 outbox） |

**关键链路**

- **发送（异步，仅 chatapp）**：`service/chatapp/outbox/MessageSendApplicationService`（`@Transactional`）→ 写 `outbox_jobs`（`insertIgnore`）→ 事务提交后 `eventHub.publish("message-new")` → `service/chatapp/outbox/MessageOutboxScheduler` 自适应轮询（基线 1s、空闲退避至 5s，入队后由 `wake` 立即唤醒） → `service/chatapp/outbox/MessageOutboxWorker` 实际发送。
  > **边界澄清**：email 走 `channel/email/EmailSendService`、wecom 走 `channel/wecom/WeComSendService`，两者均为**同步直发**，不进 outbox；outbox 的 `jobType` 全代码库只有 `chatapp_send` 一个取值。所以「统一出站」这个说法在出站链路上并不成立 —— outbox 是 chatapp 专属出站队列（2026-09-20 由 `service/message` 归位到 `service/chatapp/outbox`）。
- **查询（同步）**：`ThreadService.threadPage` 多表联查（conversation + message）+ 游标分页（base64 `{occurredAt}:{messageId}`）。

**数据表**：`messages`、`conversations`、`attachments`、`outbox_jobs`、`message_status_events`、`channel_events`。

**Review 关注点**：outbox 事务边界（写 outbox 与业务写同一事务）；游标分页的正确性。

**消息核心（`service/message/`）当前只剩**：`MessageQueryService`、`ThreadService`、`TemplateMessageTextResolver`。

**压测关注点**：`GET /api/threads` 是热点（多表联查 + 排序，注意索引）；发送吞吐受 **outbox 批量 × 轮询间隔** 上限约束（基线 1s、`claimAndProcess` 批次上限 50），压「发送」要同时观察 `outbox_jobs` 积压。

**压测关注点**：**会话存档同步是本板块最重链路**（外部拉取 + 解密 + 批量入库），压测时重点观察 60s 同步的吞吐和积压；viewer 会话创建/查询依赖企微 OpenData 外部调用。

### 板块 9 · 联系人记忆（contactmemory）

- **职责**：用 LLM 从历史对话里提炼联系人的「事实记忆」与 AI 标签，经审核后写入联系人档案。
- **文件范围**：`service/contactmemory/`（11）。

**入口 API**

| Method | Path | Service |
|---|---|---|
| GET | `/api/contacts/{contactId}/memory` | ContactMemoryController → ContactMemoryQueryService |

**关键链路**：`ContactMemoryScheduler`（**600s**）扫到期的 `contact_memory_states` → `ContactMemoryWorker` 取批
→ `ContactMemoryConsolidationService` 调 `OpenAiCompatibleContactMemoryGateway`（LLM）
→ 写 `contact_memory_observations` / `contact_memory_facts` / `contact_ai_labels`，证据落在独立的 evidence 表。

**数据表**：`contact_memory_facts` / `_observations` / `_observation_evidence` / `_fact_evidence` / `_states` /
`_attempts`、`contact_profile_versions`、`contact_ai_labels` / `contact_ai_label_evidence`（V70–V73、V76 建）。

**Review 关注点**：
- `processing` 租约与 fencing（V71 引入），防止并发 worker 重复消费同一条 state。
- V76 把 `contact_ai_label_evidence.fact_id` 放开为**可空**，并将唯一约束改为 `NULLS NOT DISTINCT`。
  原设计要求「每条 AI 标签证据必须挂到一条已确证事实」，但一条事实需要两条独立证据才会晋级，
  而联系人**首轮运行永远没有事实** —— 于是首跑必然失败，且整个变更在同一事务里回滚，下一轮又从空状态开始（死循环）。

**压测关注点**：LLM 外部调用是唯一瓶颈；600s 批量扫描时关注 `contact_memory_states` 的 runnable 索引。

**提醒规则**：`WeComTodoReminderScheduler` 作为 `PollingTask` 注册进 `AdaptivePollingScheduler`，baseline = ceiling = 60 秒，因此是"每分钟扫一次"而不是秒级空转，也跑在独立调度链上：

- **当天汇总** —— 当天 `app.todo-reminder-daily-hour`（默认 0 点）起，当天还没成功发过的用户各一条，内容为其当天全部未完成待办（带时间的排前面）。判据是"当天已跨过钟点且当天未发送"而非"此刻正好是钟点"，所以服务在钟点前后重启、或用户钟点后才补建当天待办都不会漏，一天仍最多一条。幂等键 `todo_daily_reminders(user_id, reminder_date)`。
- **开始前 N 小时** —— 仅带具体时间的待办参与，进入 `(now, now + leadHours]` 窗口时逐条发送（默认提前 3 小时）。上界"还没开始"不可省：停机恢复后不应把早已开始的事项补成"即将开始"。幂等键 `todo_items.lead_reminder_sent_at`。
- 两个候选查询都 `join wecom_user_bindings`，未绑定企微的账号不进候选；单个 tick 最多发 20 条，其余顺延。
- 时区取 `app.todo-reminder-zone`（默认 `Asia/Shanghai`）：`due_date`/`due_time` 是本地日历时间语义，而 `Clock` bean 是 UTC，不显式指定会把"今天"算错。
- **说明**：本库**最小的板块**（后端 `service/todo` 仅 1 个 service 类），但链路完整 —— 前后端 + 企微自动提醒齐备。

### 4.2 架构门禁（硬规则，无冻结基线）

`backend/src/test/java/com/crmforlogistics/messagecenter/architecture/ArchitectureBoundaryTest.java`

- **当前形态是一条普通硬规则**：`noClasses().that().resideInAPackage(service..)` 且在白名单外，
  `should().dependOnClassesThat().resideInAPackage(channel..)`。**任何一条新越界都会让构建当场变红。**
- 白名单只有三个包（`service.channel` 渠道编排层 / `service.wecom` / `service.chatapp` 同板块黏合），理由逐条写在测试类里，**不要为了过测试而加白名单**。
- **历史**：2026-09-20 之前用 `FreezingArchRule` 把 51 条已有越界冻结成 `archunit_store/` 快照，只对新增越界失败
  —— 那是为了「门禁能立即合入、不把构建当场打红」而搭的过渡脚手架。四步清理把基线推到 0 之后脚手架已拆除：
  `FreezingArchRule` 换回普通规则，`archunit_store/` 与 `archunit.properties` 一并删除。
  留一个**空快照**等于留一个语义模糊的终点（会让人误以为还剩债），债还完就该拆。
- **仍然有效的两个坑**（详见测试类注释）：
  1. 不能用 `@ArchTest` + `@AnalyzeClasses`。其自定义 TestEngine 在 surefire 的 `-Dtest` 过滤下会 `Tests run: 0`，且**失败被吞** —— 门禁看着在跑，实际完全失效。必须用普通 JUnit Jupiter `@Test` 手动驱动。
  2. 包标识符不能用 `..channel..`。它会同时匹配顶层 `channel` 和 `service.channel`，把编排层的**合法**依赖误判成越界（误伤比漏判更伤门禁公信力）。要用全限定名。
- 三条**已随冻结机制作废**的历史坑（保留备查，万一将来重新引入冻结）：
  - `allowStoreCreation` **默认就是 `false`**（曾被我误记为 `true`，2026-09-20 用探针实测纠正）：
    基线缺失时 ArchUnit **报错**（`StoreInitializationFailedException`）而非静默重建 —— 这是 fail-loud 的安全默认。
    真风险在反方向：把 `allowStoreCreation=true` 写进 `archunit.properties` 再提交，基线一旦丢失才会被静默重建。
    首次冻结应用命令行 `-Darchunit.freeze.store.default.allowStoreCreation=true`（**漏 `archunit.` 前缀则属性不生效**）。
  - `allowStoreUpdate` 默认 `true`：越界修掉后快照会被**自动**回写收窄（沉默写盘，当时提交前必须单独 diff 快照确认「只减不增」）。
  - 归零时的落盘行为（实测）：最后一条违规消失时，快照文件**被截断为 0 字节、但不删除**
    （`java.nio.file.Files.write` 默认 `TRUNCATE_EXISTING`，且 `stored.rules` 索引条目保留）
    → 所以「空快照 + `allowStoreCreation=false`」不报错（`getStoredRulesFile()` 检查的是索引文件而非快照文件），
    并且空快照**不会**放行新违规。结论：留着不坏，但毫无价值。

**怎么跑**

```bash
mvn -f demo/message-center-spring/backend/pom.xml test -Dtest=ArchitectureBoundaryTest
```

**新增越界的正确处置**：改代码；若确属「同板块内部结构」或「职责本身就是协调渠道」，
在白名单 `CHANNEL_AWARE_SERVICE_PACKAGES` 补条目并写明理由。没有「临时加一个让自己过测试」这种加法。

**先例（2026-09-23）**：`message.send_email` / `message.send_chatapp` 落地时，编排逻辑放在 `service.message`
⇒ 14 条越界、构建当场变红。处置是**搬进 `service.channel`**（本就是为协调渠道而设的板块）并把渠道类型的
回执映射掉，白名单**一条没加**。这条先例值得记住：门禁拦下新代码时，先问「它该住在哪一层」，
而不是「它算不算例外」。

**当前进度**：**0 条** —— 51 → 40 → 32 → 0（2026-09-20，四步全部「只删不加」）。
归零后已用一次**故意注入的越界探针**复验：普通规则同样产出 `Failures: 1` + `BUILD FAILURE`，越界点精确报出，且不再生成任何快照文件 —— 证明门禁没被顺手拆空。

## 六、后续维护约定

- 新增 Controller/Service 时，请归入对应板块并在本文补一行入口 API。
- 板块间依赖应保持「业务 → 基础设施」单向；若出现反向依赖，先评估是否属于同一板块，否则记录到第四节。
- **容器集成测试统一用 `@Testcontainers(disabledWithoutDocker = true)`**（2026-09-20 全库拉齐，26 个容器测试类无一例外）。
  裸 `@Testcontainers` 在 Docker 不可用时抛异常、**构建变红**，把「环境不具备」误报成「代码有问题」——
  本仓历史验收记录里积压的多条「N errors 属 Docker 环境阻断」基本都是这一条造成的。
  代价是**CI 假绿风险**：Docker 挂掉时整批集成测试静默跳过、`BUILD SUCCESS` 照旧。
  → 因此**验收不能只看过不过，必须显式核对 `Skipped` 计数**，别让「跳过」冒充「通过」。
- **依赖当前时间的生产代码一律构造注入 `java.time.Clock`**。容器里虽有 `JacksonConfig.clock()` 这个 `Clock` bean，
  但本仓约定是：公开构造用 `Clock.systemUTC()`，另留包私有构造收测试注入的 `Clock`
  （见 `ContactMemoryScheduler`、`WeComApiAuditTrail`、`WeComAccessTokenService` 等 20+ 个类）。
  **禁止在业务代码里直接调 `Instant.now()`** —— 那会让测试只能靠相对时间凑合，写出「写死绝对时间戳」的定时炸弹：
  `ContactMemoryConsolidationServiceTest` 就是把 `expiresAt` 写成 `2026-09-20T04:00:00Z`，
  到点之后**永久失败**（2026-09-20 实发）。现已改为注入 `Clock` + 测试用 `Clock.fixed(...)`。
- **本文与 `docs/learning/00-架构总图.md` 是配套的两份，改一份就要改另一份。**
  2026-09-20 曾出现两份都只列 9 个板块、文件数写着 311（实际 505）的漂移：
  当时 `service/aitopic`(22)、`service/contactmemory`(11)、`service/todo`(1)、`service/channel`(8)
  四个板块已存在却未被收录。**补板块时同时更新 1.2 表格、对应小节、第三节定时任务表、第五节压测表四处。**
- 本文只描述现状，不随代码自动更新；大改后需手动同步。
