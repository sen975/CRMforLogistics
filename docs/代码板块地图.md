# 代码板块地图（Review + 压测双视角）

> **用途**：① Review 时按板块定位 diff 影响面，快速判断改动波及范围；② 压测 / 性能稳定性测试时按板块定位入口、链路和瓶颈。
> **代码基准**：当前工作区（`codex/message-center-presplit-runtime`），后端源码根 `demo/message-center-spring/backend/src/main/java/com/crmforlogistics/messagecenter`，共 311 个 Java 文件。
> **口径**：本文只做「看得清、测得准」的梳理，不涉及改构建、不改 pom、不拆微服务。

| 层 | 技术 |

## 二、板块详情

### 板块 1 · 消息核心

- **职责**：消息的收发、会话（conversation）、线程（thread/分页时间线）。
- **文件范围**：`service/message/`、`service/conversation/`。

**入口 API**

| Method | Path | Service |
|---|---|---|
| GET | `/api/messages/{id}` | MessageQueryService |
| GET | `/api/threads` | ThreadService.threadPage |
| GET | `/api/threads/wecom/contact/{contactId}` | ThreadService |
| GET | `/api/threads/wecom/group/{sourceConversationId}` | ThreadService |
| GET | `/api/conversations` | UnifiedConversationService |
| POST | `/api/send/email`、`/api/send/chatapp`、`/api/send/chatapp-media` | 见各渠道板块（发送走 outbox） |

**关键链路**

- **发送（异步）**：`MessageSendApplicationService`（`@Transactional`）→ 写 `outbox_jobs`（`insertIgnore`）→ 事务提交后 `eventHub.publish("message-new")` → `MessageOutboxScheduler` 每 **1s** 轮询 → `MessageOutboxWorker` 实际发送。
- **查询（同步）**：`ThreadService.threadPage` 多表联查（conversation + message）+ 游标分页（base64 `{occurredAt}:{messageId}`）。

**数据表**：`messages`、`conversations`、`attachments`、`outbox_jobs`、`message_status_events`、`channel_events`。

**Review 关注点**：outbox 事务边界（写 outbox 与业务写同一事务）；游标分页的正确性；`MessageOutboxWorker` 直接依赖 chatapp 网关（越界，见第四节）。

**压测关注点**：`GET /api/threads` 是热点（多表联查 + 排序，注意索引）；发送吞吐受 **outbox 1s 轮询** 上限约束，压「发送」要同时观察 `outbox_jobs` 积压。

### 板块 3 · 通话记录

- **职责**：通话记录、录音、转写。
- **文件范围**：`service/callrecord/`。

### 板块 5 · 企业微信渠道（最大板块）

- **职责**：企业微信会话存档同步、客户/群/通讯录、会话组件 viewer、群聊/单聊消息。
- **文件范围**：`channel/wecom/`（网关，30）+ `service/wecom/`（业务，46）。两者互相依赖，属同一板块。

**入口 API**（节选，完整见 controller）

| Method | Path | 说明 |
|---|---|---|
| GET | `/api/v1/wecom/installations` | 安装列表 |
| POST | `/installations/{authCorpId}/app-chats` | 应用群聊 |
| GET | `/installations/{authCorpId}/external-contacts` | 外部联系人 |
| POST | `/installations/{authCorpId}/customer-groups:search` | 客户群搜索 |
| GET | `/installations/{authCorpId}/directory/members` | 通讯录成员 |
| POST | `/installations/{authCorpId}/directory/profile-sync` | 资料同步 |
| POST | `/conversation-view/bootstrap`、`/sessions` | 会话组件 |
| POST | `/api/wecom/send`、`/api/wecom/callback` | 发送 / 回调 |

**外部 API（`channel/wecom/` 网关）**

- 授权：`gettoken`、`get_suite_token`、`get_permanent_code`、`get_auth_info`、`getuserinfo`
- 会话存档：`sync_call_program`（`/cgi-bin/chatdata/sync_call_program`）
- 应用群聊：`appchat/create` `get` `update` `send`
- 通讯录：`user/get`、`user/simplelist`、`department/list`、`tag/list`、`tag/get`
- 客户联系：`externalcontact/list` `get` `batch/get_by_user` `remark` `groupchat/list` `groupchat/get`
- 消息：`message/send`

**关键链路**：`WeComChatDataSyncRuntime` 每 **60s**（可配）拉取会话存档 → 解密（`CredentialCipher` + 公钥）→ 归一化入库。群成员靠观察消息 sender/receiver 逐步累积。

**数据表**：`wecom_source_conversations`、`wecom_source_conversation_participants`、`wecom_parties`、`wecom_chatdata_ingest_failures`、`wecom_*` 系列（约 15 张）。

**定时任务**：chatdata 同步 60s、公钥注册 60s、日报 60s、审计保留（cron）。

**Review 关注点**：解密/凭证（`CredentialCipher`、`WeComCallbackCodec`）；会话存档同步的幂等与游标（`WeComChatDataCursorMapper`）；`WeComChatDataNormalizer` 只处理 party type 1/2，type=3 机器人会抛错。

**压测关注点**：**会话存档同步是本板块最重链路**（外部拉取 + 解密 + 批量入库），压测时重点观察 60s 同步的吞吐和积压；viewer 会话创建/查询依赖企微 OpenData 外部调用。

### 板块 6 · 邮件渠道

- **职责**：邮件收发、附件、IMAP 同步。
- **文件范围**：`channel/email/`（13，网关与业务混合在此，无独立 `service/email/`）。

**入口 API**

| Method | Path | Service |
|---|---|---|
| POST | `/api/email/send` | EmailSendService |
| POST | `/api/email/send`(multipart) | EmailSendService |
| POST | `/api/email/sync` | EmailSyncService |
| POST | `/api/send/email` | （消息核心入口，复用 EmailSendService） |

**关键链路**：SMTP 发送 / IMAP 拉取（`OpenSslImapClient`、`BouncyCastle139ImapSocketFactory`）；附件存 MinIO（`EmailAttachmentStore`）。
**定时任务**：`EmailSyncScheduler` 每 **5min** 同步。
**压测关注点**：IMAP 同步是外部 I/O 重链路（5min 轮询）；附件上传走 MinIO。

### 板块 7 · 应用消息渠道 chatapp（短信/模板消息）

- **职责**：阿里云 ChatApp 消息收发、模板、广播（broadcast）、webhook 回执。
- **文件范围**：`channel/chatapp/`（15）+ `service/chatapp/`（25）。

**入口 API**

| Method | Path | Service |
|---|---|---|
| POST | `/api/chatapp/send/text`、`/send/template` | ChatAppSendService |
| POST | `/api/chatapp/sync/messages`、`/sync/templates` | 同步 |
| POST | `/api/chatapp/webhook` | webhook 接收 |
| GET | `/api/templates` | TemplateController |
| POST | `/api/v1/chatapp/broadcasts`、GET、`/{id}/failures`、`/reconcile`、`/retry-failures` | ChatAppBroadcast* |

**压测关注点**：**广播（broadcast）是最重链路**（批量发 + 对账 + 重试），压测重点；模板同步走阿里云外部 API。

## 三、后台定时任务总表（稳定性测试重点）

| 任务 | 频率 | 板块 |
|---|---|---|
| MessageOutboxScheduler | **1s** | 消息核心（发送） |
| ChatAppSyncScheduler | 5s + 5min | chatapp |
| ChatAppWebhookRetryWorker | 5s | chatapp |
| ChatAppBroadcastScheduler | cron | chatapp |
| EmailSyncScheduler | 5min | 邮件 |
| WeComChatDataSyncRuntime | **60s**（可配） | 企业微信 |
| WeComChatDataPublicKeyRegistrar | 60s | 企业微信 |

## 四、越界依赖清单（Review 重点盯）

现有代码存在 3 处「核心 → 渠道」的反向依赖，属架构泄漏，review 改动涉及这些文件时需格外注意影响面：

| # | 位置 | 问题 |
|---|---|---|
| 1 | `service/message/MessageOutboxWorker.java:3` | 核心消息域直接 import `channel/chatapp/ChatAppOutboundGateway` |
| 2 | `service/channel/ChannelAccountService.java` | 跨渠道编排同时 import chatapp + wecom + email |
| 3 | `service/whatsapp/`（1 处） | WhatsApp 复用 `channel/chatapp` 网关 |

另：`channel/wecom` ↔ `service/wecom` 双向依赖（8 + 89 处）——属同一板块（企业微信）内部黏合，不算越界，但说明 wecom 的网关与业务**不可拆开**。

## 六、后续维护约定

- 新增 Controller/Service 时，请归入对应板块并在本文补一行入口 API。
- 板块间依赖应保持「业务 → 基础设施」单向；若出现反向依赖，先评估是否属于同一板块，否则记录到第四节。
- 本文只描述现状，不随代码自动更新；大改后需手动同步。
