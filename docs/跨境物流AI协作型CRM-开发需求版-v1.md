# 跨境物流 AI 协作型 CRM 开发需求版 v1

## 一、需求变更说明

### 1.1 本版定位

本文件是 `跨境物流AI协作型CRM-开发需求版.md` 的 v1 调整版，用于明确当前客户调整后的第一阶段 MVP 范围。

新版第一阶段不再以“完整 AI 销售开发 CRM”作为首个交付目标，也不再以 Chatwoot 客服中控二开作为第一阶段技术底座。当前客户的真实业务目标是销售人员通过企业微信、WhatsApp、邮件、电话等渠道主动经营客户，系统负责客户资产管理、沟通记录沉淀、AI 话术辅助和销售协作，而不是由系统代替销售个人发送企业微信消息。

新版第一阶段 MVP 调整为一个面向跨境物流销售团队的轻量 SCRM 沟通工作台：围绕企业、联系人、销售归属和多渠道身份，把 WhatsApp、邮件、电话纪要、企业微信客户联系资料及可合规获取的沟通记录统一沉淀到 CRM。企业微信方向不再承诺通过 Chatwoot 或第三方系统代替销售个人发一对一消息，而是采用“客户联系同步 + 会话内容存档（如已开通）+ AI 回复草稿 + 复制并唤起企业微信 + 销售本人确认发送”的合规辅助模式。

第一阶段 MVP 的核心是：

1. 企业与联系人分离管理。
2. 联系人支持多个标签。
3. 联系人与企业的归属关系由系统使用者人工设定。
4. 只有联系人被设定到某个企业后，才可以在对应企业详情中看到对方的信息和已归属沟通记录。
5. 每个联系人可以绑定多个企业微信外部联系人身份、邮箱、WhatsApp 账号和电话。
6. 系统必须保留多渠道身份路径整理能力。
7. 第一阶段重点实现销售沟通工作台、WhatsApp/邮件沟通接入、电话纪要、企业微信客户联系同步、AI 回复草稿和企业微信客户端辅助唤起。
8. Chatwoot 不再作为第一阶段核心底座；仅作为会话工作台交互、Conversation/Message 模型和多渠道中控设计的参考，后续如需要客服团队统一接待，再评估是否作为独立客服模块接入。

### 1.2 与旧版需求的关系

旧版文档中的完整客户开发管理、Topic 时间线、AI 秘书、背调、任务阶段、团队看板、问题经验库等能力仍属于长期产品方向，但不进入第一阶段 MVP 的强制交付范围。

`D:\WorkItems\CRMforLogistics\demo` 中的第一版系统前端 demo 表达的是更完整的 CRM 愿景，包含工作台、客户开发、AI 建议、任务、看板等较完整能力。该 demo 可作为后续产品体验和视觉方向参考，但第一阶段 MVP 暂不按该 demo 的完整功能范围开发。

### 1.3 第一阶段 MVP 一句话目标

先做一个面向跨境物流销售团队的 AI 协作型 SCRM 工作台：员工可以管理企业、联系人、多渠道身份和跟进记录，通过 WhatsApp、邮件、电话纪要和企业微信客户联系资料沉淀沟通路径；企业微信消息不由系统代替个人发送，而是由系统生成话术、复制内容、尝试唤起企业微信，最终由销售本人确认发送。

## 二、第一阶段 MVP 范围

### 2.1 必做能力

第一阶段 MVP 必须实现以下能力：

1. 企业管理。
2. 联系人管理。
3. 联系人标签管理。
4. 联系人与企业归属关系管理。
5. 联系人多渠道身份管理。
6. 销售沟通工作台。
7. WhatsApp 信息接入与回复能力（以官方 Business API 或客户实际服务商能力为准）。
8. 企业微信客户联系资料同步。
9. 企业微信 AI 回复草稿、复制话术、尝试唤起本机企业微信客户端。
10. 企业微信会话内容存档接入预留；如客户已开通并满足合规条件，则同步销售与外部联系人的聊天记录。
11. 邮件信息收发。
12. 电话聊天记录/电话纪要录入。
13. 沟通记录按联系人和企业归档。
14. 基础账号、权限和操作审计。
15. Chatwoot 仅作为产品交互和会话模型参考，不作为第一阶段后端底座或消息真相库。

### 2.2 暂不实现能力

以下能力不作为第一阶段 MVP 交付项：

- 完整客户开发流程。
- 完整供应商资源库。
- Topic 时间线自动推进。
- AI 自动识别联系人身份。
- AI 背调和开发建议。
- AI 自动生成任务和阶段建议。
- 老板团队看板。
- 复杂 BI 和经营分析。
- 订单、报价、财务、TMS、WMS。
- 电话录音自动转写。
- 自动替员工制定开发流程。
- 自动从历史个人 WhatsApp 账号拉取全部聊天记录。
- Chatwoot 企业微信客服 `Channel::Wecom` 二开。
- 企业微信客服 `kf/sync_msg`、`kf/send_msg` 作为第一阶段主链路。
- 第三方系统代替销售个人企业微信向个人微信客户发送一对一消息。
- 保证网页按钮每次都能精确弹出指定企业微信外部联系人聊天窗口。

这些能力可以在第二阶段及后续版本中，基于第一阶段沉淀的企业、联系人、多渠道身份和沟通记录继续扩展。

### 2.3 MVP 成功标准

第一阶段上线后，应至少满足：

- 员工可以新建、编辑、搜索企业。
- 员工可以新建、编辑、搜索联系人。
- 一个联系人可以拥有多个标签。
- 一个联系人可以绑定多个邮箱、多个 WhatsApp 账号、多个企业微信号和多个电话。
- 使用者可以人工把联系人关联到一个或多个企业。
- 企业详情页只展示已经关联到该企业的联系人和沟通记录。
- 未关联企业的联系人不会自动出现在企业详情中。
- WhatsApp 消息可以进入系统并形成沟通记录或会话。
- 企业微信外部联系人资料可以同步到系统，并与联系人、销售归属建立关系。
- 企业微信聊天记录如已开通会话内容存档并满足合规条件，可以同步为沟通记录。
- 员工可以在系统中生成企业微信回复草稿，复制话术并尝试唤起本机企业微信客户端。
- 企业微信最终发送动作由销售本人在企业微信客户端中确认完成。
- 邮件可以进入系统并形成会话或沟通记录。
- 员工可以从系统内回复 WhatsApp 和邮件。
- 员工可以手动录入电话聊天记录或电话纪要，并关联联系人/企业。
- 系统能保留每条沟通来自哪个渠道、哪个账号、哪个外部身份、哪个联系人、哪个企业。
- 企业也有多重的身份标签：供应商、客户、其他等支持自定义标签。

## 三、核心产品模型

### 3.1 企业

企业是公司、客户、供应商、海外代理、同行或内部组织的主体档案。

第一阶段企业只做基础管理，不承载复杂销售阶段和 AI 判断。

基础字段建议：

| 字段 | 说明 |
| --- | --- |
| 企业名称 | 必填，企业或组织名称 |
| 企业类型 | 客户、供应商、海外代理、同行、内部、未知、其他 |
| 国家/地区 | 可选 |
| 城市/港口 | 可选 |
| 官网 | 可选 |
| 负责人 | 当前负责员工 |
| 备注 | 人工备注 |
| 状态 | active/disabled |
| 创建人 | 系统用户 |
| 创建时间 | 系统时间 |

第一阶段不要求企业具备完整开发阶段、风险等级、合作价值评分、AI 摘要等字段；这些字段可以预留，但不作为 MVP 操作主线。

### 3.2 联系人

联系人是具体沟通对象。联系人必须与企业分离管理，不能把联系人直接嵌死在某个企业下面。

联系人可以先独立存在，再由使用者人工关联到一个或多个企业。

基础字段建议：

| 字段 | 说明 |
| --- | --- |
| 联系人姓名 | 必填，可为姓名、昵称或称呼 |
| 职位/角色 | 可选，例如采购、老板、销售、操作、财务、客服 |
| 备注 | 人工备注 |
| 标签 | 多选，可配置 |
| 状态 | active/disabled/merged |
| 创建人 | 系统用户 |
| 创建时间 | 系统时间 |

### 3.3 联系人标签

联系人标签用于描述联系人身份、业务角色、沟通特点或人工分类。

标签要求：

- 一个联系人可以拥有多个标签。
- 标签由使用者或管理员配置。
- 标签不等同于企业归属。
- 标签不决定联系人在企业详情中的可见性。
- 标签可以用于筛选、搜索和后续 AI 画像。

示例标签：

- 客户联系人。
- 供应商联系人。
- 海外代理。
- 决策人。
- 财务。
- 操作。
- 价格敏感。
- 英文沟通。
- 重点跟进。

### 3.4 联系人与企业关系

联系人与企业的关系由使用者人工设定，是第一阶段最重要的业务规则之一。

规则：

1. 联系人可以不属于任何企业。
2. 联系人可以属于一个企业。
3. 联系人可以属于多个企业，但每一条关系都必须由使用者明确创建。
4. 企业详情页只展示已经与该企业建立关系的联系人。
5. 企业详情页只展示已经归属到该企业的沟通记录。
6. 不能因为联系人邮箱域名、WhatsApp 号码、企业微信号或电话相似，就自动把联系人塞进某个企业详情。
7. 后续 AI 可以提出“疑似属于某企业”的建议，但第一阶段不作为自动写入规则。

关系字段建议：

| 字段 | 说明 |
| --- | --- |
| 企业 ID | 关联企业 |
| 联系人 ID | 关联联系人 |
| 关系类型 | 员工设定，例如客户方、供应商方、代理方、内部协作 |
| 是否主联系人 | 可选 |
| 备注 | 可选 |
| 创建人 | 谁建立该关系 |
| 创建时间 | 关系建立时间 |

### 3.5 联系人多渠道身份

每个联系人可能有多个沟通身份。系统必须把“联系人”和“渠道身份”分开，保留信息路径整理能力。

一个联系人可绑定：

- 多个企业微信外部联系人 ID、员工跟进关系或企业微信客户联系身份。
- 多个邮箱地址。
- 多个 WhatsApp 账号或 WhatsApp Business 联系人标识。
- 多个电话。

渠道身份字段建议：

| 字段 | 说明 |
| --- | --- |
| 联系人 ID | 归属联系人 |
| 渠道类型 | wecom/whatsapp/email/phone |
| 渠道账号值 | 邮箱、手机号、WhatsApp ID、企业微信 external_userid 等 |
| 展示名称 | 可选 |
| 是否主账号 | 可选 |
| 验证状态 | unverified/verified |
| 来源 | 人工录入、消息同步、导入 |
| 创建时间 | 系统时间 |

## 四、销售沟通工作台

### 4.1 模块定位

销售沟通工作台是第一阶段 MVP 的主界面和主链路。它不是传统客服系统的坐席收件箱，也不是单纯备注区，而是销售人员日常维护客户、查看沟通上下文、生成回复草稿、登记跟进结果的核心工作台。

系统应在一个统一工作台中展示来自 WhatsApp、邮件、电话记录、企业微信客户联系资料以及企业微信会话内容存档（如已开通）的沟通信息，并支持按渠道、联系人、企业、负责人、跟进状态、最近沟通时间筛选。

### 4.2 Chatwoot 的新定位

Chatwoot 不再作为第一阶段 MVP 的核心后端底座，也不承担企业微信销售沟通的发送能力。原因是本项目当前主线是销售主动经营客户，而 Chatwoot 的核心模型更适合客户进线、客服坐席分配和被动会话回复。

第一阶段对 Chatwoot 的使用方式调整为：

- 作为会话工作台交互参考。
- 借鉴 Conversation/Message/Contact/Contact Inbox 的模型思想。
- 借鉴左侧会话列表、中间消息时间线、右侧联系人资料的布局。
- 借鉴标签、未读、状态、负责人分配、消息附件展示等设计。
- 不复用 Chatwoot Rails 后端作为 CRM 主系统。
- 不把 Chatwoot 数据库表作为企业、联系人、销售归属和沟通记录的业务真相。
- 不在第一阶段开发 Chatwoot `Channel::Wecom` 企业微信客服渠道。

本项目第一阶段的业务 owner 是 Java CRM 后端。React 前端只调用 Java 后端 API。后续如客户确实需要客服团队统一接待，再将 Chatwoot 作为独立客服模块候选，而不是销售 SCRM 的第一阶段主线。

### 4.3 会话与沟通记录

第一阶段需要区分两个概念：

- 沟通线程：面向销售工作台，用于聚合同一联系人或同一渠道身份下的 WhatsApp、邮件、企业微信归档消息和电话纪要。
- 沟通记录：面向 CRM 沉淀，用于按企业、联系人、渠道路径追溯历史。

MVP 应在 Java CRM 中建立轻量沟通模型，而不是依赖 Chatwoot Conversation/Message 作为事实层。建议模型包括：

- `communication_thread`：沟通线程。
- `communication_message`：消息或记录。
- `communication_channel_identity`：渠道身份。
- `follow_up_record`：人工跟进记录。

每条沟通记录至少要保留：

| 字段 | 说明 |
| --- | --- |
| 渠道类型 | wecom/whatsapp/email/phone |
| 外部消息 ID | 渠道侧消息 ID，如无则为空 |
| 方向 | incoming/outgoing/manual/system |
| 发送人渠道身份 | 外部账号或系统用户 |
| 接收人渠道身份 | 外部账号或系统账号 |
| 内容 | 文本，后续可扩展附件 |
| 发生时间 | 渠道消息时间或人工记录时间 |
| 联系人 ID | 归属联系人，可为空 |
| 企业 ID | 归属企业，可为空，必须由关系或人工归档产生 |
| 负责人 | 当前销售或跟进员工 |
| 来源 | API 同步、会话存档、人工录入、AI 草稿、系统事件 |
| 发送方式 | direct_api/client_assisted/manual_note/archive_only |

### 4.4 企业微信辅助回复原则

企业微信个人销售沟通不做系统代发。系统只做辅助：

1. 展示客户资料、归属销售、最近沟通和上下文。
2. 生成 AI 回复草稿。
3. 复制话术到剪贴板。
4. 尝试唤起本机企业微信客户端。
5. 明确展示目标客户姓名、备注名、手机号、企业和归属销售。
6. 由销售本人在企业微信客户端确认对象、粘贴或修改内容并点击发送。
7. 发送后销售可在 CRM 点击“已发送/已跟进”，系统记录跟进结果。

系统不能承诺每次都能精确打开指定外部联系人聊天窗口。若企业微信客户端或浏览器协议不支持精确跳转，系统必须退回到“复制话术 + 打开企业微信 + 展示客户搜索信息”的兜底模式。
## 五、渠道能力

### 5.1 企业微信销售客户联系

企业微信方向调整为销售 SCRM 接入，不再优先做企业微信客服 / WeCom KF，也不把企业微信自建应用普通消息 API 误用为个人聊天代发能力。

关键原则：

- 销售使用企业微信客户端与个人微信客户沟通。
- 系统通过企业微信客户联系 API 同步外部联系人、客户归属、标签等资料。
- 如客户开通会话内容存档，并满足企业微信合规要求，系统可以同步销售与外部联系人的聊天记录。
- 系统不代替某个销售个人向个人微信客户发送一对一消息。
- 系统可以生成回复草稿、复制内容、尝试唤起企业微信客户端。
- 最终发送必须由销售本人在企业微信客户端确认完成。

企业微信 MVP 能力：

- 配置企业微信企业 ID、客户联系 Secret、通讯录/客户联系权限。
- 同步企业微信成员或销售账号。
- 同步外部联系人列表与 `external_userid`。
- 同步客户归属关系，即哪个外部联系人由哪个销售跟进。
- 同步企业微信客户标签。
- 将 `external_userid`、跟进销售 `userid`、客户备注名等信息沉淀为联系人渠道身份。
- 支持将企业微信外部联系人身份绑定到系统联系人。
- 支持将系统联系人再人工归属到企业。
- 支持 AI 生成企业微信回复草稿。
- 支持复制话术并尝试唤起本机企业微信客户端。
- 支持销售手动确认“已发送/已跟进”并形成跟进记录。

企业微信后续可选能力：

- 会话内容存档接入，用于合规同步聊天记录。
- 客户群同步。
- 离职继承/客户转接流程。
- 企业微信客服 WeCom KF 独立模块，用于真正的客服接待场景，而不是销售个人沟通场景。

边界：

- 不承诺第三方系统代替销售个人发送企业微信一对一消息。
- 不承诺网页按钮每次都能精准打开指定企业微信外部联系人聊天窗口。
- 不使用企业微信客服 `kf/send_msg` 伪装销售个人沟通。
- 不把自建应用接收消息回调当作外部联系人聊天内容来源。
### 5.2 WhatsApp

WhatsApp 第一阶段目标是实现业务号码消息进入销售沟通工作台，并支持员工从系统回复。

MVP 能力：

- 配置 WhatsApp Business 或第三方服务商账号。
- 接收 WhatsApp webhook 消息。
- 发送 WhatsApp 文本消息。
- 保存 WhatsApp 联系人标识。
- 将 WhatsApp 标识绑定到系统联系人。
- 支持一个联系人绑定多个 WhatsApp 账号。

边界：

- 不承诺拉取员工个人 WhatsApp 历史聊天。
- 不承诺绕过 WhatsApp 官方或服务商合规限制。
- 模板消息、媒体消息、群聊等可作为后续扩展。

### 5.3 邮件

邮件第一阶段目标是把邮件纳入销售沟通工作台，而不是先做复杂邮件营销或完整邮箱客户端。

MVP 能力：

- 配置邮箱账号。
- 接收邮件。
- 发送邮件。
- 展示邮件会话或邮件线程。
- 保存发件人、收件人、抄送、主题、正文、附件元数据。
- 将邮箱地址绑定到系统联系人。
- 支持一个联系人绑定多个邮箱。

边界：

- 可优先支持常见 IMAP/SMTP 或服务商 API。
- Gmail、Outlook、腾讯企业邮、阿里邮箱等可以作为适配目标，但第一阶段应先确认客户实际账号条件和授权方式。
- 复杂邮件规则、营销群发、邮件模板审批不进入 MVP。

### 5.4 电话聊天记录/电话纪要

电话第一阶段不做自动录音转写，而是支持人工录入电话聊天记录或电话纪要。

MVP 能力：

- 员工录入电话记录。
- 选择或新建联系人。
- 选择或新建电话渠道身份。
- 可选关联企业。
- 记录沟通时间、沟通对象、纪要内容、下一步备注。
- 在联系人详情和企业详情中查看已归属电话记录。

边界：

- 不采集电话录音。
- 不做自动转写。
- 不做电话号自动归档到企业。

## 六、关键业务流程

### 6.1 新联系人进入系统

1. WhatsApp、邮件、企业微信客户联系同步或电话记录产生一个外部沟通身份。
2. 系统检查该渠道身份是否已绑定联系人。
3. 如果已绑定，则沟通记录进入该联系人对应沟通线程。
4. 如果未绑定，则生成未归属联系人/未知身份记录。
5. 员工可以创建新联系人，或把该渠道身份绑定到已有联系人。
6. 员工可以为联系人添加标签。
7. 员工可以把联系人关联到一个或多个企业。
8. 只有完成企业关联后，企业详情中才展示该联系人及相关沟通。
### 6.2 企业详情查看沟通

1. 使用者进入企业详情。
2. 系统读取该企业下已建立关系的联系人。
3. 系统读取这些联系人已归属到该企业的消息和电话记录。
4. 系统展示企业维度沟通历史。
5. 未建立企业关系的联系人不展示。
6. 未归属企业的消息不展示在企业详情，只保留在销售沟通工作台或待整理队列。

### 6.3 多账号归并

1. 同一个联系人可能先后通过企业微信、WhatsApp、邮箱、电话出现。
2. 每个渠道账号先作为独立渠道身份保存。
3. 员工确认这些身份属于同一个人后，绑定到同一个联系人。
4. 后续该联系人的多渠道沟通可以在联系人详情中统一查看。
5. 企业详情中是否展示这些沟通，仍取决于联系人和企业是否建立关系，以及消息是否归属到该企业。

### 6.4 沟通与回复

1. 员工在销售沟通工作台打开联系人或沟通线程。
2. 系统根据渠道类型展示不同操作。
3. WhatsApp 消息如接入官方 Business API 或服务商 API，可从系统内直接回复。
4. 邮件消息可从系统内直接回复。
5. 企业微信销售沟通不从系统代发；系统生成 AI 草稿并提供“复制话术并打开企业微信”。
6. 企业微信打开后由销售本人确认客户、粘贴或修改内容并发送。
7. 如果浏览器或客户端不能精确打开目标客户，系统展示客户姓名、备注名、手机号、企业、归属销售，销售自行搜索发送。
8. 销售发送后可点击“已发送/已跟进”，系统记录跟进结果。
9. 电话沟通由员工手动录入纪要。
10. 所有沟通记录都要能归属到联系人；是否进入企业详情取决于联系人与企业关系及人工归档规则。
## 七、权限与隐私

### 7.1 基础角色

| 角色 | 第一阶段权限 |
| --- | --- |
| 员工 | 处理分配给自己的会话，维护自己有权限的企业和联系人 |
| 主管 | 查看团队会话和团队客户沟通情况 |
| 管理员 | 配置渠道账号、用户、权限、标签和基础字典 |
| 老板 | 可查看汇总和授权范围内数据，默认不直接看全部沟通原文 |

### 7.2 权限原则

- 前端隐藏不是权限真相，服务端必须做数据范围校验。
- 企业详情只展示与该企业建立关系的数据。
- 联系人多渠道身份归并必须可追溯。
- 渠道账号密钥、邮箱授权、WhatsApp token、企业微信 secret 必须加密保存。
- 查看敏感沟通原文应记录审计日志。
- 管理员负责配置，不等于默认拥有所有客户沟通原文查看权。

## 八、技术方向

### 8.1 主线技术选择

第一阶段技术主线调整为：

- Java/Spring Boot 后端作为 CRM 业务 owner。
- React 前端作为销售工作台。
- 企业、联系人、标签、销售归属、多渠道身份、沟通记录、跟进任务均由 Java CRM 自己建模。
- 企业微信接入走客户联系 API、通讯录/成员能力、客户标签能力；会话内容存档作为已开通客户的合规增强能力。
- WhatsApp 和邮件按客户实际账号条件接入官方 API 或服务商 API。
- Chatwoot 不作为第一阶段底座；仅作为会话工作台、消息时间线、多渠道身份设计的参考。

### 8.2 不以 Chatwoot 作为 MVP 核心底座

第一阶段不再建议封装 Chatwoot 作为核心客服中控，原因：

- 当前真实需求是销售主动经营客户，不是客服坐席被动接待。
- 企业微信个人销售消息不能由第三方系统代替员工发送。
- Chatwoot 的 account/inbox/conversation/message 模型会引入 Rails 与 Java CRM 双事实源问题。
- 第一阶段更重要的是企业、联系人、销售归属、多渠道身份和销售跟进闭环。
- 直接复用 Chatwoot 后端会增加集成、权限、数据对账和后续裁剪成本。

Chatwoot 可借鉴内容：

- 左侧会话列表、中间消息时间线、右侧联系人资料的工作台布局。
- Conversation/Message/Contact/Contact Inbox 的模型思想。
- 标签、未读、负责人、状态、附件展示等交互模式。
- 后续如客户需要客服团队统一接待，可作为独立客服模块重新评估。

### 8.3 企业微信接入边界

企业微信接入必须围绕销售 SCRM 能力，而不是企业微信客服 API。

第一阶段企业微信内容包括：

- 企业微信应用配置。
- access_token 获取与 IP 白名单配置。
- 客户联系 API 接入。
- 外部联系人同步。
- 成员/销售账号同步。
- 客户归属关系同步。
- 客户标签同步。
- external_userid、follow_userid、备注名等字段保存。
- 渠道身份和系统联系人绑定。
- AI 回复草稿生成。
- 复制话术与企业微信客户端唤起尝试。
- 销售手动确认发送后的跟进记录。

明确不做：

- `Channel::Wecom` 企业微信客服二开作为 MVP 主线。
- `kf/sync_msg`、`kf/send_msg` 作为销售个人沟通链路。
- 自建应用普通消息回调作为外部联系人聊天内容来源。
- 系统代替销售个人发送企业微信一对一消息。

## 十、第一阶段验收用例

1. 创建企业 A。
2. 创建联系人 John。
3. 给 John 添加“客户联系人”“重点跟进”等多个标签。
4. 给 John 绑定两个邮箱、一个 WhatsApp 账号、一个企业微信 external_userid、一个电话。
5. 在未关联企业 A 前，企业 A 详情不展示 John。
6. 使用者手动把 John 关联到企业 A。
7. 企业 A 详情开始展示 John。
8. 企业微信客户联系同步后，系统能看到 John 的 external_userid、跟进销售、备注名或标签信息。
9. 在 John 的联系人详情中点击“企业微信回复”。
10. 系统根据上下文生成回复草稿。
11. 员工点击“复制话术并打开企业微信”。
12. 系统复制话术，并尝试唤起本机企业微信客户端。
13. 如果无法精确打开 John 的聊天窗口，系统展示 John 的姓名、备注名、手机号、企业和归属销售，提示销售自行搜索发送。
14. 销售在企业微信客户端确认对象并发送。
15. 销售回到 CRM 点击“已发送/已跟进”，系统生成一条跟进记录。
16. WhatsApp 收到 John 的消息后，销售沟通工作台出现对应记录或会话。
17. 员工从系统回复 WhatsApp 消息，状态显示发送成功或失败原因。
18. John 的邮箱发来邮件后，系统可展示邮件沟通。
19. 员工从系统发送邮件回复。
20. 员工录入一次电话纪要并关联 John 和企业 A。
21. 联系人详情中可以看到 John 的 WhatsApp、企业微信资料/归档记录、邮件和电话记录。
22. 企业 A 详情中可以看到已归属到企业 A 的 John 相关沟通。
23. 删除或解除 John 与企业 A 的关系后，企业 A 详情不再展示 John 的联系人信息；历史审计仍可追溯。
## 十一、后续阶段方向

第一阶段完成后，后续可以在已有数据基础上逐步恢复和扩展旧版 CRM 愿景：

1. AI 对联系人和企业进行摘要。
2. AI 根据多渠道沟通建议联系人标签和企业归属。
3. AI 生成沟通摘要。
4. Topic 时间线。
5. 客户开发任务和阶段。
6. 老板/主管团队看板。
7. 背调和开发建议。
8. 问题经验库。
9. 报价机会和订单推进。
10. Chatwoot 作为独立客服模块接入，用于真正的客服团队统一接待。
11. 企业微信客服 WeCom KF 接入，用于客服账号场景，而不是销售个人企业微信场景。

后续扩展必须基于第一阶段沉淀的多渠道身份、联系人企业关系、销售归属、跟进记录和企业维度沟通历史，而不是重新发明一套并行数据模型。

## 十二、最终边界结论

第一阶段 MVP 的核心不是完整 CRM，也不是完整 AI 销售秘书，而是先把跨境物流业务最基础、最高频、最能沉淀数据的沟通入口做好。

当前推荐主线是：

> 以 Java CRM 和 React 销售工作台为第一阶段主线，打通企业、联系人、标签、多渠道身份、企业微信客户联系同步、WhatsApp/邮件沟通、电话纪要和 AI 辅助回复；企业微信不由系统代替销售个人发送，而是采用“生成草稿、复制话术、尝试唤起企业微信、销售本人确认发送”的合规辅助模式。Chatwoot 不再作为 MVP 核心底座，仅作为后续客服模块候选和交互设计参考。
